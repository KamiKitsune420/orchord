# Guest accessibility after boot: audio, VoiceOver during install, keyboard pass-through and the VM console (Intel macOS guest on a Windows 11 host)

Research date: 2026-10-09. Evidence labels used below: **[source code]** = I read the file directly; **[docs]** = official documentation; **[maintainer claim]** = stated by a project maintainer, not independently verified; **[first-hand report]** = a user describing their own result; **[snippet only]** = I only saw a search-engine summary because the site refused direct fetch (AppleVis and AudioGames.net returned HTTP 403 to every direct fetch, so all AppleVis/AudioGames material here is snippet-level and should be re-read by a human before being quoted).

Headline for the report writer: I found **no** published guide, forum post or blog in which a blind person describes installing Intel macOS in a VM on a Windows host without sighted help. Every building block exists separately (kext-free guest audio on macOS 12+, VoiceOver in Recovery, QMP key injection, Windows OCR, NVDA sleep mode), but nobody has documented the chain end to end, and the chain has two unproven links: (1) whether guest audio works inside Recovery/the installer, and (2) whether macOS boots at all under WHPX.

---

## 1. Audio in macOS guests under QEMU (devices, kexts, Recovery vs post-install, host backends on Windows)

### Takeaway
As of 2026 the best-supported path is version-dependent: `virtio-sound-pci` (QEMU >= 8.2) is reported to give kext-free audio on macOS 12 Monterey through 26 Tahoe (user-tested on 14, 15 and 26 only), while 10.13-11.x still need `intel-hda`/`ich9-intel-hda` plus VoodooHDA, which is choppy and, from 11.3 on, unreliable when injected by OpenCore. Nobody has documented whether any of these produce sound inside Recovery/the installer, which is exactly where a blind user first needs it.

### Cited Findings

**What each project ships today**
- **[source code]** kholia/OSX-KVM `OpenCore-Boot.sh` uses `-device ich9-intel-hda -device hda-duplex` with **no** `-audiodev` argument; USB sound card `usb-host` lines are present but commented out. — [OSX-KVM OpenCore-Boot.sh](https://github.com/kholia/OSX-KVM/blob/master/OpenCore-Boot.sh)
- **[source code]** OSX-KVM's shipped OpenCore `config.plist` injects Lilu, VirtualSMC, WhateverGreen, VoodooPS2Controller (+VoodooPS2Keyboard plugin), AppleMCEReporterDisabler, USBToolBox/UTBMap. It injects **no audio kext** (no VoodooHDA, no AppleALC), and has `AudioSupport=false`, `PickerAudioAssist=false`, `PlayChime=Auto`. So a stock OSX-KVM guest is silent until the user installs a kext after install. — [OSX-KVM config.plist](https://github.com/kholia/OSX-KVM/blob/master/OpenCore/config.plist)
- **[docs]** OSX-KVM `notes.md`, "Virtual Sound Device": points to chris1111/VoodooHDA-OC, says it works on macOS 10.12 to Big Sur 11.2, "Do NOT mix VoodooHDA with AppleALC", and "The emulated sound output can be choppy, and distorted. Use Sound Card / USB Sound Card passthrough instead." It also says a cheap USB sound card "works pretty well on macOS *without* requiring" extra drivers when passed through. — [OSX-KVM notes.md](https://github.com/kholia/OSX-KVM/blob/master/notes.md)
- **[source code]** sickcodes/Docker-OSX `Dockerfile` generates `-audiodev ${AUDIO_DRIVER:-alsa},id=hda -device ich9-intel-hda -device hda-duplex,audiodev=hda` and `-device usb-kbd,bus=xhci.0 -device usb-tablet,bus=xhci.0`. — [Docker-OSX Dockerfile](https://github.com/sickcodes/Docker-OSX/blob/master/Dockerfile)
- **[docs]** Docker-OSX README (PulseAudio section) states that AppleALC, `alcid` and VoodooHDA-OC "do not have codec support" for the emulated device, although IORegistryExplorer "does show the controller component working". This **conflicts** with OSX-KVM's statement that VoodooHDA-OC works up to 11.2. — [Docker-OSX README](https://github.com/sickcodes/Docker-OSX/blob/master/README.md); contradicted by [OSX-KVM notes.md](https://github.com/kholia/OSX-KVM/blob/master/notes.md)
- **[source code]** quickemu selects the sound card by macOS release: `monterey|ventura|sonoma|sequoia|tahoe` -> `sound_card="virtio-sound-pci"` (comment: "macOS 12+ (Monterey onwards) supports virtio-sound-pci natively"); `big-sur` -> `ich9-intel-hda` (comment: "Big Sur uses VirtIO but usb-audio/VoodooHDA don't work reliably ... Fall back to ich9-intel-hda which may work with VoodooHDA"); older -> default `intel-hda` with `hda-micro`. Device strings: HDA is `-device ${sound_card} -device ${sound_duplex},audiodev=audio0`; virtio is `-device virtio-sound-pci,audiodev=audio0`. — [quickemu script](https://github.com/quickemu-project/quickemu/blob/master/quickemu)
- **[maintainer claim]** quickemu commit eb54549 (Martin Wimpress, 2026-01-25): "VoodooHDA injected via OpenCore stopped working from macOS 11.3+ onwards and usb-audio proved unreliable for Big Sur+. virtio-sound-pci works natively on macOS 12+ without kexts and fixes guest audio for affected versions." — [quickemu commit eb54549](https://github.com/quickemu-project/quickemu/commit/eb54549353edaa14432b006e99e77b1089eddbbc)
- **[docs]** quickemu wiki audio table: Monterey-Tahoe `virtio-sound-pci` "Native VirtIO driver, works out-of-the-box"; Big Sur `ich9-intel-hda` "Requires VoodooHDA kext; unreliable from 11.3+"; Catalina and earlier `intel-hda` "Requires VoodooHDA kext"; "Gatekeeper and System Integrity Protection (SIP) must be disabled to install it"; alternatively pass through a USB audio device "for reliable audio on any version". — [quickemu wiki: Create macOS virtual machines](https://github.com/quickemu-project/quickemu/wiki/03-Create-macOS-virtual-machines)
- **[first-hand reports]** quickemu issue #1642 (opened 2025-05-03 by rockyhetherington): `-audio driver=sdl,model=virtio` "Allows both input and output of audio to/from macOS guests with no further modification"; tested by the author on macOS 15 only (macOS 12 was inferred from Apple's Virtualization framework adding virtio sound in macOS 12). Confirmed on Sonoma by wilkesreid (2025-08-13, "great") and on a macOS 26 Tahoe VM by mal1k-me (2025-11-08). No failure reports in the thread. Requires QEMU 8.2+. Nobody in the thread tested macOS 12 or 13, Recovery/installer, or audio quality. — [quickemu issue #1642](https://github.com/quickemu-project/quickemu/issues/1642)
- **[first-hand reports]** Earlier quickemu discussion #951 (2024): one user had no sound on Catalina even after trying VoodooHDA OC; another had sound on Catalina that broke after upgrading the guest to Ventura. — [quickemu discussion #951](https://github.com/orgs/quickemu-project/discussions/951)
- **[docs]** QEMU's own virtio-snd documentation describes the device generically and only names Linux (`CONFIG_SND_VIRTIO`) as a guest; it does not mention macOS guests. — [QEMU VirtIO Sound docs](https://www.qemu.org/docs/master/system/devices/virtio/virtio-snd.html)
- **[docs, 2019]** Gerd Hoffmann's 2019 inventory of Apple's `AppleVirtIO.kext` listed virtio-console/serial, virtio-blk and virtio-9p personalities only (no sound) — consistent with sound arriving later (macOS 12). — [kraxel.org: macOS guest support for qemu](https://www.kraxel.org/blog/2019/06/macos-qemu-guest/)
- **[docs]** Community VoodooHDA-on-QEMU guide (Dastux, undated): `-audiodev pa,id=audio0 -device intel-hda -device hda-output,audiodev=audio0`; VoodooHDA 3.01 copied to `/Library/Extensions` after `csrutil disable` (or `csrutil enable --without kext`), approval in Security & Privacy, reboot; "expected to work" on Big Sur/Monterey/Ventura; "VoodooHDA has a poor audio quality, you will most likely hear stuttering or distortion"; no crackling fix offered. Note every one of those install steps (Recovery Terminal, a Security-pane approval click) is itself a sight-dependent step if there is no audio yet. — [Dastux VoodooHDA-QEMU-KVM.md](https://github.com/MobCode100/Dastux/blob/main/VoodooHDA-QEMU-KVM.md)
- **[docs]** A QEMU issue titled "usb-audio does not work with Mac OS" exists upstream (I did not read the body; title only). — [QEMU issue #446](https://gitlab.com/qemu-project/qemu/-/work_items/446)

**macOS 26 Tahoe and the HDA path**
- **[docs]** Dortania: AppleHDA.kext "is no longer present in macOS 26, resulting in AppleALC not working"; digital paths (HDMI, DP, USB adapters) keep working; VoodooHDA is the suggested fallback and needs lowered SIP and install to `/Library/Extensions`. — [Dortania: macOS 26 Tahoe](https://dortania.github.io/OpenCore-Install-Guide/extras/tahoe.html)
- Consequence for QEMU: on Tahoe, an AppleALC-with-QEMU-layout approach is dead; HDA audio would need VoodooHDA installed post-install with SIP lowered. — [Dortania: macOS 26 Tahoe](https://dortania.github.io/OpenCore-Install-Guide/extras/tahoe.html)

**QEMU audio backends that exist on a Windows host**
- **[source code]** QEMU `audio/meson.build` (master, fetched 2026-10-09) defines backends alsa, coreaudio, dsound, oss, pa, sdl, jack, sndio, pipewire, spice, plus dbus (only if `dbus_display`). **There is no `wasapi` backend in upstream QEMU.** `meson.build` enables dsound when `host_os == 'windows'`, and the default priority on non-Linux hosts is `pa, coreaudio, dsound, sndio, oss` then `sdl`. So on Windows the realistic choices are `dsound` and `sdl`. — [QEMU audio/meson.build](https://github.com/qemu/qemu/blob/master/audio/meson.build); [QEMU meson.build](https://github.com/qemu/qemu/blob/master/meson.build)
- **[docs]** Generic `-audiodev` options: `timer-period` (microseconds, default 10000), per-direction `out.mixing-engine`, `out.fixed-settings` (default on), `out.frequency` (default 44100), `out.channels` (2), `out.format` (s16), `out.voices`, `out.buffer-length` (microseconds). Backend-specific: `dsound` has `latency` (microseconds, default 10000); `sdl` has `out.buffer-count`; `wav` writes to a file (`path`, default `qemu.wav`); `none` discards. — [QEMU invocation docs](https://www.qemu.org/docs/master/system/invocation.html)
- **[first-hand report]** With newer QEMU, an HDA codec with no audiodev configured fails at start with "no default audio driver available"; fix is an explicit `-audiodev ...,id=X` + `audiodev=X` on the codec. — [Ubuntu Discourse: macOS Sequoia 15.2 VM sound error](https://discourse.ubuntu.com/t/qemu-macos-sequoia-15-2-vm-runs-well-vmm-kvm-fails-to-start-with-sound-error/52902)

**WHPX caveat (affects everything else)**
- **[first-hand report]** QEMU issue #4385: macOS 13.7.8 via OVMF+OpenCore under `-accel whpx` on Windows 11 24H2 (AMD Ryzen 7 9700X, QEMU 11.0.50 dev build + 4 upstream WHPX patches) dies deterministically in earliest kernel boot with "WHPX: Unexpected VP exit code 4"; the same guest boots under KVM; no maintainer response, no workaround. — [QEMU issue #4385](https://gitlab.com/qemu-project/qemu/-/work_items/4385)

### Inferences
- For macOS 12-26 the project should default to `-device virtio-sound-pci,audiodev=snd0 -audiodev dsound|sdl,id=snd0` and treat it as the only candidate for **kext-free** audio, because a kext-free device is the only kind that can possibly work in Recovery/the installer without OpenCore injection. Whether Apple's virtio sound driver is present in BaseSystem/Recovery is untested (see Gaps) — this is the single most valuable experiment for orchord.
- For 10.13-10.15 the only documented route is `intel-hda`/`ich9-intel-hda` + VoodooHDA. To have speech in the installer, orchord would have to pre-inject VoodooHDA via OpenCore `Kernel -> Add` (OpenCore-injected kexts are loaded for any macOS kernel it boots, including the installer). This is plausible for <= 11.2 given OSX-KVM's "10.12 to 11.2" statement, but I found no report of anyone verifying VoiceOver speech in a 10.13-10.15 installer under QEMU.
- Big Sur 11.3+ and (without virtio) Tahoe are the worst cases: OpenCore-injected VoodooHDA is reported unreliable from 11.3, virtio-sound is only claimed from 12. Big Sur may have **no** working audio during install. Recommend orchord mark Big Sur as "not blind-installable" until tested, or install 10.15/12 and upgrade.
- A dual-device configuration (HDA controller for OpenCore's AudioDxe picker speech + virtio-sound for macOS itself) is technically coherent since each is consumed by a different layer; untested.
- The `wav` audiodev is a cheap automated test oracle: orchord's CI/self-test can boot a guest with `-audiodev wav`, trigger VoiceOver, and check that the WAV is non-silent — a way to verify "guest audio works" without ears.

### Gaps
- **Recovery/installer audio is undocumented for every device.** No source states whether virtio-sound, usb-audio or OpenCore-injected VoodooHDA yields sound in macOS Recovery, the installer environment, or Setup Assistant under QEMU.
- No independent confirmation of virtio-sound on macOS 12 or 13 (only 14, 15, 26 user-tested), and no evidence of which kext/driver class binds (no `ioreg`/`system_profiler` output published).
- No data on virtio-sound audio quality, latency or behaviour after guest sleep on macOS; no data at all on any QEMU macOS audio device **on a Windows host** (all reports are Linux/macOS hosts).
- AC97 (`AC97`), `es1370`: no macOS-guest reports found. AppleALC with a QEMU-specific layout-id: Docker-OSX says no codec support; I found no working layout-id claim.
- DarwinKVM: its repository front page gave no audio guidance in what I could retrieve; I did not locate its docs' audio page. UTM: irrelevant on Windows and on Apple Silicon it uses Apple's Virtualization framework for macOS guests; I found no Intel-macOS-guest audio statement from UTM.
- No published latency-tuning recipe for `dsound`/`sdl` on Windows for speech (values for `out.buffer-length`, `dsound latency`, `timer-period` must be determined empirically).
- Sample-rate mismatch and "audio stops after sleep" reports specific to macOS guests: not found (only generic VoodooHDA "choppy/distorted").

## 2. Audio in macOS guests under Hyper-V, VMware Workstation and VirtualBox

### Takeaway
Hyper-V exposes no audio device to a macOS guest at all, and the maintainer's only workarounds (BlackHole + a network streaming app, VirtualHere USB-over-IP, or GPU passthrough on Server editions) all require a working, already-configured guest — so Hyper-V cannot deliver VoiceOver speech during installation. VMware Workstation (via OC4VM) is the only other Windows backend with an emulated sound card, but on Tahoe it needs VoodooHDA plus SIP changes post-install.

### Cited Findings
- **[docs]** acidanthera/MacHyperVSupport supported devices: heartbeat, guest shutdown, time sync, host-to-guest file copy, PCI passthrough (partial), PS/2 keyboard (Gen1 only), synthetic graphics, **synthetic keyboard, synthetic mouse**, synthetic network, synthetic IDE (Gen1), synthetic SCSI. No audio and no serial/COM device is listed. All Intel macOS versions supported (10.4+; separate Monterey+ kext). — [MacHyperVSupport README](https://github.com/acidanthera/MacHyperVSupport)
- **[docs]** Qonfused/OSX-Hyper-V README: "By default, Hyper-V does not expose an audio device to macOS." Supported 10.4 to 26.0, with Tahoe marked "In Progress". Default resolution 1024x768 with 8 MB VRAM, no acceleration. DDA (device passthrough) "is only available for Windows Server and Microsoft Hyper-V Server versions 2016 and newer" — i.e. not on Windows 11 Pro. "Tiger Lake and newer require a Comet Lake CPUID spoof" (relevant to the i7-1355U). — [OSX-Hyper-V README](https://github.com/Qonfused/OSX-Hyper-V)
- **[maintainer statement, 2024-07-11]** OSX-Hyper-V issue #9 "How to enable audio support?" (opened 2024-06-10, closed "not planned", labelled known-issue / workaround available): "Hyper-V unfortunately does not provide audio virtualization." Workarounds named: GPU passthrough via DDA (with problems getting AppleALC/WhateverGreen patches applied early enough); "the best option at the moment" is a virtual loopback device (BlackHole) captured and sent to the host by a network app (maintainer used OBS Ninja), or a networked USB audio interface via VirtualHere. No user in the thread confirms a working setup. — [OSX-Hyper-V issue #9](https://github.com/Qonfused/OSX-Hyper-V/issues/9)
- **[snippet only]** AppleVis thread "Hyper-V Audio Support": a user states Hyper-V "doesn't emulate a virtual audio device" and that there is "no option to add audio device in Hyper-V". — [AppleVis: Hyper-V Audio Support](https://applevis.com/comment/164892)
- **[snippet only]** A blind JAWS-list user reported that under Hyper-V "Narrator does not turn on, just hear caps lock on and off", and under VMware Player was "able to use the windows 10 talking installer" but speech stopped after reboot. (Windows guest, but it is first-hand blind-user evidence that Hyper-V consoles are silent during setup.) — [jfw.groups.io topic 78656637](https://jfw.groups.io/g/main/topic/78656637)
- **[docs]** DrDonk/OC4VM: an OpenCore boot disk for Intel macOS in VMware Fusion and **Workstation Pro 17.6 and 25H2 on Windows and Linux**, no VMware patching (successor to the archived Unlocker); guests Big Sur through Tahoe; separate Intel and AMD templates; host CPU needs AVX, AVX2, F16C, RDRAND; fixes booting to Recovery ("broken in VMware's EFI implementation"); credits VoodooHDA and "VoodooHDA for Tahoe" (chris1111). States Apple-Silicon-only macOS 27 "Golden Gate" or later cannot run. — [OC4VM](https://github.com/DrDonk/OC4VM)
- **[third-party guides, 2025-26]** For macOS Tahoe on VMware Workstation: "By default, audio doesn't work"; fix is to boot OpenShell from the OpenCore menu, run `CsrUtil.efi disable 0xA85`, then install the "VoodooHDA Tahoe" package and approve the blocked system software in System Settings. Every one of those steps is post-install and visually driven. — [Techy Druid: macOS Tahoe on VMware](https://techydruid.com/macos-tahoe-vmware/); [Tips 4 IT: macOS 26 Tahoe in VMware on Windows](https://www.tips4it.com/run-macos-26-tahoe-vmware-windows/)
- **[maintainer statement]** OpenCore's AudioDxe has "basic VMware support" for UEFI-stage audio, but sound was distorted/interrupted in testing; "boot chime plays on both QEMU and VMware" while sample sequences (picker audio assist) were dropped/choppy. — [acidanthera/bugtracker #740](https://github.com/acidanthera/bugtracker/issues/740)
- **[docs]** Broadcom KB for VMware sound: `sound.present = "TRUE"`, `sound.filename = "-1"`, `sound.autodetect = "TRUE"`; the article (written for Windows guests) says to remove `sound.virtualDev = "hdaudio"` to fall back to the default device. — [Broadcom KB 339532](https://knowledge.broadcom.com/external/article/339532/sound-is-not-working-in-windows-virtual.html)
- **[first-hand report]** InsanelyMac/AudioGames-adjacent reports of no sound in macOS guests on VMware Workstation 10 and VirtualBox (10.13) exist; details not retrieved. — [InsanelyMac: VMware Workstation 10 OSX no sound](https://www.insanelymac.com/forum/topic/293098-new-vmware-workstation-10-osx-no-sound/)

### Inferences
- Hyper-V is disqualified as a backend for an unassisted blind **install**. It could only be offered with a pre-built, pre-configured disk image (SSH enabled, a network audio sender already installed), which orchord cannot legally redistribute and cannot build without first completing a silent install. If Hyper-V is supported at all, it should be flagged "requires sighted help or OCR-only installation; no speech until network audio is configured".
- Enhanced Session Mode/RDP audio redirection is a Windows-guest feature and no source suggests it works for macOS guests; treat as unavailable.
- VMware Workstation is the fallback backend with an emulated HDA device: for pre-Tahoe guests AppleHDA may drive VMware's HD Audio device natively (this is how macOS guests on Fusion traditionally have sound), which would mean audio in Recovery/installer without kexts — but I found no source confirming that on Workstation + OC4VM, so it must be tested.

### Gaps
- No source states whether audio works in macOS Recovery/installer on VMware Workstation (any macOS version), nor which `sound.virtualDev` OC4VM's templates use.
- VirtualBox macOS-guest audio (Intel HD Audio / AC97): nothing reliable retrieved; VirtualBox macOS guests on non-Apple hosts are in any case unsupported by Oracle.
- No report of USB passthrough of a physical sound card to a macOS guest under Hyper-V on Windows 11 Pro (Hyper-V has no generic USB passthrough; VirtualHere is USB-over-IP and needs a guest client).
- Whether any Hyper-V macOS user has actually got VoiceOver speech out via BlackHole + network streaming: no reports.

## 3. VoiceOver in the macOS installer, Recovery and Setup Assistant

### Takeaway
Apple documents Command-F5 as the VoiceOver toggle, and blind users report it works in macOS Recovery after waiting for Recovery to finish loading (with quirks: Fn may be needed for F-keys, Command-Tab does not work). All of that evidence is from real Macs with working audio; I found no per-version (10.13 to 26) confirmation and nothing about which voices BaseSystem contains.

### Cited Findings
- **[docs]** Apple VoiceOver User Guide, "Turn VoiceOver on or off": "Press Command-F5"; on a Mac or Magic Keyboard with Touch ID, hold Command and quickly press Touch ID three times; or ask Siri; or System Settings > Accessibility > VoiceOver; Option-Command-F5 opens the Accessibility Shortcuts panel. The guide's version selector runs from High Sierra through macOS 27 Golden Gate. (Touch ID and Siri routes are irrelevant in a VM: only Command-F5 is usable.) — [Apple: Turn VoiceOver on or off](https://support.apple.com/guide/voiceover/turn-voiceover-on-or-off-vo2682/mac)
- **[docs]** Apple's login-window guidance: Command-F5 turns VoiceOver on manually at the login window. — [Apple VoiceOver guide (login window, es-LAMR edition)](https://support.apple.com/es-lamr/guide/voiceover/vo2755/mac)
- **[snippet only, old thread]** AppleVis "Recovery mode and VoiceOver": boot to Recovery (Command-R), "Wait about 2 minutes for it to boot up, then press Command and F5 to start VoiceOver as usual"; function keys "do not act as standard function keys when in Recovery mode" so Fn may be needed on laptops; "Cmd+tab doesn't work in recovery, so you'll need to invoke the application chooser with VO+f1". The thread is very old (search summary dated it at roughly 12 years). — [AppleVis: Recovery mode and VoiceOver](https://www.applevis.com/forum/accessibility-advocacy/recovery-mode-voiceover)
- **[snippet only]** Another AppleVis thread (2015): wait ~30 seconds after Command-R, then Command-F5; one participant reported it did not work for them. — [AppleVis: Problems using Disk Utilities in OS X](https://applevis.com/comment/35426)
- **[snippet only]** AppleVis threads on Internet Recovery conflict: one poster says "Internet recovery is completely accessible via voiceover"; others say a sighted person may be needed to know when the download finished, and a 2016 user's Internet Recovery stalled silently. — [AppleVis: Can Internet Recovery be used with VoiceOver?](https://www.applevis.com/forum/macos-mac-app-discussion/can-internet-recovery-be-used-voiceover)
- **[third-party article]** TechRepublic: at the Recovery welcome screen press Command+F5 (or Command+Fn+F5 on Apple laptops) to enable VoiceOver; then Control+Option+arrows to reach the Install button and Space to activate. — [TechRepublic: How to use macOS with only a keyboard](https://www.techrepublic.com/article/how-to-use-macos-with-only-a-keyboard/)
- **[docs, low confidence in exact wording]** Apple's "Export, import, and reset VoiceOver preferences" page refers to starting VoiceOver in Recovery Mode as part of a reset procedure, i.e. Apple itself treats VoiceOver-in-Recovery as a supported state. I only saw a search summary of this page. — [Apple: Export, import, and reset VoiceOver preferences](https://support.apple.com/guide/voiceover/export-import-and-reset-voiceover-preferences-vo27926/mac)
- **[first-hand report, 2026-06]** A known VoiceOver quirk: pressing Command-F5 twice in quick succession may not toggle; press again. — [AppleVis: command f5 not toggling voiceover](https://applevis.com/forum/macos-mac-apps/command-f5-not-toggling-voiceover)
- **[docs]** Lume (a macOS VM tool for Apple Silicon) notes that "Sequoia can still show the Accessibility step of Setup Assistant on its first display boot" — confirming Setup Assistant has a dedicated Accessibility pane in recent releases. — [Lume: how unattended setup works](https://cua.ai/docs/concepts/how-lume-unattended-setup-works)
- **[docs]** VMware-specific: `macosguest.forceRecoveryModeInstall = "TRUE"` in the .vmx forces a macOS guest to boot to Recovery without timing a Command-R press (2017, Fusion). — [Der Flounder: boot macOS VM to Recovery HD in Fusion](https://derflounder.wordpress.com/2017/08/01/setting-a-macos-vm-to-automatically-boot-to-recovery-hd-using-vmware-fusion/)
- **[snippet only, 2016]** AudioGames.net thread "MAC OS X virtual machines please?": blind users asking for macOS VMs on Windows chiefly to get MacinTalk voices; replies note licensing problems. No walkthrough. — [AudioGames forum topic 20096](https://forum.audiogames.net/viewtopic.php?id=20096)

### Inferences
- The "wait, then Command-F5" pattern means orchord must tell the user **when** Recovery has finished loading — silence is ambiguous (still loading vs no audio vs VoiceOver failed). The manager should detect readiness itself (framebuffer stops changing / OCR finds "macOS Utilities" or "Recovery"/language chooser text) and announce it through NVDA, then offer a one-key "Start VoiceOver in guest" action that injects `meta_l`+`f5` via QMP.
- Because Recovery is used here as the *installer* (OpenCore boots BaseSystem from a recovery image), VoiceOver in Recovery is the critical path for every version, not an edge case.
- After Command-F5, a verification step is needed: capture guest audio for ~3 s (or OCR for the VoiceOver caption panel) and report "VoiceOver is speaking" / "No guest audio detected".

### Gaps
- **No per-version confirmation** (10.13, 10.14, 10.15, 11, 12, 13, 14, 15, 26) that Command-F5 works in Recovery/BaseSystem; no information on which voice (Fred/Alex/Samantha, compact vs none) BaseSystem ships, or its language behaviour before a language is chosen.
- The Setup Assistant spoken prompt ("press Escape to learn how to use VoiceOver") — I could not retrieve an Apple page documenting it; its existence/timing per version is unverified here.
- **No first-hand account found of a blind person installing macOS in VMware/QEMU/Hyper-V on Windows**, and no guide titled or shaped like "installing macOS in a VM as a blind user". Searches of AppleVis, AudioGames.net, r/Blind-style queries and blog queries returned only the reverse case (Windows guest on a Mac) and one 2016 AudioGames request thread. Mastodon blind-tech posts were not searchable with the tools available.
- No blind-hackintosh install write-up found either (the closest material is OpenCore's own audio-assist documentation, section 4).

## 4. OpenCore boot picker accessibility (PickerAudioAssist, AudioDxe on QEMU, skipping the picker, serial)

### Takeaway
OpenCore has a real pre-boot screen reader (`PickerAudioAssist`, Command+F5 toggle, pre-recorded phrases) but it depends on AudioDxe, which is an HDA-only "staging" driver that the maintainers describe as choppy on QEMU for exactly the multi-sample speech the picker uses. The robust design is to make the picker unnecessary: fixed default entry, `ShowPicker=false` (or a short `Timeout`), and OpenCore logging to a serial port that orchord reads.

### Cited Findings

### Inferences
- Do not make picker speech a dependency. Design so the user never has to choose in the picker: orchord generates the OpenCore config per phase — phase "install": only the recovery/BaseSystem image and the empty target are attached, `Timeout` small, default = installer; phase "second-stage install" and "normal": default = the macOS volume. The stage transitions (the installer reboots 2-3 times and the default entry must switch from "macOS Base System" to "macOS Installer"/the target volume) are the fragile part; OpenCore normally follows the Startup Disk NVRAM choice macOS sets, which requires emulated NVRAM to persist (OVMF vars file writable).
- When the user does need the picker (e.g. to boot Recovery later), offer manager-side actions instead of in-guest interaction: "Boot to Recovery next time" can be implemented by orchord sending held `meta_l`+`r` via QMP during the takeoff window, or by regenerating config; no picker UI needed.
- Picker audio assist can still be offered as an *experimental* option on HDA configurations (it costs only an HDA device, AudioDxe and ~the OcBinaryData audio files); because it only speaks canned entry types it is of limited use even when it works.
- OpenCore serial log -> QEMU `-serial` chardev (pipe/TCP) -> orchord text log pane is a fully screen-reader-readable channel for the pre-kernel phase and gives deterministic "OpenCore reached boot entry X" events.

### Gaps
- No confirmed report of **picker audio assist working intelligibly under QEMU** (any version) after the 0.7.7 fixes; the tracking issue still describes it as choppy and is open.
- Whether AudioDxe works at all under WHPX or TCG on Windows (the only TCG data point is a 2021 hang).
- AudioDxe has no virtio-sound or USB audio support (HDA only per docs), so a virtio-only VM has no UEFI-stage audio; the dual-device idea is untested.
- OVMF's own setup UI over serial (`-serial` + OVMF console redirection) was not researched in depth; standard OVMF does mirror its text console to serial, but I have no source confirming this for the OVMF builds shipped with Windows QEMU packages.
- Whether macOS kernel verbose output can be routed to the emulated serial port on current macOS (boot-args such as `serial=`) was not verified.

## 5. Keyboard pass-through from Windows to the guest, and coexisting with NVDA/JAWS

### Takeaway
Three separate problems must be solved: (a) the host screen reader eats Insert/Caps Lock and its own commands unless it is put to sleep for the console process (NVDA: `sleepMode = True` in an app module, or NVDA+Shift+S per session); (b) Windows itself reserves Win+L and Ctrl+Alt+Del, so "Windows key = Command" can never be a complete mapping; (c) QEMU's stock GTK window hard-codes Ctrl+Alt as its hotkey modifier, which is the same chord as VoiceOver's Control+Option modifier. Only (c) is avoidable by configuration (`-display sdl,grab-mod=rctrl`) — (a) and (b) need orchord's own design.

### Cited Findings

**NVDA**
- **[docs]** NVDA 2026.2 User Guide: the NVDA modifier can be "the insert, numpadInsert, and/or capsLock key"; by default both Insert keys. Sleep mode (NVDA+Shift+S desktop / NVDA+Shift+Z laptop) "disables all NVDA commands and speech/braille output for the current application ... most useful in applications that provide their own speech or screen reading features"; "NVDA will only retain the Sleep Mode setting until it is restarted." NVDA+F2 "Tells NVDA to pass the next key press straight through to the active application". — [NVDA User Guide](https://download.nvaccess.org/documentation/userGuide.html)
- **[docs]** NVDA 2026.2 Developer Guide: an app module can set `sleepMode = True`, which "almost completely disables NVDA within that application"; scripts can opt back in with `allowInSleepMode` ("A boolean indicating whether this script should run when sleep mode is active", default False). App modules are named after the executable (e.g. `notepad.py` for `notepad.exe`); where the executable name conflicts with Python naming rules, a global plugin can call `appModuleHandler.registerExecutableWithAppModule()`. NVDA exposes a `decide_handleRawKey` extension point that runs "before any NVDA processing". — [NVDA Developer Guide](https://download.nvaccess.org/documentation/developerGuide.html)
- **[source code]** NVDA ships exactly this pattern for a self-voicing app: `source/appModules/dosvox.py` is nothing but `class AppModule(appModuleHandler.AppModule): sleepMode = True`. — [NVDA dosvox.py](https://github.com/nvaccess/nvda/blob/master/source/appModules/dosvox.py)
- **[source code]** NVDA's bundled app modules (directory listing fetched 2026-10-09) include none for `vmware`, `vmware-vmx`, `vmconnect`, `mstsc`, `VirtualBoxVM` or `qemu-system-*`. - **[docs]** Feature requests show the limits of today's sleep mode: "Add a global sleep mode" (#18856), "Sleep mode part of profile configuration request" (#3721), "Partial sleep mode (only report messages generated from a plugin)" (#11333), "Braille display sleep mode" (#20023). **JAWS and the reverse case (evidence of the modifier-key collision)**

**Injecting keys without a focused guest window (QMP)**
- **[source code / docs]** `send-key` (since 1.3): array of keys pressed simultaneously, `hold-time` default 100 ms. `input-send-event` (since 2.6): separate key-down / key-up events (`InputKeyEvent {key, down}`), plus button and absolute-axis events (range 0-0x7fff). ### Inferences
- **Mapping**: a USB HID keyboard presents the PC "GUI/Windows" key as Command and Alt as Option to macOS, so the natural mapping is Win=Command, Alt=Option, Ctrl=Control. VoiceOver's modifier is then Ctrl+Alt (or Caps Lock), and Command-F5 is Win+F5. (General knowledge; not verified against an Apple page in this research.)
- **Stock QEMU GTK is unusable for VoiceOver users**: its Ctrl+Alt+G / Ctrl+Alt+F / Ctrl+Alt+digit hotkeys sit on the Control+Option chord, so common VO commands would be swallowed or would release the grab. Stock SDL with `grab-mod=rctrl` avoids the chord collision, but an SDL window exposes nothing to NVDA except its title. Recommendation: orchord owns the console window and the key capture, and runs QEMU with `-display none`.
- **Win+L cannot be delivered**, so "Command-L" (Safari/ Finder "Go to location" equivalents) typed as Win+L will lock the host instead. Orchord needs at least one alternative Command mapping that avoids the Windows key entirely — e.g. a user-selectable "Right Ctrl acts as Command" or "swap Alt and Win" option, implemented by translating in orchord before sending QMP `input-send-event`. This is a design requirement, not a nicety.
- **Recommended capture design**: orchord's console window installs its own `WH_KEYBOARD_LL` hook only while "keyboard captured" is on and its window is foreground; it swallows everything except the release chord and forwards events over QMP as discrete down/up events (needed so that Ctrl+Alt can be *held* as the VO modifier while other keys are tapped — `send-key` with a fixed hold time is not sufficient for that). Low-level hooks are called most-recently-installed first, and NVDA also uses one, so hook ordering between NVDA and orchord is not deterministic; relying on NVDA sleep mode for the console process is the dependable way to stop NVDA consuming Insert/Caps Lock. (Hook-ordering statement is general Win32 knowledge, uncited.)
- **Ship an NVDA add-on with orchord** containing (1) an app module for the console executable with `sleepMode = True`, registered via `registerExecutableWithAppModule` if the exe name is not a valid Python identifier, and (2) optionally an `allowInSleepMode` script for the release key. Without the add-on, instruct users to press NVDA+Shift+S in the console (session-only, per the user guide). Put the console in a **separate process** from the wx manager so the manager's dialogs are not put to sleep.
- **Speaking while NVDA sleeps**: since sleep mode suppresses NVDA output for the focused app, capture/release announcements should be pushed explicitly (Controller Client `speakText`, with SAPI/earcon fallback when NVDA is not running or JAWS is in use). Whether Controller Client speech is honoured while the foreground app is in sleep mode needs a test (see Gaps). Distinct earcons for "captured" and "released" are the screen-reader-independent fallback.
- **Release key**: Right Ctrl is the least harmful choice — it is QEMU SDL's built-in alternative (`rctrl`), macOS/VoiceOver users conventionally use the left Control with Option, and it is not an NVDA/JAWS modifier. A single tap of Right Ctrl (VirtualBox-style host key) is easier than a chord; offer it as default with a setting. Avoid Ctrl+Alt (VO chord), Insert, Caps Lock, and anything with the Windows key.
- **Caps Lock as VO modifier**: QEMU's own hook deliberately never grabs Caps Lock, and Windows will toggle host caps state; if users want Caps Lock as the VoiceOver modifier, orchord's hook must swallow it and track down/up itself, and NVDA must be asleep (or not using Caps Lock as its modifier).

### Gaps
- JAWS: I could not retrieve Freedom Scientific documentation for JAWS's per-application sleep mode or its pass-key-through command; the JAWS equivalents of the NVDA mechanisms are **unverified** here and must be checked against JAWS help before being documented for users. Narrator was not researched.
- No source documents how VMware Workstation, VirtualBox or VMConnect consoles interact with NVDA on Windows (which keys reach the guest, whether NVDA sleeps); only one mailing-list anecdote for VirtualBox.
- Untested: whether `nvdaController_speakText` speaks while the foreground application is in NVDA sleep mode; whether NVDA's low-level hook or an application's wins for Insert/Caps Lock when both are installed.
- No authoritative Apple citation gathered for PC-keyboard modifier mapping or the VoiceOver modifier definition (well known, but uncited here).
- RegisterHotKey and Raw Input were not compared in detail; Raw Input cannot *block* keys from reaching the system (general knowledge, uncited), which is why a low-level hook is still needed for the Windows key.

## 6. Console / display options and their accessibility

### Takeaway
None of QEMU's own windows (GTK or SDL) offers anything to a screen reader beyond a title bar, and I found no accessibility testing of them on Windows. The viable architecture is headless QEMU (`-display none`, optionally `-vnc` on localhost) driven over QMP by orchord's own wx console, which is then free to expose a title, a status line and spoken state changes.

### Cited Findings
- **[source code]** Display types and build conditions: `none` (always), `gtk` (CONFIG_GTK), `sdl` (CONFIG_SDL), `spice-app` (CONFIG_SPICE), `dbus` (CONFIG_DBUS_DISPLAY, since 7.0), `curses`, `egl-headless`, `cocoa`. `default` picks the first available of gtk, sdl, cocoa, vnc. — [QEMU qapi/ui.json](https://github.com/qemu/qemu/blob/master/qapi/ui.json)
- **[docs]** `-display none` suppresses video output while the guest still sees an emulated graphics card. `-vnc` options include `password`, `share`, `key-delay-ms` (default 10), `power-control`, and `audiodev` (QEMU's VNC server can carry guest audio to clients that implement QEMU's audio extension). — [QEMU invocation docs](https://www.qemu.org/docs/master/system/invocation.html)
- **[docs]** QEMU's D-Bus display has Windows-specific listener interfaces: `org.qemu.Display1.Listener.Win32.Map` (`ScanoutMap`/`UpdateMap`, "Windows specific shared memory scanouts" via a file-mapping handle) and `...Win32.D3d11` (shared Direct3D textures). It also defines `Keyboard.Press/Release`, `Mouse.SetAbsPosition`, and an `Audio` interface (`RegisterOutListener`) — so one channel can carry framebuffer, input and audio. Peer registration is described in terms of a Unix socket FD. — [QEMU D-Bus display docs](https://www.qemu.org/docs/master/interop/dbus-display.html)
- **[source code / docs]** QMP: `screendump` (since 0.14) writes the framebuffer to a file; `device`/`head` since 2.12; `format` `ppm` (default) or `png` since 7.1. `query-status` returns `{running, status}`. Events: `SHUTDOWN` (with `guest` and `reason`), `RESET`, `POWERDOWN`, `STOP`, `RESUME`, `GUEST_PANICKED`. `query-vnc`, `change-vnc-password`, `set_password` exist for VNC management. — [QEMU qapi/ui.json](https://github.com/qemu/qemu/blob/master/qapi/ui.json); [QEMU QMP reference](https://www.qemu.org/docs/master/interop/qemu-qmp-ref.html)
- **[source code]** Other projects' display choices for macOS guests: OSX-KVM `-device vmware-svga` (SPICE line commented out) with `-monitor stdio`; quickemu `vmware-svga` ("macOS has native VMware display driver support"), GTK default with `grab-on-hover=on`, falling back to SDL. — [OSX-KVM OpenCore-Boot.sh](https://github.com/kholia/OSX-KVM/blob/master/OpenCore-Boot.sh); [quickemu script](https://github.com/quickemu-project/quickemu/blob/master/quickemu)
- **[docs]** Docker-OSX documents fully headless operation: `-nographic -serial null` with `-monitor telnet::45454,server,nowait`, plus a VNC variant on localhost:8888, and SSH on a forwarded port. — [Docker-OSX README](https://github.com/sickcodes/Docker-OSX/blob/master/README.md)
- **[source code]** quickemu's `--braille` option (QEMU's `-usbdevice braille` / braille chardev) "Requires SDL" and is enabled only when the host kernel is Linux. — [quickemu script](https://github.com/quickemu-project/quickemu/blob/master/quickemu)
- **[first-hand reports]** Prior hypervisor UIs are poor with NVDA: VirtualBox 6.0.0 VM list/menus gave no NVDA feedback (#9202); "Severe Accessibility Issues in VirtualBox on Windows" (elements announced as "Unknown", unusable shutdown dialog); VirtualBox ticket 20581 (inaccessible "close VM" dialog); a 2015 VirtualBox crash with NVDA attributed to Qt accessibility (#4795). — [NVDA #9202](https://github.com/nvaccess/nvda/issues/9202); [VirtualBox GitHub issue #7](https://github.com/VirtualBox/virtualbox/issues/7); [VirtualBox ticket 20581](https://www.virtualbox.org/ticket/20581); [NVDA #4795](https://github.com/nvaccess/nvda/issues/4795)

### Inferences
- Recommended stack: `-display none -qmp <named pipe or 127.0.0.1 TCP> -vnc 127.0.0.1:N` (VNC only as the pixel source for an optional on-screen view for low-vision users/sighted helpers; QMP `screendump` alone is enough for OCR). Input goes over QMP `input-send-event`, not through VNC, so orchord controls exact modifier semantics.
- The framebuffer view is optional for blind users but valuable for low-vision users (zoom, high contrast inversion can be applied host-side) — and makes sighted assistance possible when wanted.
- What orchord's console window should expose to NVDA: (1) a meaningful window title: "<VM name> - macOS console - keyboard captured|released"; (2) a focusable read-only status line (state: running/paused/shut down, boot phase, last event); (3) a read-only log/edit control containing OpenCore serial log and manager events; (4) spoken + earcon announcements for capture/release, VM state changes (`SHUTDOWN`/`RESET`/`STOP`/`GUEST_PANICKED` events from QMP), "guest audio detected / silent"; (5) a menu bar reachable when released, with every guest action (Start VoiceOver in guest, Read screen, Send Command-Tab, Boot to Recovery, Power off, Reset) as ordinary accessible menu items so that nothing *requires* capture mode.
- A window that hosts a pure bitmap should have a sensible accessible name/role (e.g. "Guest screen, press Enter to capture keyboard") rather than being an unnamed pane.

### Gaps
- **No accessibility evaluation of QEMU's GTK or SDL UI on Windows with NVDA/JAWS was found** (menu reachability, focus behaviour). The claim "GTK UI on Windows is poorly accessible" is plausible but unverified by any source I could find; it needs a 10-minute hands-on test.
- Whether common Windows QEMU binaries (MSYS2 `mingw-w64-qemu`, Stefan Weil's installers) are built with `dbus_display`, SPICE or VNC-audio support was not verified; the D-Bus display also needs a D-Bus daemon or p2p socket on Windows, and its registration API is documented in Unix-FD terms. Treat `-display dbus` on Windows as unproven.
- No wxPython VNC widget was identified; an embedded view would be custom (RFB client + bitmap blit) or periodic `screendump`.
- Hyper-V/VMware consoles: no research on embedding (VMConnect, RDP ActiveX, VMware VIX/`vmrun` capture) beyond the Hyper-V thumbnail API noted in section 7.

## 7. Reading the guest screen when VoiceOver is not yet talking (OCR, AI description, serial text)

### Takeaway
A built-in "read the VM screen" command is feasible with stock parts: QMP `screendump` to PNG, then Windows' offline OCR API, then text into an accessible control and/or speech. This is the essential safety net for every silent phase (picker, Recovery loading, installer progress, kernel panics), and there is prior art for both halves.

### Cited Findings
- **[docs]** NVDA: "To recognize the text in the current navigator object using Windows OCR, press NVDA+r"; results open in a browse-mode-like document (Enter/Space activates the text under the cursor, Escape dismisses, NVDA+F5 refreshes); "Periodically refresh recognized content" re-recognises every 1.5 seconds when enabled (off by default); language comes from installed Windows OCR languages; Screen Curtain prevents OCR. — [NVDA User Guide](https://download.nvaccess.org/documentation/userGuide.html)
- **[docs]** `Windows.Media.Ocr.OcrEngine`: `RecognizeAsync(SoftwareBitmap)` returns an `OcrResult`; engines are created with `TryCreateFromUserProfileLanguages()` or `TryCreateFromLanguage(Language)`; `AvailableRecognizerLanguages` lists installed languages. Recognition is local/offline and depends on installed Windows language packs. — [Microsoft: OcrEngine class](https://learn.microsoft.com/uwp/api/windows.media.ocr.ocrengine); [Microsoft: OcrEngine.RecognizeAsync](https://learn.microsoft.com/en-us/uwp/api/windows.media.ocr.ocrengine.recognizeasync)
- **[example code]** A Python module using `winsdk.windows.media.ocr` (`OcrEngine.try_create_from_language`, `recognize_async`, `SoftwareBitmap.create_copy_from_buffer`) exists publicly, showing the API is callable from Python. — [comicocr ocr_windows.py](https://huggingface.co/datasets/dlxjj/comicocr/blob/main/modules/ocr/ocr_windows.py)
- **[source code]** QMP `screendump` with `format: png` (since QEMU 7.1). — [QEMU qapi/ui.json](https://github.com/qemu/qemu/blob/master/qapi/ui.json)
- **[prior art, proposal]** TheWorkBench issue #150 (Kelly Ford's project): "Hyper-V Manage: take a picture of a VM's screen and view it so a screen reader can describe it" — motivated by VMs stuck "at a setup screen, a BitLocker prompt, a hung sign-in or a blue screen" where "there's no Remote Desktop and no screen reader inside it"; proposes feeding the image to JAWS Picture Smart, NVDA add-ons such as AI Content Describer, or Be My AI; uses Hyper-V's thumbnail API, which returns the VM screen from the host without a guest agent. An open proposal, not shipped. — [TheWorkBench issue #150](https://github.com/kellylford/TheWorkBench/issues/150)
- **[prior art, shipped]** Lume's `lume sip` flow "uses a temporary VNC session in Recovery and reads the prompts with OCR" to automate SIP changes in macOS Recovery (Apple Silicon VMs) — i.e. OCR-driven automation of macOS Recovery screens works in production. — [Lume: how unattended setup works](https://cua.ai/docs/concepts/how-lume-unattended-setup-works)
- **[first-hand guide, 2025-09]** Blind users already rely on OCR for inaccessible VM setup screens in the reverse direction (VOCR on macOS for Parallels setup). — [AppleVis: Windows 11 on Mac using Parallels guide](https://applevis.com/comment/194603)
- **[docs]** OpenCore serial logging via `Misc -> Debug -> Target` bit 3; Docker-OSX uses `-serial`/telnet monitor headlessly. — [OpenCore Configuration.tex](https://github.com/acidanthera/OpenCorePkg/blob/master/Docs/Configuration.tex); [Docker-OSX README](https://github.com/sickcodes/Docker-OSX/blob/master/README.md)

### Inferences
- NVDA+R cannot be the mechanism if the console process is in NVDA sleep mode (all NVDA commands are disabled there), and it depends on NVDA specifically. Orchord should implement its own "Read guest screen" (hotkey recognised by orchord's capture hook even in captured mode, plus a menu item): `screendump` -> PNG -> `OcrEngine` -> text placed in a read-only multi-line control and spoken. Line/word bounding boxes from `OcrResult` allow a later "click this text" feature via `input-send-event` absolute coordinates — useful for the few installer steps keyboard navigation cannot reach.
- A **screen-change watcher** (periodic `screendump`, hash/diff, OCR on change, announce only new text; plus "progress still moving / screen unchanged for N minutes") turns silent waits — the 20-60 minute install phases and reboots — into spoken status, addressing the "no reliable way to tell when an install finishes" complaint blind users make about VM installers.
- Phase detection by OCR keywords ("macOS Utilities"/"Recovery", "Reinstall macOS", "Disk Utility", "Select your Country or Region", "panic") gives orchord a state machine it can speak from, independent of guest audio. Language must be pinned (guest UI language = an installed Windows OCR language).
- Verbose boot (`-v`) puts kernel text on the framebuffer in a console font that OCR handles well; that plus OpenCore's serial log covers boot diagnostics. An optional cloud/LLM image description should be opt-in (privacy; needs network) — OCR is the offline default.
- Tesseract is a possible fallback for machines lacking the right Windows OCR language pack; not researched in depth.

### Gaps
- No measurements of Windows OCR accuracy on macOS installer/Recovery/Setup Assistant screens (thin San Francisco font on translucent/blurred backgrounds, Tahoe's "Liquid Glass" styling) or on low-resolution vmware-svga output.
- `OcrEngine` maximum image dimension and Python binding specifics (`winsdk` vs `winrt-*` packages, maintenance status) not verified.
- Whether macOS kernel/installer logs can be mirrored to a QEMU serial port on current macOS (boot-arg support) — not verified; the installer log (`/var/log/install.log`) is otherwise only reachable inside the guest.
- NVDA's AI image description capabilities/add-ons (e.g. "AI Content Describer") were not examined; not found in the portions of the 2026.2 user guide retrieved.

## 8. Remote access after install and unattended-setup options

### Takeaway
Once macOS is installed, SSH is the fully accessible channel (plain text in a Windows terminal) and standard VNC/Screen Sharing carries no VoiceOver speech; but there is no supported way to preseed a macOS install so that SSH is on at first boot. The proven unattended technique (Lume) patches the guest's Data volume offline from a macOS host, which a Windows host cannot do natively.

### Cited Findings
- **[source code]** OSX-KVM forwards a host port to guest SSH out of the box (`-netdev user,...,hostfwd` 2222 -> 22). — [OSX-KVM OpenCore-Boot.sh](https://github.com/kholia/OSX-KVM/blob/master/OpenCore-Boot.sh)
- **[docs]** OSX-KVM: "Enable `Remote Login` (aka SSH) via `System Preferences -> Sharing`" — a manual, in-guest GUI step. — [OSX-KVM notes.md](https://github.com/kholia/OSX-KVM/blob/master/notes.md)
- **[docs]** Docker-OSX: "Enable SSH in network sharing inside the guest first"; SSH on localhost:50922; a prebuilt `:auto` image exists for command-line-only use with `-e USERNAME/-e PASSWORD` and `OSX_COMMANDS`; "Naked-Auto (use your own .img and SSH in)". — [Docker-OSX README](https://github.com/sickcodes/Docker-OSX/blob/master/README.md)
- **[docs]** Apple Platform Deployment: on macOS 14 or later, removing `/private/var/db/.AppleSetupDone` no longer relaunches Setup Assistant if a local user already exists; the supported way to skip Setup Assistant panes is a device-management (MDM) service. — [Apple Platform Deployment guide](https://support.apple.com/guide/deployment/depdeff4a547)
- **[docs]** Mac admin lore: creating `/var/db/.AppleSetupDone` suppresses Setup Assistant in an image, but a user account must then be created by script. — [krypted.com](https://krypted.com/?p=4053); [MacAdmins docs: Setup Assistant](https://macadminsdoc.readthedocs.io/en/latest/General/macOS_Installation/Setup_Assistant.html)
- **[docs]** Lume `create --unattended` (Apple Silicon, Virtualization.framework): installs macOS, boots once, stops the VM, mounts the guest Data volume on the host and writes the account, SSH, auto-login and no-sleep settings as files, then boots and waits for SSH — explicitly to avoid depending on Setup Assistant layout. Tahoe is the verified preset; Sequoia may still show the Accessibility pane. — [Lume: how unattended setup works](https://cua.ai/docs/concepts/how-lume-unattended-setup-works); [Lume unattended setup guide](https://cua.ai/docs/lume/guide/fundamentals/unattended-setup)
- **[docs]** QEMU's VNC server has an `audiodev` option (audio over VNC for clients that support QEMU's extension); SPICE has its own audio backend. — [QEMU invocation docs](https://www.qemu.org/docs/master/system/invocation.html)

### Inferences
- A realistic "minimum sight" flow for orchord: (1) boot installer with guest audio; (2) user (or an orchord-scripted key sequence verified by OCR) runs the install with VoiceOver; (3) in Setup Assistant the user creates the account with VoiceOver; (4) orchord offers "Enable SSH in guest" which types the required Terminal command sequence via QMP (`sudo systemsetup -setremotelogin on` / `launchctl` — exact commands and Full Disk Access requirements on current macOS must be verified); from then on the manager can configure everything else over SSH (install VoodooHDA where needed, set VoiceOver to start at login, disable sleep, install a network-audio sender for Hyper-V).
- Offline preseeding from Windows is blocked by APFS: Windows has no native APFS write support, so Lume's approach would need a helper (e.g. doing the patch from the Recovery Terminal inside the guest via scripted keystrokes, or a small Linux helper VM with an APFS driver — both speculative).
- Scripted Setup Assistant via QMP keystrokes + OCR checkpoints is possible in principle (Lume previously drove Setup Assistant through VNC, and still drives Recovery that way), but Setup Assistant changes every release, so it should be a per-version, best-effort convenience with a manual VoiceOver path always available.
- macOS Screen Sharing gives pixels only; VoiceOver speech stays on the guest's audio device. So even post-install, speech must come from emulated audio (QEMU/VMware) or a network audio path (Hyper-V).

### Gaps
- No verified, current (macOS 13-26) command sequence for enabling Remote Login headlessly from Recovery or first boot; no verified file-level recipe (which plist/launchd overrides) for offline enabling.
- No source on `startosinstall`-based unattended installs inside OpenCore VMs (it needs a full installer app and a running macOS/Recovery to start from).
- Whether macOS Screen Sharing / Apple Remote Desktop can forward audio in any mode was not researched; treated as "no" by default.
- Whether VoiceOver can be pre-enabled for the login window/Setup Assistant by writing a preference from Recovery was not found.

## 9. Performance of VoiceOver in an unaccelerated or weakly accelerated VM

### Takeaway
There are no measurements or even anecdotes of VoiceOver responsiveness inside a QEMU macOS guest on Windows. All that exists is the general finding that emulated macOS audio is choppy under load and sensitive to CPU contention, plus one open bug showing macOS not booting under WHPX at all.

### Cited Findings
- **[docs]** OSX-KVM: "The emulated sound output can be choppy, and distorted." — [OSX-KVM notes.md](https://github.com/kholia/OSX-KVM/blob/master/notes.md)
- **[docs]** VoodooHDA in QEMU: "you will most likely hear stuttering or distortion"; "more for convenience than entertainment". — [Dastux VoodooHDA-QEMU-KVM.md](https://github.com/MobCode100/Dastux/blob/main/VoodooHDA-QEMU-KVM.md)
- **[first-hand report]** Unraid users: macOS VMs "are very finicky about audio and sharing cores, even with the host" (crackling thread). — [Unraid: No/Crackling Audio in VM](https://forums.unraid.net/topic/77010-nocrackling-audio-in-1036-vm/)
- **[first-hand report]** Even Apple's own Virtualization framework showed ~0.3 s guest audio delay (macOS guest on M1, 2021). — [Apple Developer Forums thread 693897](https://developer.apple.com/forums/thread/693897)
- **[first-hand report]** macOS 13.7.8 fails in early kernel boot under `-accel whpx` (AMD host, dev QEMU 11.0.50), unresolved. — [QEMU issue #4385](https://gitlab.com/qemu-project/qemu/-/work_items/4385)
- **[first-hand report, 2021]** AudioDxe hung under TCG (no acceleration) with `ich9-intel-hda`. — [acidanthera/bugtracker #740](https://github.com/acidanthera/bugtracker/issues/740)
- **[docs]** Tunables that exist: `-audiodev` `timer-period` (default 10000 µs), `out.buffer-length`, `dsound` `latency` (default 10000 µs), `sdl` `out.buffer-count`. — [QEMU invocation docs](https://www.qemu.org/docs/master/system/invocation.html)
- **[docs]** macOS guests have no GPU acceleration under QEMU (vmware-svga framebuffer, a few MB VRAM) and Hyper-V's synthetic framebuffer has 8 MB with no acceleration, so all window-server compositing is CPU work that competes with speech synthesis. — [OSX-Hyper-V README](https://github.com/Qonfused/OSX-Hyper-V); [quickemu script](https://github.com/quickemu-project/quickemu/blob/master/quickemu)
- **[docs]** OSX-Hyper-V ships an `optimize-vm.sh` that disables Spotlight indexing, reduces disk I/O and turns off system animations — the kind of guest-side tuning that also helps VoiceOver. — [OSX-Hyper-V README](https://github.com/Qonfused/OSX-Hyper-V)

### Inferences
- With TCG (no acceleration) on a 15 W i7-1355U, a modern macOS desktop with VoiceOver is unlikely to be usable; if WHPX cannot boot macOS, QEMU on Windows is effectively not a backend and VMware Workstation (its own hypervisor, or WHP mode) becomes the only audio-capable option. This dependency should be resolved before any audio/keyboard work.
- Tuning advice to test (not sourced as effective for macOS guests): larger audio buffers trade latency for fewer dropouts — for speech, 40-80 ms of extra latency is tolerable but dropouts are not; raise QEMU process priority (Above Normal/High) and keep the host on AC power/"Best performance"; give the guest 4 vCPUs and leave host cores free; on this hybrid CPU (2 P-cores + 8 E-cores) restrict QEMU's affinity to P-core threads if stutter is observed (Windows supports process-level affinity even without per-vCPU pinning; general knowledge, uncited); in the guest, enable Reduce Motion/Reduce Transparency, disable Spotlight indexing during setup, and prefer a compact VoiceOver voice.
- 16 GB host RAM: OSX-Hyper-V says Big Sur+ needs 6-8 GB to boot the installer; an 8 GB guest leaves little for Windows + NVDA, so memory pressure/swap on the host is a likely source of speech stutter.

### Gaps
- No data on VoiceOver latency, speech stutter or usability in any x86 macOS VM (KVM, WHPX, VMware, TCG). No blind-user reports.
- No confirmation that macOS boots under WHPX on Intel 13th-gen hosts with any QEMU version; no known-good WHPX CPU model/flag set for macOS.
- No evidence on audio behaviour after guest sleep/wake; safest default is to disable guest sleep.

## 10. Existing accessible VM front ends and prior art by/for blind users

### Takeaway
I found no accessible VM manager built for blind users and no "talking installer" image for macOS. Prior art is limited to guides for the reverse scenario (Windows guests on Macs), scattered bug reports about inaccessible hypervisor UIs, one open proposal to OCR/describe Hyper-V VM screens, and reusable components (NVDA sleep-mode app modules, NVDA Controller Client, QEMU's Linux-only braille device).

### Cited Findings
- **[guide, 2016-12]** AudioGames.net "The ultimate guide for gaming on a Mac using a virtual machine": Windows 10 in VMware Fusion 8.5.3 driven by VoiceOver on the host and Narrator/NVDA in the guest; warns the installer may break or keyboard focus may be lost, leaving no speech. — [AudioGames forum topic 20646](https://forum.audiogames.net/viewtopic.php?id=20646)

- **[proposal]** TheWorkBench #150: accessible viewer/description of a Hyper-V VM's screen from the host. — [TheWorkBench issue #150](https://github.com/kellylford/TheWorkBench/issues/150)
- **[bug reports]** VirtualBox accessibility problems on Windows with screen readers. — [VirtualBox GitHub issue #7](https://github.com/VirtualBox/virtualbox/issues/7); [VirtualBox ticket 20581](https://www.virtualbox.org/ticket/20581); [NVDA #9202](https://github.com/nvaccess/nvda/issues/9202)

- **[component]** quickemu `--braille` / QEMU braille USB device: SDL-only and Linux-host-only. — [quickemu script](https://github.com/quickemu-project/quickemu/blob/master/quickemu)
- **[patent]** US11500659B2, "System and method for virtual machine and virtual desktop accessibility" (VMware/Intuit) — existence noted; not read. — [Google Patents US11500659B2](https://patents.google.com/patent/US11500659)
- **[web-dev testing guides]** Sighted developers' guides for running NVDA in VirtualBox/VMware on Macs note that screen-reader shortcuts need remapping and that Caps Lock as modifier "doesn't seem to work with VirtualBox". — [De Voorhoede: Testing accessibility on Windows with VirtualBox](https://www.voorhoede.nl/en/blog/testing-accessibility-on-windows-with-virtualbox/)

### Inferences
- Orchord would be the first tool of its kind; there is no existing accessible front end to borrow UX conventions from, so conventions should follow what blind users already know: VirtualBox's single "host key" (Right Ctrl), NVDA's sleep-mode model for self-voicing apps, and the "talking installer" expectation from Windows (where Narrator is one keystroke away at setup) — orchord's equivalent is a one-key "Start VoiceOver in guest" plus an OCR "where am I" command.
- The recurring complaint in every blind-user VM report is not "the screen reader is bad" but "silence is ambiguous". The manager's status/announcement layer (section 6/7) addresses the real pain point and is independent of whether guest audio works.

### Gaps
- NVDA Add-on Store: I did not find (and could not exhaustively search) add-ons specific to VMware/VirtualBox/Hyper-V consoles; absence is not established.
- No audio-game-community VM tooling for macOS guests found; no pre-made "talking" macOS VM images (which would in any case raise licensing problems).
- Mastodon/Fediverse blind-tech posts and r/Blind were not directly searchable with the available tools; relevant first-hand reports may exist there.
- AppleVis and AudioGames.net blocked direct fetching, so thread contents beyond search summaries are unread.

## Consolidated defect list (every point at which sight is currently required)

### Takeaway
Ordered by how early they block an unassisted install; items 1-3 are unproven prerequisites, the rest are things orchord must build.

### Cited Findings
- (1) Accelerated boot on Windows is unproven: macOS fails under WHPX in the one public report. — [QEMU issue #4385](https://gitlab.com/qemu-project/qemu/-/work_items/4385)
- (2) Guest audio during Recovery/installer is undocumented for every device; virtio-sound is claimed kext-free for macOS 12+ but tested only post-install on 14/15/26. — [quickemu issue #1642](https://github.com/quickemu-project/quickemu/issues/1642)
- (3) macOS 10.13-11.x need VoodooHDA; OpenCore injection is reported unreliable from 11.3; manual install needs SIP changes in Recovery and a GUI approval click. — [quickemu commit eb54549](https://github.com/quickemu-project/quickemu/commit/eb54549353edaa14432b006e99e77b1089eddbbc); [Dastux VoodooHDA-QEMU-KVM.md](https://github.com/MobCode100/Dastux/blob/main/VoodooHDA-QEMU-KVM.md)
- (4) OpenCore picker: speech depends on AudioDxe, which is choppy on QEMU; default configs in the wild show the picker (`ShowPicker=true`). — [acidanthera/bugtracker #740](https://github.com/acidanthera/bugtracker/issues/740); [OSX-KVM config.plist](https://github.com/kholia/OSX-KVM/blob/master/OpenCore/config.plist)
- (5) Knowing when Recovery has loaded (reports say wait 30 s to 2 min before Command-F5) and when install phases/reboots finish. — [AppleVis: Recovery mode and VoiceOver](https://www.applevis.com/forum/accessibility-advocacy/recovery-mode-voiceover); [AppleVis: Problem with VMware Fusion 12 and VoiceOver](https://applevis.com/comment/118478)
- (6) Host screen reader intercepting Insert/Caps Lock and its commands unless asleep for the console; NVDA core has no VM app modules. — [NVDA User Guide](https://download.nvaccess.org/documentation/userGuide.html); [NVDA source/appModules](https://github.com/nvaccess/nvda/tree/master/source/appModules)
- (7) QEMU GTK's fixed Ctrl+Alt hotkeys collide with the Control+Option chord; SDL needs `grab-mod=rctrl`. — [QEMU ui/gtk.c](https://github.com/qemu/qemu/blob/master/ui/gtk.c); [QEMU invocation docs](https://www.qemu.org/docs/master/system/invocation.html)
- (8) Win+L and Ctrl+Alt+Del can never be forwarded, so Windows-key-as-Command is incomplete. — [Microsoft: KeyboardDeliveryInterceptor](https://learn.microsoft.com/en-us/uwp/api/windows.ui.input.keyboarddeliveryinterceptor)
- (9) Hyper-V: no audio device at all; workarounds need a configured guest. — [OSX-Hyper-V issue #9](https://github.com/Qonfused/OSX-Hyper-V/issues/9)
- (10) VMware + Tahoe: audio requires OpenShell `CsrUtil` and a kext package approval after install. — [Techy Druid: macOS Tahoe on VMware](https://techydruid.com/macos-tahoe-vmware/)
- (11) Enabling SSH/Remote Login is a manual in-guest step; no supported preseed; `.AppleSetupDone` tricks changed in macOS 14. — [OSX-KVM notes.md](https://github.com/kholia/OSX-KVM/blob/master/notes.md); [Apple Platform Deployment guide](https://support.apple.com/guide/deployment/depdeff4a547)

### Inferences
- Minimum experiments to run before design is frozen (each is under an hour once a guest boots): (a) does any macOS boot under WHPX on the i7-1355U, else fall back to VMware; (b) boot a macOS 14/15/26 BaseSystem with `virtio-sound-pci` + `-audiodev wav` and inject Command-F5 via QMP after the Recovery UI appears — is the WAV non-silent?; (c) same for 10.15 with `intel-hda` + OpenCore-injected VoodooHDA; (d) VMware Workstation + OC4VM: is there sound in Recovery on Sonoma/Sequoia without any kext?; (e) NVDA sleep-mode app module + own low-level hook: do Insert, Caps Lock, Win+F5 and Ctrl+Alt chords all reach the guest; does Controller Client still speak?; (f) Windows OCR accuracy on Recovery, installer and Setup Assistant screenshots.
- Things orchord must build regardless of experiment outcomes: per-phase OpenCore config generation that never requires picker interaction; headless QEMU + QMP console with its own key capture, Right-Ctrl release, configurable Command mapping, earcons and spoken state; "Start VoiceOver in guest" and "Read guest screen (OCR)" commands; a screen-change/phase watcher; an optional bundled NVDA add-on; serial-log capture pane; a guest-audio self-test.

### Gaps
- Everything in the experiment list above is, as of October 2026, unanswered by any public source I could find.
