# Boot-level and kernel-level factors in macOS guest processor load (OpenCore, kexts, boot-args, SMBIOS)

Scope: Intel macOS 11, 12, 14, 15 guests under QEMU 11.1 with WHPX on Windows. Method notes that apply to every section:

- XNU line numbers refer to the `main` branch of apple-oss-distributions/xnu as fetched on 2026-10-12 unless a tag is named. The four release tags compared were `xnu-7195.141.2` (macOS 11), `xnu-8020.140.41` (12), `xnu-10063.141.1` (14) and `xnu-11417.140.69` (15).
- "[first-party]" marks a measurement taken from this project's own serial logs under `lab\vm-*\`. Those logs have no timestamps, so rates are bounds, not exact figures.
- "[KVM]" marks advice that comes from Linux/KVM experience and has not been shown to transfer to WHPX.
- Nothing in these notes was tested by changing the VM and measuring. Every recommendation is derived from source code, documentation, or existing logs.

## 1. Serial and verbose logging: cost of `serial=3`, `-v`, `debug=0x100`, `keepsyms=1`, and the minimal boot-args that keep panic detection

### Takeaway
`serial=3` is the one boot-arg with a continuous cost: bit 0x2 starts a kernel thread that polls the UART every 16 ms for the whole uptime (62.5 wake-ups and port reads per second) and signals user space to load a serial console job; bit 0x1 alone (`serial=1`) is what puts the panic text on the serial port. `debug=0x100` and `keepsyms=1` cost nothing at run time, and kprintf is already off, so the recommended line is `keepsyms=1 debug=0x100 serial=1` (with `-v` optional).

### Cited Findings

Meaning of each `serial=` bit (XNU):
- `SERIALMODE_OUTPUT 0x01` ("Is output supported ?"), `SERIALMODE_INPUT 0x02` ("Is input supported ?"), `SERIALMODE_SYNCDRAIN 0x04` ("Force synchronous output ?"), `SERIALMODE_BASE_TTY 0x08` ("Load Base/Recovery/FVUnlock TTY"), `SERIALMODE_NO_IOLOG 0x10` ("Prevent IOLogs writing to serial"), `SERIALMODE_DKLOG 0x20` ("Allow DriverKit os_log/IOLogs writing to serial"), `SERIALMODE_ON_DEMAND 0x40` ("Start logging on to a serial only once data has been received on this serial. Requires SERIALMODE_INPUT set"), `SERIALMODE_NO_EXCLAVE 0x80` (only under `CONFIG_EXCLAVES`). — [xnu main, osfmk/console/serial_protos.h L52-L76](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/console/serial_protos.h#L52-L76)
- Availability by release: macOS 11 defines only 0x1, 0x2, 0x4, 0x8. — [xnu-7195.141.2 serial_protos.h L49-L52](https://github.com/apple-oss-distributions/xnu/blob/xnu-7195.141.2/osfmk/console/serial_protos.h#L49-L52). macOS 12 adds 0x10 (`SERIALMODE_NO_IOLOG`). — [xnu-8020.140.41 serial_protos.h L50-L54](https://github.com/apple-oss-distributions/xnu/blob/xnu-8020.140.41/osfmk/console/serial_protos.h#L50-L54). macOS 14 adds 0x20 and 0x40. — [xnu-10063.141.1 serial_protos.h L52-L71](https://github.com/apple-oss-distributions/xnu/blob/xnu-10063.141.1/osfmk/console/serial_protos.h#L52-L71). macOS 15 adds 0x80. — [xnu-11417.140.69 serial_protos.h L52-L75](https://github.com/apple-oss-distributions/xnu/blob/xnu-11417.140.69/osfmk/console/serial_protos.h#L52-L75)
- So `serial=3` = OUTPUT + INPUT. It does not mean "console + kprintf"; kprintf is controlled by `debug=`, not `serial=` (see below).

What bit 0x1 (output) does:
- At early boot the kernel parses `serial`; if `SERIALMODE_OUTPUT` is set it sets `serial_console_enabled = true`, calls `switch_to_serial_console()` and sets `disableConsoleOutput = FALSE`. — [xnu main, osfmk/i386/i386_init.c L923-L944](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/i386/i386_init.c#L923-L944)
- Every kernel `printf()` goes to `os_log` and also to the console through `console_printbuf_putc`. — [xnu main, osfmk/kern/printf.c L870-L893](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/kern/printf.c#L870-L893). `IOLog` does the same unless `disable_iolog_serial_output` is set (bit 0x10). — [xnu main, iokit/Kernel/IOLib.cpp L1500-L1517](https://github.com/apple-oss-distributions/xnu/blob/main/iokit/Kernel/IOLib.cpp#L1500-L1517)
- The console is one device at a time: `cons_ops[]` holds a serial entry and a video entry and `cons_ops_index` selects one. — [xnu main, osfmk/console/serial_console.c L121-L137](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/console/serial_console.c#L121-L137)
- When the graphical interface takes the screen, the kernel turns console output off only if the console is the screen: "only disable console output if it goes to the graphics console ... if (console_is_serial() == FALSE) disableConsoleOutput = TRUE". With a serial console the output therefore continues for the whole uptime. — [xnu main, osfmk/console/video_console.c L350-L356](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/console/video_console.c#L350-L356)
- With console output disabled, `console_write()` returns at its first statement. — [xnu main, osfmk/console/serial_console.c L524-L528](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/console/serial_console.c#L524-L528)

How a character reaches the UART:
- The x86 serial driver describes itself as "Polled-mode 16x50 UART driver"; the legacy port is COM1 at 0x3f8. — [xnu main, pexpert/i386/pe_serial.c L30-L75](https://github.com/apple-oss-distributions/xnu/blob/main/pexpert/i386/pe_serial.c#L30-L75)
- `legacy_uart_init()` writes `IER = 0` ("Disable hardware interrupts"), so transmission is never interrupt-driven. — [pe_serial.c L164-L192](https://github.com/apple-oss-distributions/xnu/blob/main/pexpert/i386/pe_serial.c#L164-L192)
- `uart_putc()` is `while (!gPESF->tr0()) ; gPESF->td0(c);` where `tr0` is `inb(LSR) & THRE` and `td0` is `outb(THR, c)`. That is at least one port read and one port write per byte. — [pe_serial.c L152-L161](https://github.com/apple-oss-distributions/xnu/blob/main/pexpert/i386/pe_serial.c#L152-L161) and [L626-L634](https://github.com/apple-oss-distributions/xnu/blob/main/pexpert/i386/pe_serial.c#L626-L634)
- Each `\n` is sent as `\r\n`. — [serial_console.c L252-L265](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/console/serial_console.c#L252-L265)
- In normal running, `console_write()` copies into a ring buffer and then the calling thread itself drains it ("Do good faith flush if preemption is not disabled") in 16-byte chunks (`MAX_FLUSH_SIZE_LOCK_HELD 16`) under a mutex. There is no background transmit interrupt; the thread that printed pays for the port accesses. — [serial_console.c L105-L111](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/console/serial_console.c#L105-L111), [L394-L480](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/console/serial_console.c#L394-L480), [L524-L592](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/console/serial_console.c#L524-L592)
- Bit 0x4 (`SYNCDRAIN`, also boot-arg `drain_uart_sync`) forces fully synchronous output; the kernel's own warning reads "printf()s/IOLogs will impact kernel performance. You are advised to avoid using 'drain_uart_sync' boot-arg." — [i386_init.c L927-L937](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/i386/i386_init.c#L927-L937)

What bit 0x2 (input) does:
- `serial_keyboard_init()` returns immediately unless `SERIALMODE_INPUT` is set; otherwise it starts a kernel thread at `MAXPRI_KERNEL`. The thread reads the port until empty, then sleeps with `clock_interval_to_deadline(16, 1000000, &next)` (16 ms) and repeats forever. — [xnu main, osfmk/console/serial_general.c L52-L97](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/console/serial_general.c#L52-L97)
- The 16 ms interval is identical in all four release tags (line 92 of the same file in each). — [xnu-7195.141.2 serial_general.c L92](https://github.com/apple-oss-distributions/xnu/blob/xnu-7195.141.2/osfmk/console/serial_general.c#L92), [xnu-11417.140.69 serial_general.c L92](https://github.com/apple-oss-distributions/xnu/blob/xnu-11417.140.69/osfmk/console/serial_general.c#L92)
- It is started from `kernel_bootstrap_thread` after `bsd_init()`. — [xnu main, osfmk/kern/startup.c L911](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/kern/startup.c#L911)
- Each poll calls `uart_getc()`, which reads the line status register (one `inb`) and returns -1 when no data is waiting. — [pe_serial.c L195-L207](https://github.com/apple-oss-distributions/xnu/blob/main/pexpert/i386/pe_serial.c#L195-L207) and [L637-L646](https://github.com/apple-oss-distributions/xnu/blob/main/pexpert/i386/pe_serial.c#L637-L646)
- When both 0x1 and 0x2 are set, the sysctl `hw.serialdebugmode` reports 1: "hw.serialdebugmode = 1 will load the serial console job in the multi-user session; = 2 will load the serial console job in the base system as well" (2 needs bit 0x8). — [xnu main, bsd/kern/kern_mib.c L864-L883](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/kern_mib.c#L864-L883)
- The polled input also feeds an NMI trigger: a 32-character magic string received on serial drops the kernel into the debugger. — [serial_console.c L141-L145](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/console/serial_console.c#L141-L145) and [L637-L661](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/console/serial_console.c#L637-L661)

kprintf and the `debug=` bits:
- On RELEASE kernels `disable_serial_output` starts as `true`; `PE_init_kprintf()` enables kprintf-to-serial only `if (debug_boot_arg & DB_KPRT)`. — [xnu main, pexpert/i386/pe_kprintf.c L58-L96](https://github.com/apple-oss-distributions/xnu/blob/main/pexpert/i386/pe_kprintf.c#L58-L96). Same test in macOS 11. — [xnu-7195.141.2 pe_kprintf.c L62-L92](https://github.com/apple-oss-distributions/xnu/blob/xnu-7195.141.2/pexpert/i386/pe_kprintf.c#L62-L92)
- When enabled, `kprintf()` disables interrupts, takes a spin lock and writes each character straight to the UART (`_doprnt(fmt, &listp, PE_kputc, 16)`). — [pe_kprintf.c L123-L175](https://github.com/apple-oss-distributions/xnu/blob/main/pexpert/i386/pe_kprintf.c#L123-L175)
- `debug=` bit definitions: `DB_HALT 0x1`, `DB_PRT 0x2` ("enable always-on panic print to serial"), `DB_NMI 0x4`, `DB_KPRT 0x8`, `DB_KDB 0x10`, `DB_ARP 0x40`, `DB_KDP_BP_DIS 0x80`, `//#define DB_LOG_PI_SCRN 0x100 -- obsolete`, `DB_KDP_GETC_ENA 0x200`, `DB_KERN_DUMP_ON_PANIC 0x400`, `DB_KERN_DUMP_ON_NMI 0x800`, `DB_DBG_POST_CORE 0x1000`, `DB_PANICLOG_DUMP 0x2000`, `DB_REBOOT_POST_CORE 0x4000`, `DB_NMI_BTN_ENA 0x8000`, `DB_DISABLE_LOCAL_CORE 0x20000`, `DB_DISABLE_GZIP_CORE 0x40000`, `DB_DISABLE_CROSS_PANIC 0x80000`, `DB_REBOOT_ALWAYS 0x100000`, `DB_DISABLE_STACKSHOT_TO_DISK 0x200000`. — [xnu main, osfmk/kern/debug.h L580-L610](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/kern/debug.h#L580-L610)
- `0x100` is commented out as obsolete in all four releases; `DB_PRT 0x2` is commented out as obsolete in macOS 11, 12 and 14 and defined again in macOS 15. — [xnu-7195.141.2 debug.h L470-L477](https://github.com/apple-oss-distributions/xnu/blob/xnu-7195.141.2/osfmk/kern/debug.h#L470-L477), [xnu-10063.141.1 debug.h L520-L527](https://github.com/apple-oss-distributions/xnu/blob/xnu-10063.141.1/osfmk/kern/debug.h#L520-L527), [xnu-11417.140.69 debug.h L574-L581](https://github.com/apple-oss-distributions/xnu/blob/xnu-11417.140.69/osfmk/kern/debug.h#L574-L581)
- On x86 any non-zero `debug=` value sets `panicDebugging = TRUE` (the `#else` branch of an arm64 test), which is the only effect `0x100` has: the machine stays stopped at a panic. — [xnu main, osfmk/kern/debug.c L434-L446](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/kern/debug.c#L434-L446)
- VirtualSMC's FAQ lists `keepsyms=1`, `-v`, `debug=0x100`, `io=0xff` as "generic boot-args" for debugging, which is where this combination comes from. — [VirtualSMC Docs/FAQ.md](https://github.com/acidanthera/VirtualSMC/blob/master/Docs/FAQ.md)

`keepsyms`, `msgbuf`, `-x`:
- `keepsyms` is read inside the panic handler and only gates symbol-name printing in the backtrace ("Display address-symbol translation only if the "keepsyms" boot-arg is suppplied, since we unload LINKEDIT otherwise"). — [xnu main, osfmk/i386/AT386/model_dep.c L1455](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/i386/AT386/model_dep.c#L1455) and [L1532-L1539](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/i386/AT386/model_dep.c#L1532-L1539)
- OpenCore's `DisableLinkeditJettison` (true in this project's config) "lets Lilu.kext, and possibly other kexts, function in macOS Big Sur at their best performance levels without requiring the keepsyms=1 boot argument". — [OpenCore 1.0.8 Docs/Configuration.tex, Kernel Quirks, DisableLinkeditJettison](https://github.com/acidanthera/OpenCorePkg/blob/1.0.8/Docs/Configuration.tex#L2767)
- `msgbuf=n` only resizes the in-memory kernel message buffer read by `dmesg`. — [xnu main, bsd/kern/subr_log.c L837-L845](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/subr_log.c#L837-L845)
- `-x` is safe boot. — [xnu main, bsd/kern/bsd_init.c L1221](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/bsd_init.c#L1221)

How the panic text reaches the serial port:
- The panic header is `paniclog_append_noflush("panic(cpu %u caller 0x%lx): ", ...)`. — [xnu main, osfmk/kern/debug.c L1456](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/kern/debug.c#L1456)
- That path writes each character with `console_write_unbuffered(c)` (the current console) and additionally `if (!console_is_serial() && !disable_serial_output && (PE_kputc != NULL)) PE_kputc(c);`. So the panic text reaches COM1 if either the serial console is active (`serial` bit 0x1) or kprintf is enabled (`debug` bit 0x8). — [xnu main, osfmk/kern/printf.c L916-L938](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/kern/printf.c#L916-L938)

[first-party] What this project's logs show (boot-args `-v keepsyms=1 debug=0x100 serial=3`):
- None of the logs contain "kprintf initialized" or "Serial mode specified", which are kprintf lines, confirming kprintf is off with `debug=0x100`. — project logs `lab\vm-bigsur\serial.log`, `lab\vm-monterey\serial.log`, `lab\vm-sequoia\serial.log`
- Bytes written before the first logged-in console line: Big Sur 41,835; Monterey 48,787; Sequoia 120,105. Bytes after it (includes log-in burst and shutdown messages): Big Sur 30,561 (410 lines); Monterey 29,913 (343 lines); Sequoia 67,884 (700 lines). — same logs
- Whole-session size and duration (QEMU start to last serial write): Big Sur 72,396 bytes in 18 min 22 s; Monterey 78,700 bytes in 5 min 19 s; Sequoia 187,989 bytes in 4 min 52 s. — same logs plus `qemu.pid` timestamps
- Installer stage-1 logs: Big Sur 115,101 bytes; Monterey 1,699,906 bytes; Sequoia 3,385,874 bytes (23,351 lines). — `lab\vm-*\serial-stage1.log`
- Most frequent post-login lines are AppleKeyStore, ACM, APFS (`tx_flush`, `set_dir_stats`), AHCI and launchd messages. No `login:` prompt appears in any log. — same logs

### Inferences
- Each serial byte costs at least two I/O-port accesses (one `inb` on the status register, one `outb` on the data register), and each is a VM exit that WHPX must hand to QEMU in user space. Lower bound for one Sequoia boot to the desktop: 120,105 bytes, so more than 240,000 exits; for the Sequoia installer stage 1: more than 6.7 million exits. This is a boot-time and install-time cost.
- Steady-state output is small. The longest session (Big Sur, 18 minutes) wrote at most about 28 bytes per second after log-in, which is on the order of 60 port accesses per second.
- The poll thread from bit 0x2 is of the same order by itself: 62.5 timer wake-ups plus 62.5 port reads every second, on every boot, for the whole uptime, and it stops one virtual processor from staying halted for longer than 16 ms. Changing `serial=3` to `serial=1` removes it and still sends all console text and the panic text to the log. The host never writes to the guest's serial port (it is a `-serial file:` log), so input serves no purpose.
- `serial=1` also makes `hw.serialdebugmode` report 0, so user space is no longer told to load a serial console job. Whether that job actually runs today is unknown (no login prompt is visible in the logs).
- On macOS 12 and later, `serial=0x11` would additionally keep driver `IOLog` lines off the serial port while kernel `printf` lines and the panic text still appear. This trades diagnostic detail for fewer exits; on macOS 11 the bit is undefined and ignored.
- Do not add `debug=0x8`: it enables kprintf, whose path runs with interrupts disabled and writes each byte directly to the port, the most expensive form of serial output.
- Removing `serial=` entirely would make console output stop at the moment the graphical interface starts (zero run-time cost), but then the panic text would not reach the log unless kprintf were enabled, which is worse. `serial=1` is the cheapest setting that keeps panic detection.
- `debug=0x100` and `keepsyms=1` have no run-time processor cost. `debug=0x100` only keeps the machine stopped at a panic (all virtual processors spin until the host stops the VM, which the host already does on seeing "panic(cpu").
- `-v` does not appear in any of the XNU files examined; the verbose/graphics choice arrives from the boot loader as a video mode. With a serial console selected the kernel text goes to serial, not the screen, so `-v` adds launchd's verbose lines to the log but no screen drawing. Dropping `-v` would save a little serial traffic at boot and log-in only.

### Gaps
- The cost of one I/O-port exit under WHPX on this host was not measured and no reliable published figure was found, so exit counts could not be converted to seconds.
- Where `DB_PRT` (0x2, "always-on panic print to serial", macOS 15) is implemented was not found in the x86 files examined; whether `debug=0x102` alone would print panics to COM1 on Sequoia without `serial=` is unverified.
- `SERIALMODE_ON_DEMAND` (0x40) is not referenced in `i386_init.c`; it may be Apple silicon only.
- Whether Apple's `Apple16X50Serial` driver, which the logs show attaching to COM1 ("Apple16X50ACPI1: Identified Serial Port on ACPI Device=COM1"), adds any polling of its own was not investigated.
- The precise lines-per-second rate in steady state needs a timestamped capture; the logs give only upper bounds.

## 2. Power management and idle: DummyPowerManagement, HLT versus MWAIT, XCPM, `plugin-type`, CPUFriend

### Takeaway
With no processor power-management kext registered, XNU's idle loop is a plain `sti; hlt`, so an idle virtual Mac should halt its virtual processors rather than spin; nothing found shows a macOS-specific idle spin under QEMU. `DummyPowerManagement` only matters on macOS 11 and 12 (the kext it disables is gone afterwards); on Monterey and Sequoia the logs show `X86PlatformPlugin` loading and failing to read C-states and P-states, and the only documented VM-specific alternative is the `plugin-type = 2` "VMPlatformPlugin" route used by MacHyperVSupport, which is untested under QEMU.

### Cited Findings
- `machine_idle()`: if a power-management kext has registered (`pmInitDone && pmDispatch != NULL && pmDispatch->MachineIdle != NULL`) its idle routine is called; otherwise the comment reads "If no power management, re-enable interrupts and halt. This will keep the CPU from spinning through the scheduler and will allow at least some minimal power savings" and the code is `pal_hlt(); pal_cli();`. — [xnu main, osfmk/i386/pmCPU.c L103-L176](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/i386/pmCPU.c#L103-L176)
- The idle dispatch table is installed only when a kext calls `pmKextRegister()`. — [pmCPU.c L964-L1010](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/i386/pmCPU.c#L964-L1010)
- Before halting, the idle path checks pending timers and skips the halt if a soft deadline has passed and the hard deadline is within `idle_entry_timer_processing_hdeadline_threshold = 5000000` (5 ms). — [pmCPU.c L96](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/i386/pmCPU.c#L96) and [L116-L124](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/i386/pmCPU.c#L116-L124)
- `DummyPowerManagement`: "Disables AppleIntelCpuPowerManagement." Requirement "10.4-12". "This option is a preferred alternative to NullCpuPowerManagement.kext for CPUs without native power management driver in macOS." — [OpenCore 1.0.8 Configuration.tex, Kernel Emulate, DummyPowerManagement](https://github.com/acidanthera/OpenCorePkg/blob/1.0.8/Docs/Configuration.tex#L2386)
- The Emulate section notes: "It may also be the case that the CPU model is supported but there is no power management supported (e.g. virtual machines). In this case, MinKernel and MaxKernel can be set to restrict CPU virtualisation and dummy power management patches to the particular macOS kernel version." — [OpenCore 1.0.8 Configuration.tex L2330-L2332](https://github.com/acidanthera/OpenCorePkg/blob/1.0.8/Docs/Configuration.tex#L2330-L2332)
- `AppleXcpmCfgLock` only stops XNU writing MSR 0xE2 ("commonly causing early kernel panic, when it is locked from writing (XCPM power management)") and "should be avoided whenever possible"; `AppleXcpmForceBoost` writes 0xFF00 to MSR 0x199 and is "strongly discouraged on all systems but those explicitly dedicated to scientific or media calculations". Both are false in this project. — [OpenCore 1.0.8 Configuration.tex L2653-L2692](https://github.com/acidanthera/OpenCorePkg/blob/1.0.8/Docs/Configuration.tex#L2653-L2692)
- MacHyperVSupport (macOS on Hyper-V) ships an ACPI table for this: "SSDT-HV-PLUG: Ensures VMPlatformPlugin loads on Big Sur and above, avoids freezes with the default PlatformPlugin." — [MacHyperVSupport README](https://github.com/acidanthera/MacHyperVSupport/blob/master/README.md)
- That table adds a `_DSM` on the first processor object returning `"plugin-type", 0x02`, guarded by `_OSI ("Darwin")`; its header says "Hyper-V CPU plugin-type SSDT to enable VMPlatformPlugin on Big Sur and newer". — [OpenCorePkg Docs/AcpiSamples/Source/SSDT-HV-PLUG.dsl](https://github.com/acidanthera/OpenCorePkg/blob/master/Docs/AcpiSamples/Source/SSDT-HV-PLUG.dsl)
- The ordinary XCPM table returns `"plugin-type", One` ("XCPM power management compatibility table with Darwin method"). — [OpenCorePkg Docs/AcpiSamples/Source/SSDT-PLUG.dsl](https://github.com/acidanthera/OpenCorePkg/blob/master/Docs/AcpiSamples/Source/SSDT-PLUG.dsl)
- MacHyperVSupport also says: "DummyPowerManagement and CPU spoofing may be required depending on the host CPU for older versions of macOS." — [MacHyperVSupport README](https://github.com/acidanthera/MacHyperVSupport/blob/master/README.md)
- CPUFriend is "A Lilu plug-in for dynamic power management data injection" and "most likely not required when the CPU is natively supported by XNU". — [CPUFriend README](https://github.com/acidanthera/CPUFriend/blob/master/README.md)
- Dortania: processor type (mobile, desktop, server) determines whether Apple's XCPM can be used and which profiles apply, issues that are "mostly resolved with CPUFriend". — [Dortania, Choosing the right SMBIOS](https://dortania.github.io/OpenCore-Install-Guide/extras/smbios-support.html)
- XNU changes several timeouts when the CPUID hypervisor bit is set: `virtualized = ((cpuid_features() & CPUID_FEATURE_VMM) != 0)`; a `vti` boot-arg (default 6) inflates lock and other timeouts. — [xnu main, osfmk/i386/machine_routines.c L1045-L1051](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/i386/machine_routines.c#L1045-L1051)
- [KVM] Docker-OSX's default boot-args are `-v keepsyms=1 tlbto_us=0 vti=9`. — [Docker-OSX custom/config-nopicker-custom.plist](https://github.com/sickcodes/Docker-OSX/blob/master/custom/config-nopicker-custom.plist). `tlbto_us` is the TLB-flush timeout boot-arg. — [machine_routines.c L992](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/i386/machine_routines.c#L992)
- [KVM/HVF] The only "high CPU" remark found in OSX-KVM is a comment above a commented-out line that hides the hypervisor (`hypervisor=off,vmx=on,kvm=off`): "This causes high cpu usage on the *host* side". — [OSX-KVM OpenCore-Boot-macOS.sh](https://github.com/kholia/OSX-KVM/blob/master/OpenCore-Boot-macOS.sh)
- OSX-KVM's shipped config sets `DummyPowerManagement = true` and `ProvideCurrentCpuInfo = true`, the same as this project. — [OSX-KVM OpenCore/config.plist](https://github.com/kholia/OSX-KVM/blob/master/OpenCore/config.plist)
- [first-party] Big Sur (Penryn model) logs "ACPI_SMC_PlatformPlugin::start - waitForService(resourceMatching(AppleIntelCPUPowerManagement) timed out". — `lab\vm-bigsur\serial.log` line 424
- [first-party] Monterey (Penryn) and Sequoia (Skylake-Client) load `X86PlatformPlugin`, which logs "getCPUCStates - C000 ACST and _CST evaluations failed!", "_CST did not return a package", and on Sequoia "getCPUPStates - C003 APSS and _PSS evaluations failed!" and "publishACPIStates - Failed to get CPU P States!". — `lab\vm-monterey\serial.log` lines 467-468, `lab\vm-sequoia\serial.log` lines 1165-1170
- Web searches for a documented macOS-guest idle spin under QEMU found none; the nearest results were a FreeBSD guest on Apple silicon and a Parallels Ventura guest. — [QEMU issue 959](https://gitlab.com/qemu-project/qemu/-/issues/959)

### Inferences
- On Big Sur the platform plugin waits for `AppleIntelCPUPowerManagement`, which `DummyPowerManagement` has disabled, and times out. No kext registers an idle routine, so idle is `hlt`. This is the cheapest possible idle for a virtual machine; under WHPX a halted virtual processor is blocked until the next interrupt (how WHPX delivers that is covered by the hypervisor-side notes, not here).
- On Monterey and Sequoia it is not known from open source whether Apple's built-in XCPM registers its own idle routine in a VM. If it does, it would choose between `mwait` and `hlt` from CPUID; a guest that is not offered MONITOR/MWAIT can only halt. This needs checking in the guest (see Gaps).
- `DummyPowerManagement` is inert on macOS 14 and 15 (requirement 10.4 to 12). Leaving it on is harmless.
- The `plugin-type = 2` table is the only acidanthera-documented way to select a VM-specific platform plugin, and it exists because the default plugin caused freezes under Hyper-V. Under QEMU the processor objects are named differently (the logs show `C000` to `C003`), so the Hyper-V table cannot be used unchanged; an equivalent would need to target QEMU's processor objects. This is an experiment with unknown benefit and a real risk of a boot failure, not a recommendation.
- CPUFriend, `plugin-type = 1` and the XCPM quirks address frequency scaling on real processors. A guest cannot change the host processor's frequency or sleep state, so none of them can lower host load.
- Hiding the hypervisor from the guest is the wrong direction: XNU uses the hypervisor bit to relax timeouts and pick x2APIC mode (section 3), and the one OSX-KVM comment on high host load is attached to a hypervisor-hidden configuration.

### Gaps
- No source describes what `VMPlatformPlugin` does or how it differs from `X86PlatformPlugin`; it is closed source and two searches returned nothing beyond the MacHyperVSupport sentence.
- Whether XCPM is active in these guests is unverified. Checks to run inside the guest: `sysctl machdep.xcpm.mode`, `sysctl machdep.cpu.features | grep -i mon` (MONITOR), and `kextstat | grep -i -e X86Platform -e ACPI_SMC`.
- Whether an idle guest's virtual processors really block on the host was not measured here. The decisive test is host-side: per-thread processor time of the QEMU process with the guest idle at the desktop.
- No OSX-KVM, UTM, Docker-OSX or quickemu issue describing idle spin with a fix was found; this is absence of evidence from four searches, not proof.

## 3. Timer behaviour: tick, LAPIC versus TSC-deadline versus HPET, coalescing, TSC/FSB frequencies under Hyper-V

### Takeaway
XNU on x86 is tickless (one-shot deadlines on the local APIC), with a 10 ms scheduling quantum only while threads run and timer coalescing on by default; there is no boot-arg that usefully lowers wake-ups. The points that differ in this VM are the timer mode (TSC-deadline on the Skylake-Client model, plain LAPIC one-shot on Penryn), automatic x2APIC mode under a hypervisor, and where the TSC and bus frequencies come from, which under Hyper-V is exactly what `ProvideCurrentCpuInfo` fixes.

### Cited Findings
- Timer source selection: if CPUID reports the TSC-deadline feature, `TSC_deadline_timer` defaults to 1 (boot-arg `TSC_deadline_timer=0` turns it off) and the kernel prints "TSC Deadline Timer supported and enabled"; otherwise it uses the LAPIC timer in one-shot mode (`lapic_config_timer(TRUE, one_shot, divide_by_1)`). — [xnu main, osfmk/i386/rtclock_native.c L72-L79](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/i386/rtclock_native.c#L72-L79) and [L166-L199](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/i386/rtclock_native.c#L166-L199)
- Arming cost: LAPIC mode reads and writes `LVT_TIMER` then writes `TIMER_INITIAL_COUNT` (three register accesses); TSC-deadline mode is a single `wrmsr64(MSR_IA32_TSC_DEADLINE, deadline)`. — [xnu main, osfmk/i386/lapic_native.c L790-L802](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/i386/lapic_native.c#L790-L802)
- The LAPIC count is derived from the bus frequency (`tmrCvt(count, busFCvtn2t)`), the TSC-deadline from the TSC frequency (`tmrCvt(delta, tscFCvtn2t)`). — [rtclock_native.c L81-L96](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/i386/rtclock_native.c#L81-L96) and [L113-L132](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/i386/rtclock_native.c#L113-L132)
- x2APIC: "If no x2apic boot-arg was set and if we're running under a VMM, autoenable x2APIC mode", applied when CPUID offers x2APIC and `cpuid_vmm_family != CPUID_VMM_FAMILY_NONE`; boot-arg `x2apic=0/1` overrides. — [lapic_native.c L393-L406](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/i386/lapic_native.c#L393-L406)
- Hypervisor families XNU recognises by CPUID vendor string: VMware, Parallels, bhyve/xhyve, HVF, KVM; anything else with the hypervisor bit is `CPUID_VMM_FAMILY_UNKNOWN` (still not NONE). — [xnu main, osfmk/i386/cpuid.c L1440-L1462](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/i386/cpuid.c#L1440-L1462)
- TSC and bus frequency under a hypervisor: XNU reads CPUID leaf 0x40000010 ("VMM generic leaves") only `if (max_vmm_leaf >= 0x40000010)`, taking EAX as TSC kHz and EBX as bus kHz. — [cpuid.c L1463-L1469](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/i386/cpuid.c#L1463-L1469)
- `tsc_init()` uses those values and returns early only when both are non-zero; otherwise it falls through to per-family code. — [xnu main, osfmk/i386/tsc.c L143-L165](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/i386/tsc.c#L143-L165)
- Per-family fallbacks: Skylake-family computes `tscFreq = refFreq * N / M` from CPUID leaf 0x15 and the firmware's `ARTFrequency`; Penryn reads `IA32_PERF_STS` and the firmware's `FSBFrequency`. — [tsc.c L167-L215](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/i386/tsc.c#L167-L215) and [L246-L254](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/i386/tsc.c#L246-L254)
- `ProvideCurrentCpuInfo`: "For Microsoft Hyper-V it provides the correct TSC and FSB values to the kernel, as well as disables CPU topology validation (10.8+). For KVM and other hypervisors it provides precomputed MSR 35h values solving kernel panic with -cpu host." — [OpenCore 1.0.8 Configuration.tex, Kernel Quirks, ProvideCurrentCpuInfo](https://github.com/acidanthera/OpenCorePkg/blob/1.0.8/Docs/Configuration.tex#L2902-L2922)
- MacHyperVSupport lists the quirk as "required for proper TSC/FSB values and CPU topology values". — [MacHyperVSupport README](https://github.com/acidanthera/MacHyperVSupport/blob/master/README.md)
- OpenCore changelog entries on the same topic: "Added ProvideCurrentCpuInfo quirk to provide correct TSC/FSB for Hyper-V virtual machines", "Added PIIX4 ACPI PM timer detection for TSC calculations on Hyper-V Gen1 VMs", "Fixed Hyper-V frequency detection compatibility". — [OpenCorePkg Changelog.md](https://github.com/acidanthera/OpenCorePkg/blob/master/Changelog.md)
- [KVM] OSX-KVM and quickemu pass `+invtsc,vmware-cpuid-freq=on`; quickemu's comments say "vmware-cpuid-freq=on enables VMware TSC frequency reporting for macOS timing" and "A CPU with invtsc is required for macOS to boot". — [OSX-KVM OpenCore-Boot.sh](https://github.com/kholia/OSX-KVM/blob/master/OpenCore-Boot.sh), [quickemu script](https://github.com/quickemu-project/quickemu/blob/master/quickemu)
- This project's CPU flags are `vendor=GenuineIntel,+invtsc,+ssse3,+sse4.2,+popcnt,+avx,+aes,+xsave,+xsaveopt`, without `vmware-cpuid-freq`. — project source `crates\orchord-core\src\qemu.rs` line 20
- Under a hypervisor XNU disables its cross-processor TSC synchronisation margin ("TSC sync margin disabled") unless `TSC_sync_margin` is given. — [xnu main, osfmk/i386/mp.c L233-L238](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/i386/mp.c#L233-L238)
- Scheduler quantum: `DEFAULT_PREEMPTION_RATE 100` per second (boot-arg `preempt`), background `400` (boot-arg `bg_preempt`); the kernel prints "standard timeslicing quantum is %d us". — [xnu main, osfmk/kern/sched_prim.c L146-L150](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/kern/sched_prim.c#L146-L150) and [L499-L503](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/kern/sched_prim.c#L499-L503)
- Timer coalescing is a run-time setting, `kern.timer.coalescing_enabled`, with per-class tuning sysctls (`kern.timer_coalesce_*`). — [xnu main, bsd/kern/kern_sysctl.c L3262-L3264](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/kern_sysctl.c#L3262-L3264) and [L5167-L5280](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/kern_sysctl.c#L5167-L5280)
- Long-term timer queue: boot-arg `longterm=<ms>` sets the threshold above which timers are parked on a separate queue (0 disables); the default is `TIMER_LONGTERM_THRESHOLD`, defined as 1 second in one build configuration and disabled in the other, and disabled in server performance mode. — [xnu main, osfmk/kern/timer_call.c L86-L91](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/kern/timer_call.c#L86-L91) and [L1568-L1590](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/kern/timer_call.c#L1568-L1590)
- quickemu warns that unstable TSC "can cause macOS Ventura+ to freeze on AMD Ryzen mobile CPUs" and checks the host clock source before starting. — [quickemu script, check_macos_tsc_stability](https://github.com/quickemu-project/quickemu/blob/master/quickemu)
- [first-party] All three guests print "standard timeslicing quantum is 10000 us". Only Sequoia (Skylake-Client model) prints "TSC Deadline Timer supported and enabled"; the Big Sur and Monterey logs (Penryn model) do not, so they use the LAPIC one-shot timer. All three list an ACPI HPET table. None prints a "Longterm timer threshold" line. — `lab\vm-bigsur\serial.log`, `lab\vm-monterey\serial.log`, `lab\vm-sequoia\serial.log`
- [first-party] This project already found that with `ProvideCurrentCpuInfo` off the kernel dies immediately under WHPX. — project report `reports\Accessible macOS VM on Windows.md` line 20

### Inferences
- XNU has no periodic tick to turn down. Wake-ups come from real deadlines (timers set by the system's own services, the 10 ms quantum while something is running, and device interrupts). Lowering wake-ups is therefore a matter of running fewer services in the guest, which is outside boot-level configuration, plus removing the 62.5 Hz serial poll from section 1.
- Raising the quantum with `preempt=` would not reduce idle load (an idle processor has no quantum timer) and would hurt responsiveness under load. Not recommended.
- Under WHPX on Windows 11 the guest sees Hyper-V CPUID leaves, whose maximum leaf is below 0x40000010, so XNU cannot take frequencies from the hypervisor and falls back to processor-family code that expects real-hardware MSRs or CPUID leaf 0x15. `ProvideCurrentCpuInfo` replaces that with correct values. This explains the project's observation that the kernel dies without it, and it means the quirk is doing time-keeping work on every boot, not only fixing topology.
- On Penryn guests every timer deadline is scaled by the bus frequency. If that value were wrong, timers would fire early or late (extra wake-ups or sluggishness) and the clock would drift. A cheap sanity check is to compare guest and host elapsed time over ten minutes.
- TSC-deadline mode needs one register write per re-arm against three for LAPIC mode, so the Skylake-Client guests should cause fewer timer-related exits per deadline than Penryn guests if the hypervisor handles the APIC itself. Whether WHPX handles these writes without leaving to QEMU is a hypervisor-side question (not answered here).
- x2APIC mode is switched on automatically when the guest is offered it, because any hypervisor vendor string XNU does not recognise still counts as a hypervisor. Whether the Penryn and Skylake-Client models are offered x2APIC under WHPX was not checked.
- `vmware-cpuid-freq=on` is KVM-specific in the reference projects; this project does not pass it and relies on `ProvideCurrentCpuInfo` instead, which is the documented route for Hyper-V.

### Gaps
- XNU's use of the HPET on these releases was not analysed (the file `osfmk/i386/hpet.c` exists and maps the HPET, but its callers were not traced). MacHyperVSupport disables `_hpet_init` only for kernels up to 9.5.99.
- No measurement of guest clock drift or of timer exits per second exists for this setup.
- Whether the guest actually runs in x2APIC mode can be read from a kprintf line ("x2APIC supported and will be enabled"), which is not in the logs because kprintf is off.

## 4. Kext choices: VirtualSMC, WhateverGreen, Lilu, VoodooPS2, display drivers for VMware SVGA, input polling

### Takeaway
None of the four loaded kexts polls; VirtualSMC is a net saving because it answers Apple's SMC driver inside the kernel and disables QEMU's emulated SMC device, whose every access would be an I/O-port exit. No usable accelerated or 2D-optimised driver for the VMware SVGA device exists for macOS 11 to 15, and the pointer device is already the low-cost choice (tablet on xHCI).

### Cited Findings
- VirtualSMC implements the SMC's port interface as methods (`ioWrite8`, `ioRead8` dispatching to `pmio->writeData`, `writeCommand`, `readData`, `readStatus`, `readResult`), so Apple's SMC driver calls code instead of touching hardware ports. — [VirtualSMC kern_vsmc.cpp L582-L610](https://github.com/acidanthera/VirtualSMC/blob/master/VirtualSMC/kern_vsmc.cpp#L582-L610)
- At start it looks for other SMC devices; unless `-vsmccomp` is given, an existing device with no driver attached is renamed ("disabling another smc device ... setProperty("name", "OFF0001")"). — [kern_vsmc.cpp L364-L395](https://github.com/acidanthera/VirtualSMC/blob/master/VirtualSMC/kern_vsmc.cpp#L364-L395)
- Boot-args: "`-vsmccomp` to prefer existing hardware SMC implementation if found", "`vsmcgen=X` to force exposing X-gen SMC device (1 and 2 are supported)", "`-vsmcoff` to switch off all the Lilu enhancements". — [VirtualSMC README](https://github.com/acidanthera/VirtualSMC/blob/master/README.md)
- The only timer in the core kext is a watchdog event source that fires on request (restart or shutdown jobs). — [kern_vsmc.cpp L66-L74](https://github.com/acidanthera/VirtualSMC/blob/master/VirtualSMC/kern_vsmc.cpp#L66-L74) and [L177-L216](https://github.com/acidanthera/VirtualSMC/blob/master/VirtualSMC/kern_vsmc.cpp#L177-L216)
- Unless the first-generation device is forced, VirtualSMC routes the kernel's trap handler (`KernelPatcher::RouteRequest req("_kernel_trap", ...)`); its wrapper acts only on page faults whose address lies in the emulated SMC memory window. — [VirtualSMC kern_prov.cpp L139-L157](https://github.com/acidanthera/VirtualSMC/blob/master/VirtualSMC/kern_prov.cpp#L139-L157) and [L221-L227](https://github.com/acidanthera/VirtualSMC/blob/master/VirtualSMC/kern_prov.cpp#L221-L227)
- This project starts QEMU with `-device isa-applesmc,osk=...` and also loads VirtualSMC. — project source `crates\orchord-core\src\qemu.rs` line 59; project config `third_party\opencore\EFI\OC\config.plist`
- WhateverGreen's documented features concern Intel, AMD and NVIDIA graphics, connectors, backlight and HDMI audio; `-wegoff` disables it. Its changelog has no entry mentioning QEMU, VMware, KVM, Hyper-V or virtual machines. — [WhateverGreen README](https://github.com/acidanthera/WhateverGreen/blob/master/README.md), [WhateverGreen Changelog](https://github.com/acidanthera/WhateverGreen/blob/master/Changelog.md)
- Lilu boot-args: "`-liluoff` to disable Lilu", "`-liluuseroff` to disable Lilu user patcher (for e.g. dyld_shared_cache manipulations)", "`-liluslow` to enable legacy user patcher". Lilu enforces the slow mode in the installer and Recovery. — [Lilu README](https://github.com/acidanthera/Lilu/blob/master/README.md), [Lilu kern_start.cpp L281-L311](https://github.com/acidanthera/Lilu/blob/master/Lilu/Sources/kern_start.cpp#L281-L311)
- Lilu's changelog: "Added QEMU/KVM vendor compatibility to device detection logic" (1.3.9) and "Added support for VMware device scanning" (1.3.3). — [Lilu Changelog](https://github.com/acidanthera/Lilu/blob/master/Changelog.md)
- OSX-KVM's shipped config enables the same four kexts as this project (Lilu, VirtualSMC, WhateverGreen, VoodooPS2Controller with the keyboard plug-in) plus AppleMCEReporterDisabler, USBToolBox and UTBMap. — [OSX-KVM OpenCore/config.plist](https://github.com/kholia/OSX-KVM/blob/master/OpenCore/config.plist)
- VMsvga2: "A display driver for Mac OS 10.5+ running as a VMware guest OS"; status inactive, "no longer under development"; last update 18 January 2016; current download targets 10.6 to 10.8; user reviews report problems on 10.9 and 10.10; the page recommends VMware's own `VMwareGfx.kext`. — [SourceForge vmsvga2](https://sourceforge.net/projects/vmsvga2/)
- Forks: `QiuMike/VMsvga2ForQEMU` ("the VMware svga graphic card OSX driver for QEMU") was modified for macOS Catalina, tested with QEMU 6.0 on OSX-KVM, needs the kext installed and signed or signature checks relaxed, last pushed November 2022. — [VMsvga2ForQEMU README](https://github.com/QiuMike/VMsvga2ForQEMU/blob/master/README.md). `PureDarwin/VMQemuVGA` ("Allows to set different screen resolutions in VMware") was last pushed July 2015. — [PureDarwin/VMQemuVGA](https://github.com/PureDarwin/VMQemuVGA). `FMX/VMSvga2ForHighSierra` was last pushed June 2018. — [FMX/VMSvga2ForHighSierra](https://github.com/FMX/VMSvga2ForHighSierra)

- [KVM] quickemu chooses `vmware-svga` for macOS with the comment "macOS has native VMware display driver support; aligns with OSX-KVM"; OSX-KVM's notes say "Switching to vmware-svga device seems to have "fixed"" a Ventura resolution problem. — [quickemu script](https://github.com/quickemu-project/quickemu/blob/master/quickemu), [OSX-KVM notes.md](https://github.com/kholia/OSX-KVM/blob/master/notes.md)
- A QEMU developer found in 2019 that macOS Mojave ships drivers for QEMU's standard VGA and Cirrus VGA, and a virtio driver covering console/serial, block (legacy mode only) and 9p. — [kraxel.org, macOS as QEMU guest](https://www.kraxel.org/blog/2019/06/macos-qemu-guest/)
- [KVM, Linux host only] `qemux/qemu-macos` describes a custom Linux QEMU build with a paravirtual GPU ("Reims") that "uses the stock AppleParavirtGPU.kext already present in the guest"; it requires KVM, memfd-backed guest memory and a Vulkan 1.2 host driver. — [Docker Hub qemux/qemu-macos](https://hub.docker.com/r/qemux/qemu-macos)
- USB input: "the usb host adapter by design polls the usb devices"; UHCI, OHCI and EHCI force QEMU to emulate that polling, while xHCI's design is "radically different" and can be emulated with noticeably less overhead. Remote wake-up lets an idle device be suspended so polling stops, but operating systems often leave it off. — [kraxel.org, qemu and usb tablet cpu consumption](https://www.kraxel.org/blog/2014/03/qemu-and-usb-tablet-cpu-consumtion/)
- This project attaches `usb-tablet` to `qemu-xhci` and also creates an empty `usb-ehci` controller at a fixed PCI address; there is no USB keyboard (keyboard is PS/2 through VoodooPS2). — project source `crates\orchord-core\src\qemu.rs` lines 57-58, 92, 144-147
- [KVM] OSX-KVM's notes advise `-device usb-tablet` instead of `usb-mouse` "for better mouse" behaviour. — [OSX-KVM notes.md](https://github.com/kholia/OSX-KVM/blob/master/notes.md)
- A search-result summary of the QEMU "vmapple" patch series (2025) says the macOS xHCI driver tries to use event rings 1 and 2 even when only one pin-based interrupt exists, so events are handled only after a time-out, and that macOS provides no virtio HID drivers. This was read only as a search summary, not from the patch text. — [patchew, New vmapple machine type and xhci fixes](https://patchew.org/QEMU/20250112210056.16658-1-phil@philjordan.eu)

### Inferences
- Keep VirtualSMC. Without it, Apple's SMC driver would talk to QEMU's `isa-applesmc` through I/O ports, several accesses per key read, each one an exit to QEMU. With it, SMC reads are function calls. The cost is one extra comparison on each kernel-mode trap, which is negligible. Do not add `-vsmccomp`, which would hand SMC back to the emulated device.
- No VirtualSMC sensor plug-in (processor, battery, Super I/O) is loaded in this project, and none should be added: those are the parts that read hardware registers on a timer.
- WhateverGreen has nothing to patch when the only display device is VMware SVGA. Removing it would not reduce steady-state load in any measurable way, because Lilu plug-ins do their work when kexts load; it would shorten boot very slightly and remove one moving part. The reference projects keep it, so removal is optional and should be tested on each macOS version before shipping.
- Lilu itself cannot be removed while VirtualSMC is used with its full feature set. Its user-space patcher only acts when a plug-in registers a user patch; `-liluuseroff` is a possible experiment but no source shows a load benefit.
- VoodooPS2 keyboard input is interrupt driven by the PS/2 controller (no evidence of polling was found, but the source was not read; see Gaps).
- There is no display kext worth adding. VMsvga2 targets macOS 10.6 to 10.8, its forks stop at Catalina, all are unsigned kernel extensions that macOS 11 and later load only with security relaxed, and none offers Metal. On macOS 11 to 15 the desktop is drawn in software regardless, so display cost is governed by resolution and by guest settings such as reduced transparency and motion, not by a driver.
- The tablet on xHCI is already the efficient pointer arrangement. The empty EHCI controller is a candidate for removal (an idle controller with no devices should be cheap, but it is one more emulated device); the project comment about fixed PCI ordering means removing it must not shift the disk controller's address.
- If keyboard or pointer response ever feels delayed in bursts, the vmapple finding about xHCI event rings is the first thing to read in full; it applies to pin-based interrupts, and `qemu-xhci` normally uses message-signalled interrupts.

### Gaps
- VoodooPS2Controller's source was not read; "interrupt driven, no polling" is an expectation, not a verified fact.
- How often macOS reads SMC keys in the background on an iMac model with no sensors was not measured.
- No test exists of macOS 14 or 15 with the VMsvga2 forks; they are assumed not to work.
- Whether macOS suspends the idle root hub of the unused EHCI controller (and so stops QEMU's frame timer) is unknown.

## 5. SMBIOS model: effect of the Mac model on background behaviour, and what OSX-KVM, UTM and Docker-OSX use

### Takeaway
No source measures processor load by Mac model in a virtual machine. The models in use are iMac19,1 (OpenCore's sample, OSX-KVM, and this project) and iMacPro1,1 (Docker-OSX default); the documented difference is that every iMac model expects an Intel integrated GPU, while iMacPro1,1 and MacPro7,1 do not, which is an argument for iMacPro1,1 in a machine with no GPU at all, but its effect on load is unproven.

### Cited Findings
- This project's PlatformInfo is `Automatic = true`, `Generic.SystemProductName = iMac19,1`, `UpdateSMBIOSMode = Create`. — project config `third_party\opencore\EFI\OC\config.plist` lines 1233-1269
- OSX-KVM's config also uses `iMac19,1`. — [OSX-KVM OpenCore/config.plist](https://github.com/kholia/OSX-KVM/blob/master/OpenCore/config.plist)
- Docker-OSX templates the model (`{{DEVICE_MODEL}}`) and its examples use `DEVICE_MODEL="iMacPro1,1"`. — [Docker-OSX config-nopicker-custom.plist](https://github.com/sickcodes/Docker-OSX/blob/master/custom/config-nopicker-custom.plist), [Docker-OSX README](https://github.com/sickcodes/Docker-OSX/blob/master/README.md)
- Dortania: iMacPro1,1 and MacPro7,1 are "the only 2 SMBIOS that will allow for dGPU to handle all the workload", including tasks the integrated GPU would otherwise take; processors without an integrated GPU need care because "features like Quick Look and such will be broken if the SMBIOS expects an iGPU (ie. Every single iMac SMBIOS)". — [Dortania, Choosing the right SMBIOS](https://dortania.github.io/OpenCore-Install-Guide/extras/smbios-support.html)
- Supported ranges from the same page: iMac19,1 from 10.14.4, current; iMacPro1,1 from 10.13.2, current; MacPro7,1 from 10.15.0, current; MacPro6,1 from 10.9.1, last 12.7.6. — [Dortania, Choosing the right SMBIOS](https://dortania.github.io/OpenCore-Install-Guide/extras/smbios-support.html)
- WhateverGreen's DRM chart: "All kinds of software DRM decoders were removed from macOS 11+" and "Only IGPU-free Mac models allow for full DRM content access given a compatible AMD GPU video decoder". — [WhateverGreen Manual/FAQ.Chart.md L31-L34](https://github.com/acidanthera/WhateverGreen/blob/master/Manual/FAQ.Chart.md)
- MacPro7,1 brings memory and PCI configuration notifications that need the RestrictEvents kext to silence ("`pci` - prevent PCI and RAM configuration notifications on MacPro7,1 platforms"). — [RestrictEvents README](https://github.com/acidanthera/RestrictEvents/blob/master/README.md)
- OSX-KVM's notes mention the model only in passing, for App Store log-in trouble: "Also tweaking the smbios.plist file can help (?)". — [OSX-KVM notes.md](https://github.com/kholia/OSX-KVM/blob/master/notes.md)
- [first-party] With iMac19,1, the platform plug-in that loads differs by release and processor model: Big Sur on Penryn loads `ACPI_SMC_PlatformPlugin`; Monterey on Penryn and Sequoia on Skylake-Client load `X86PlatformPlugin`. — `lab\vm-bigsur\serial.log` line 424, `lab\vm-monterey\serial.log` line 467, `lab\vm-sequoia\serial.log` line 1165

### Inferences
- In this VM there is no GPU that macOS can use for video decoding or Metal under any model, so decoding is in software either way. The model can still change which services try and fail (for example the integrated-GPU paths an iMac model expects), but no source quantifies that.
- If a model change is tried, iMacPro1,1 is the candidate: it is current on macOS 11 to 15, expects no integrated GPU, is what Docker-OSX uses, and avoids MacPro7,1's notifications. MacPro6,1 is unsuitable because it ends at macOS 12. Laptop models should be avoided because they add battery and lid power paths.
- A model change is not free: it changes the hardware identity macOS sees (serial numbers, iCloud identity, software-update catalogue), so it should be done only on new VMs or with a re-test of installation and updates on every supported macOS version.
- Because the platform plug-in differs with release and processor model, any comparison of models must be made per macOS version.

### Gaps
- UTM's default Mac model for Intel macOS guests was not found in this pass.
- No measurement of idle or busy processor load comparing iMac19,1 with iMacPro1,1 in a VM was found anywhere; this needs a direct test (same VM, same macOS, ten minutes idle after boot, host-side processor time).
- The reason OpenCore's sample and OSX-KVM use iMac19,1 is not documented; it appears to be simply the sample default.
- Whether AirPlay, Sidecar or similar services behave differently by model in a VM was not established.

## 6. OpenCore quirks and NVRAM settings relevant to processor load

### Takeaway
No Booter, Kernel, UEFI or NVRAM setting in the current configuration imposes a continuous processor cost; the quirks in question are either correctness fixes (`ProvideCurrentCpuInfo`), inert here (`ForceSecureBootScheme` with secure boot disabled, `DummyPowerManagement` on macOS 14 and 15), or boot-time only (`SetApfsTrimTimeout`). The start-up TRIM pass takes about two seconds in the logs, so there is nothing to gain by disabling it.

### Cited Findings
- `SetApfsTrimTimeout` (failsafe -1, requirement 10.14): "All free space is trimmed (unmapped/deallocated) at macOS startup"; the driver has a 9.999999 second time-out; "the trim operation can be mostly disabled by setting a very low timeout value, while 0 entirely disables it"; "The failsafe value -1 indicates that this patch will not be applied"; "On macOS 12.0 and above, it is no longer possible to specify trim timeout. However, trim can be disabled by setting 0"; "Trim operations are only affected at booting phase when the startup volume is mounted ... will not affect normal macOS running." — [OpenCore 1.0.8 Configuration.tex, SetApfsTrimTimeout](https://github.com/acidanthera/OpenCorePkg/blob/1.0.8/Docs/Configuration.tex#L2925-L2974)
- This project leaves it at -1, and attaches the disk as `ide-hd` with `rotation_rate=1` on a qcow2 image opened with `discard=unmap`. — project config line 1002; project source `crates\orchord-core\src\qemu.rs` lines 72-73
- [first-party] Sequoia start-up TRIM of the main container: "disk2 20616166 blocks trimmed in 6160 extents (35 us/trim, 27873 trims/s)" and "disk2 scan took 1.910174 s". Small volumes report 449 to 620 trims per second for two extents each. — `lab\vm-sequoia\serial.log`
- `ForceSecureBootScheme` (requirement 11): "Force x86 scheme for IMG4 verification. Note: This option is required on virtual machines when using SecureBootModel different from x86legacy." — [OpenCore 1.0.8 Configuration.tex, ForceSecureBootScheme](https://github.com/acidanthera/OpenCorePkg/blob/1.0.8/Docs/Configuration.tex#L2841-L2848)
- This project sets `SecureBootModel = Disabled`. — project config line 1124
- `DisableLinkeditJettison` (requirement 11): "Disables __LINKEDIT jettison code. This option lets Lilu.kext, and possibly other kexts, function in macOS Big Sur at their best performance levels without requiring the keepsyms=1 boot argument." — [OpenCore 1.0.8 Configuration.tex, DisableLinkeditJettison](https://github.com/acidanthera/OpenCorePkg/blob/1.0.8/Docs/Configuration.tex#L2767-L2775)
- `PowerTimeoutKernelPanic` (requirement 10.15): "Disables kernel panic on setPowerState timeout ... Sometimes it may cause issues on misconfigured hardware, notably digital audio, which sometimes fails to wake up." False in this project. — [OpenCore 1.0.8 Configuration.tex, PowerTimeoutKernelPanic](https://github.com/acidanthera/OpenCorePkg/blob/1.0.8/Docs/Configuration.tex#L2889-L2899)
- `ProvideCurrentCpuInfo`: see section 3. — [OpenCore 1.0.8 Configuration.tex, ProvideCurrentCpuInfo](https://github.com/acidanthera/OpenCorePkg/blob/1.0.8/Docs/Configuration.tex#L2902-L2922)
- `csr-active-config`: this project and OSX-KVM use `AAAAAA==` (0, System Integrity Protection fully on); Docker-OSX uses `ZwAAAA==` (0x67). — project config lines 1168-1171; [OSX-KVM config.plist](https://github.com/kholia/OSX-KVM/blob/master/OpenCore/config.plist); [Docker-OSX config-nopicker-custom.plist](https://github.com/sickcodes/Docker-OSX/blob/master/custom/config-nopicker-custom.plist)
- OpenCore's own debug settings in this project are off (`AppleDebug`, `ApplePanic`, `SysReport` false, `Target` 0). — project config lines 1060-1075
- MacHyperVSupport's required quirks for macOS on Hyper-V are Booter `AvoidRuntimeDefrag` and `ProvideCustomSlide`, Kernel `ProvideCurrentCpuInfo`, and UEFI `DisableSecurityPolicy`; none is described as performance related. — [MacHyperVSupport README](https://github.com/acidanthera/MacHyperVSupport/blob/master/README.md)
- [first-party] The Sequoia log contains AHCI command time-outs and device recovery on two ports during a normal session: "[AHCI][DISK][00020040] CommandTimeout ... WatchdogTimeout ... AbortCommands ... InitiateDeviceRecovery ... Enabling device features", repeated for ports 2 and 4, plus "EnableDeviceFeatures failed because of a timeout, device has already been reset". — `lab\vm-sequoia\serial.log` lines 1530-1580

### Inferences
- `SetApfsTrimTimeout` should stay at -1. The start-up TRIM pass costs about two seconds on a 96 GB disk here, and it is what lets the qcow2 image give space back to the host. Setting 0 would save those two seconds per boot and make the disk image grow without bound.
- `ForceSecureBootScheme` does nothing while `SecureBootModel` is `Disabled`; it can stay or go without effect on load.
- With `DisableLinkeditJettison` on, `keepsyms=1` is not needed for Lilu; it remains useful only for readable panic backtraces, at a small memory cost and no processor cost.
- The System Integrity Protection value has no direct processor cost. It matters indirectly: switching off Apple's background services from inside the guest (the largest remaining lever for idle load, covered by the guest-side notes) generally needs protection relaxed, either through `csr-active-config` or from Recovery. Docker-OSX's 0x67 is an example of a relaxed value used for that kind of freedom.
- The AHCI time-outs are a responsiveness problem rather than a load problem: each one stalls disk input and output for the driver's time-out period and then resets the device. They appear on both the boot-loader disk (port 2) and the main disk (port 4), which suggests the cause is on the emulation or host side. This belongs with the storage findings but is recorded here because it came out of the same logs.

### Gaps
- No OpenCore Booter or UEFI quirk was found that documents an effect on run-time processor load; the Booter and UEFI sections were searched for virtual-machine notes only, not read line by line.
- The cause of the AHCI command time-outs was not investigated (candidates: host disk stalls, the virtual FAT boot disk, native command queueing in QEMU's AHCI under WHPX).
- Whether TRIM during normal running (as files are deleted) costs anything measurable on `ide-hd` under WHPX was not measured.

## 7. macOS Sonoma and Sequoia under hypervisors: VM detection, `kern.hv_vmm_present`, AppleVirtIO, anything exploitable

### Takeaway
The kernel reacts to the CPUID hypervisor bit in a handful of low-level ways (longer timeouts, automatic x2APIC, frequency from hypervisor leaves, no microcode updates) but nothing found shows it changing scheduling or switching services off to be lighter in a VM; `kern.hv_vmm_present` is consumed by user-space services such as software update and content caching. The exploitable item is Apple's built-in virtio support: the reference projects run macOS 11 and later on virtio block and network devices, which is the conventional way to cut emulation exits, but that evidence is from KVM.

### Cited Findings
- `kern.hv_vmm_present` is a read-only sysctl whose handler returns `IOGetVMMPresent()`. — [xnu-7195.141.2 bsd/kern/kern_sysctl.c L4652-L4668](https://github.com/apple-oss-distributions/xnu/blob/xnu-7195.141.2/bsd/kern/kern_sysctl.c#L4652-L4668), [xnu-8020.140.41 bsd/kern/kern_sysctl.c L4716-L4732](https://github.com/apple-oss-distributions/xnu/blob/xnu-8020.140.41/bsd/kern/kern_sysctl.c#L4716-L4732)
- An Apple engineer on the developer forums describes checking `kern.hv_vmm_present` as standard practice and reports it returning 1 under VMware Fusion, QEMU and Apple's Virtualization framework (read as a search-result summary). — [Apple Developer Forums thread 738564](https://developer.apple.com/forums/thread/738564)
- RestrictEvents options that exist because of this sysctl: "`asset` - allows Content Caching when `sysctl kern.hv_vmm_present` returns `1` on macOS 11.3 or newer" and "`sbvmm` - forces VMM SB model, allowing OTA updates for unsupported models on macOS 11.3 or newer". — [RestrictEvents README](https://github.com/acidanthera/RestrictEvents/blob/master/README.md)
- Kernel behaviour keyed on the CPUID hypervisor bit: timeouts inflated by `vti` (default 6). — [xnu main, osfmk/i386/machine_routines.c L1045-L1051](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/i386/machine_routines.c#L1045-L1051). x2APIC enabled automatically. — [lapic_native.c L393-L404](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/i386/lapic_native.c#L393-L404). TSC synchronisation margin disabled. — [mp.c L233-L238](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/i386/mp.c#L233-L238). TSC and bus frequency read from leaf 0x40000010 when offered. — [tsc.c L143-L165](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/i386/tsc.c#L143-L165). Microcode update refused ("Can't update microcode from within a VM"). — [xnu main, bsd/dev/i386/sysctl.c L256-L260](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/dev/i386/sysctl.c#L256-L260). Boot-arg `-nomsr35h` honoured only in a VM ("Not all VMMs emulate MSR_CORE_THREAD_COUNT (0x35)"). — [cpuid.c L992-L999](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/i386/cpuid.c#L992-L999)
- Apple's own paravirtual interface (hypercalls for core dumps, a time offset and a boot-session identifier) is used only when the hypervisor advertises Apple's signature leaf. — [xnu main, osfmk/i386/x86_hypercall.c L40-L52](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/i386/x86_hypercall.c#L40-L52), [cpuid.c L1472](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/i386/cpuid.c#L1472)
- [KVM] quickemu's device choices for macOS, with its comments: "VirtIO Block Media doesn't work in High Sierra (at all) or the Mojave (Recovery Image)"; "VirtIO Network is supported since Big Sur"; "VirtIO Memory Ballooning is supported since Big Sur"; "VirtIO RNG is supported since Big Sur"; "macOS 12+ (Monterey onwards) supports virtio-sound-pci natively". For Big Sur and for Monterey through Tahoe it uses `virtio-blk-pci`, `virtio-net-pci` and `virtio-balloon`; for older releases `ide-hd` on AHCI and `vmxnet3`. — [quickemu script L1088-L1125](https://github.com/quickemu-project/quickemu/blob/master/quickemu#L1088-L1125)
- [KVM] OSX-KVM's notes: "Newer macOS (namely Mojave+) have support for some virtio drivers. This can be enabled by applying the following change ... to get some performance gain", replacing `ide-hd,bus=sata.4` with `virtio-blk-pci`; its current script already uses `virtio-net-pci` and keeps `vmxnet3` only for High Sierra. — [OSX-KVM notes.md](https://github.com/kholia/OSX-KVM/blob/master/notes.md), [OSX-KVM OpenCore-Boot.sh](https://github.com/kholia/OSX-KVM/blob/master/OpenCore-Boot.sh)
- This project uses `ide-hd` on `ich9-ahci`, `vmxnet3`, and `virtio-sound-pci`. — project source `crates\orchord-core\src\qemu.rs` lines 64-86
- A QEMU developer found Apple's virtio block driver works only in legacy mode (2019, Mojave). — [kraxel.org, macOS as QEMU guest](https://www.kraxel.org/blog/2019/06/macos-qemu-guest/)
- The vmapple patch series summary states macOS provides no virtio HID drivers (read as a search-result summary). — [patchew, New vmapple machine type and xhci fixes](https://patchew.org/QEMU/20250112210056.16658-1-phil@philjordan.eu)
- MacHyperVSupport provides native Hyper-V synthetic devices (keyboard, mouse, network, SCSI, graphics, time synchronisation) for macOS guests on Hyper-V proper; its framebuffer kext "must be installed and kext signing disabled in SIP on macOS 11.0 and newer". — [MacHyperVSupport README](https://github.com/acidanthera/MacHyperVSupport/blob/master/README.md)

### Inferences
- There is no hidden "light mode" for VMs in the Intel kernel to switch on. What the kernel does differently in a VM is defensive (tolerating delays), not economising.
- `kern.hv_vmm_present` reads 1 in this guest whenever the hypervisor bit is visible, and user-space services act on it (software update catalogue, content caching). Forcing it to 0 or hiding the hypervisor bit would not make the guest lighter and would remove the kernel's VM allowances; it is not recommended.
- The practical lever in this area is device choice rather than detection: replacing the AHCI disk with `virtio-blk-pci` and `vmxnet3` with `virtio-net-pci` is what quickemu does for macOS 11 and later and what OSX-KVM recommends "to get some performance gain". Fewer, batched notifications per unit of disk or network work mean fewer exits. All of that evidence is from KVM; under WHPX every virtio notification is still an exit to QEMU in user space, so the size of the gain must be measured, and the project's rule about fixed PCI device order (the firmware stores the start-up disk as a PCI path) means a disk controller change is a migration, not a toggle. It might also sidestep the AHCI time-outs noted in section 6.
- MacHyperVSupport's synthetic devices need the Hyper-V VMBus, which a WHPX guest under QEMU does not have, so that kext family does not apply here.
- The paravirtual GPU route (`AppleParavirtGPU.kext`) needs host-side support that exists only for macOS hosts (Apple's framework) or the Linux-only project cited in section 4; nothing equivalent exists for a Windows host.

### Gaps
- The location of the `kern.hv_vmm_present` handler in the macOS 14 and 15 kernel sources was not found (it is no longer in `bsd/kern/kern_sysctl.c`), so its present-day implementation was not read.
- No authoritative list of which Apple services change behaviour when `kern.hv_vmm_present` is 1 on macOS 14 and 15 was found.
- No report of Apple's virtio block or network drivers under WHPX was found; compatibility and benefit on Windows are untested. Whether Apple's virtio block driver still requires legacy mode on macOS 11 to 15 is unconfirmed.
- Whether a virtio disk supports TRIM in Apple's driver (needed to keep the qcow2 image compact) was not established.
