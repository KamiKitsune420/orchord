# Windows host-side factors affecting speed and processor load of a QEMU/WHPX guest

Scope: Windows 10 22H2 and Windows 11 client hosts, QEMU 11.1 with `-accel whpx`, Intel macOS guest with software rendering. Researched October 2026.

Conventions used below:
- "Documented" means a vendor primary source (Microsoft Learn, QEMU docs or QEMU source) says it.
- "Measured" means a third party published numbers.
- "Hearsay" means forum reports or unsourced guides.
- "No admin" means a launcher can do it for its own QEMU child process as an ordinary user. "Admin" means it needs elevation or a reboot.
- QEMU source excerpts were read from the `master` branch on GitHub and from a local copy of the v11.1.0 `whpx-all.c`; the quoted passages are present in both.

Local observation on the test host (not a web source; taken with read-only commands on the machine these notes were written on, an i7-1355U with Windows 11 build 26200): VBS is running (`VirtualizationBasedSecurityStatus = 2`, `SecurityServicesRunning = {2}`), the active power plan is Balanced, and the only sleep state is Modern Standby (S0 Low Power Idle). No Hyper-V-Hypervisor event ID 2 was present in the System log, so the scheduler type could not be confirmed from the log.

## 1. Hybrid CPU scheduling: P-cores versus E-cores, EcoQoS, power throttling, and what a launcher can do

### Takeaway
Windows assigns every thread a Quality of Service (QoS) level, and a process that is a child of a window-owning process inherits that window's visibility state: in focus is High, visible is Medium, minimized or fully occluded is Low, and Low is documented as "schedules to efficient core" at the "most efficient CPU frequency" on battery. A launcher can remove this risk for QEMU without admin rights by calling `SetProcessInformation(ProcessPowerThrottling)` on the child with the execution-speed and timer-resolution controls explicitly turned off; that is the single best-documented, lowest-risk change in this whole topic.

### Cited Findings
- Documented: "While scheduling priority remains the main metric by which the system determines which thread to schedule next, QoS can influence core selection and processor power management. On platforms with heterogeneous processors, the QoS of a thread may restrict scheduling to a subset of processors, or indicate a preference for a particular class of processor." — [Microsoft Learn, Quality of Service](https://learn.microsoft.com/en-us/windows/win32/procthread/quality-of-service)
- Documented QoS levels and their effect: High = "Standard high performance" (since Windows 10 1709). Medium = "Varies by platform, between High and Low". Low = "Windowed applications that are not visible or audible to the end user" and "On battery, selects most efficient CPU frequency and schedules to efficient core". Utility (background services, Windows 11 22H2) = same as Low, on battery. Eco (explicitly tagged, Windows 11) = "Always selects most efficient CPU frequency and schedules to efficient cores". — [Microsoft Learn, Quality of Service](https://learn.microsoft.com/en-us/windows/win32/procthread/quality-of-service)
- Documented classification rule that covers a headless child process: "Processes which directly own a window (or are descendants of window owning processes) are assigned a QoS level according to their visibility and focus state": In Focus = High, Visible = Medium, Minimized or Fully Occluded = Low. — [Microsoft Learn, Quality of Service](https://learn.microsoft.com/en-us/windows/win32/procthread/quality-of-service)
- Documented: "Processes which are determined to be playing audio are HighQoS." — [Microsoft Learn, Quality of Service](https://learn.microsoft.com/en-us/windows/win32/procthread/quality-of-service)
- Documented heuristic fallback: threads not classified by the above "are automatically assigned a QoS level by the system. These heuristics include (but are not limited to) thread priority, where threads running with reduced thread priority can imply a lower QoS level." — [Microsoft Learn, Quality of Service](https://learn.microsoft.com/en-us/windows/win32/procthread/quality-of-service)
- Documented newer behaviour: Windows "may lower the QoS policy of a foreground application to Medium QoS after a period of user inactivity where no input is detected" (on battery only; listed as "Inactivity feature: Ge 2025.05", that is Windows 11 24H2 from the May 2025 update). It can be disabled with `HKLM\SYSTEM\CurrentControlSet\Control\Power\PowerThrottling`, value `DisableUserPresenceQos` (REG_DWORD) = 1. Admin, because it is under HKLM. — [Microsoft Learn, Quality of Service](https://learn.microsoft.com/en-us/windows/win32/procthread/quality-of-service)
- Documented opt-out API: `SetProcessInformation(hProcess, ProcessPowerThrottling, &PROCESS_POWER_THROTTLING_STATE, size)`. `ControlMask` selects the mechanism and `StateMask` says on or off. HighQoS (never throttle) = `ControlMask = PROCESS_POWER_THROTTLING_EXECUTION_SPEED`, `StateMask = 0`. EcoQoS = both set to `PROCESS_POWER_THROTTLING_EXECUTION_SPEED`. Both zero = "Let system manage all power throttling". The handle needs only the `PROCESS_SET_INFORMATION` access right, so it works on a child process handle; no privilege is mentioned. — [Microsoft Learn, SetProcessInformation](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-setprocessinformation)
- Documented: "If an application does not explicitly enable `PROCESS_POWER_THROTTLING_EXECUTION_SPEED`, the system will use its own heuristics to automatically infer a Quality of Service level." and "Prior to Windows 11, the EcoQoS level did not exist and the process was labeled as LowQoS". — [Microsoft Learn, SetProcessInformation](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-setprocessinformation)
- Documented: the per-thread equivalent is `SetThreadInformation` with `ThreadPowerThrottling` and `THREAD_POWER_THROTTLING_EXECUTION_SPEED`. — [Microsoft Learn, Quality of Service](https://learn.microsoft.com/en-us/windows/win32/procthread/quality-of-service)
- Documented: Task Manager "Efficiency mode" does two things: it "reduces process base priority to low" and "sets QoS mode to EcoQoS". Microsoft measured "up to 4x improvements (or ~76% reduction)" in UI responsiveness for other apps on a CPU-contended system, that is, the throttled process is deliberately starved. — [Microsoft Performance and Diagnostics blog](https://devblogs.microsoft.com/performance-diagnostics/reduce-process-interference-with-task-manager-efficiency-mode/)
- Documented: CPU Sets "declare application affinity in a 'soft' manner that is compatible with OS power management". Process Default CPU sets apply to all threads without a thread-level assignment. "If a thread or process has a restrictive affinity mask set, the affinity mask is respected above any conflicting CPU Set assignment." Functions: `GetSystemCpuSetInformation`, `SetProcessDefaultCpuSets`, `SetThreadSelectedCpuSets`. — [Microsoft Learn, CPU Sets](https://learn.microsoft.com/en-us/windows/win32/procthread/cpu-sets)
- Documented: QEMU on Windows cannot pin threads itself; `qemu_thread_set_affinity` and `qemu_thread_get_affinity` both `return -ENOSYS`. Any pinning has to come from outside QEMU. — [QEMU source, util/qemu-thread-win32.c](https://github.com/qemu/qemu/blob/master/util/qemu-thread-win32.c)
- Documented hidden power setting: `SchedulingPolicy` "specifies the preference (or constraint) in processor scheduling for long running threads on systems with processors with heterogeneous architecture". PowerCfg alias `SCHEDPOLICY`, hidden. Values: 0 All processors, 1 Performant processors, 2 Prefer performant processors, 3 Efficient processors, 4 Prefer efficient processors, 5 Automatic ("lets the OS determines the policy based on system configuration and QoS type"). A companion `ShortSchedulingPolicy` covers short-running threads. — [Microsoft Learn, SchedulingPolicy](https://learn.microsoft.com/en-us/windows-hardware/customize/power-settings/configuration-for-hetero-power-scheduling-schedulingpolicy)
- Hearsay with one number: a user on Windows 11 22H2 with a 12th-generation Intel processor reported HandBrake falling to E-cores only when the screen turned off, about 22 frames per second on all cores versus 10.5 on E-cores only (roughly half), and that the High performance power mode "didn't make any difference". — [Microsoft Q&A thread](https://learn.microsoft.com/en-us/answers/questions/1027852/windows-11-22h2-thread-director-issues-with-intel)
- Hearsay: the same symptom (only E-cores used when the application is minimized) is reported for MATLAB, Folding@home and others; suggested workarounds conflict. Some say Settings, System, Power, Power mode = Best performance fixes it; others say neither the High performance plan nor High process priority changed it; others say raising priority to Above normal helped. — [MathWorks Answers](https://jp.mathworks.com/matlabcentral/answers/1734465-only-e-cores-utilized-when-matlab-is-minimized); [Folding@home forum](https://forum.foldingathome.org/viewtopic.php?p=358596); [ElevenForum thread](https://www.elevenforum.com/t/forcing-performance-mode-for-background-app-on-intel-p-e-core-cpu.15763/); [XMG article](https://www.xmg.gg/en/?p=35366)
- Hearsay: a Microsoft Answers thread says the "Background" power profile prefers E-cores by default and that editing that profile to prefer P-cores is a workaround, with a possible battery cost. — [Microsoft Answers thread](https://answers.microsoft.com/en-us/windows/forum/all/power-plan-cpu-frequency-settings-affect-only-e/ebe030fe-7c02-406f-bd15-3221108552f0)

### Inferences
- Orchord is the window-owning parent and QEMU (`-display none`) is its descendant, so by the documented rule QEMU gets Low QoS whenever the Orchord window is minimized or fully covered by another window and the guest is silent. A screen-reader user who works in another maximized application while the VM runs will hit this state routinely. On battery that means E-cores and the lowest efficient frequency on the i7-1355U. The explicit HighQoS call removes the dependency on window state.
- Recommended launcher call (no admin, per-process, reversible): one `SetProcessInformation` call on the QEMU handle with `ControlMask = EXECUTION_SPEED | IGNORE_TIMER_RESOLUTION` and `StateMask = 0`. The timer flag is a Windows 11 feature, so on Windows 10 it is safer to make two separate calls and ignore a failure of the timer one (the behaviour of an unknown flag on Windows 10 was not verified).
- The documentation says Low QoS restricts cores "on battery"; the forum reports describe the same effect on desktop machines on mains power. These conflict. The safest reading is that the exact tuning per QoS level is platform- and build-dependent (the doc says it "can be modified through Windows Provisioning"), so the explicit opt-out is worth doing regardless of power source.
- Cost of the opt-out: QEMU will draw P-core power even when the user is not looking at it, which shortens battery life. It is a legitimate use of the API (the VM is foreground work from the user's point of view), not a workaround.
- The AMD Ryzen 7 5700X tester has no E-cores and is a desktop on mains, so the core-selection half of this question does not apply there; at most the frequency half would, and only "on battery" per the documentation.
- Hard pinning is probably a bad idea on the i7-1355U. It has only 2 P-cores (4 logical processors). Pinning the whole QEMU process there puts 4 vCPU threads plus QEMU's main loop, I/O and audio threads on 2 physical cores, with vCPUs sharing hyper-thread siblings. Process-level affinity or CPU sets cannot be limited to the vCPU threads from outside without enumerating QEMU's threads. If any steering is wanted, `SetProcessDefaultCpuSets` (soft) is safer than `SetProcessAffinityMask` (hard). No measurement was found for either.
- `SetThreadIdealProcessor` is only a hint to the scheduler; no source was found on its effect for WHPX threads.

### Gaps
- No Intel primary document on Thread Director's treatment of background windows was retrieved (the AnandTech article that covered it now redirects to a forum index, and no Intel support article turned up in search).
- Whether an explicit HighQoS setting also overrides the Windows 11 24H2 "user inactivity lowers foreground QoS" feature is not stated.
- No measurement of a QEMU/WHPX guest on P-cores versus E-cores was found. The only number is the HandBrake anecdote (about 2x).
- Whether changing the hidden `SCHEDPOLICY` value through `powercfg` needs elevation, and whether it holds at run time, was not verified; one forum report says heterogeneous settings "are not always applied".
- The access right required by `SetProcessDefaultCpuSets` on another process handle was not checked.

## 2. Is the Windows thread scheduler or the hypervisor in charge of where a vCPU runs? Hypervisor scheduler type on client Windows

### Takeaway
On Windows 10 (since 1803) and Windows 11 client editions the hypervisor uses the root scheduler by default, which hands all placement decisions to the ordinary Windows (NT) thread scheduler, so QoS, priority, affinity and CPU sets on QEMU's threads should genuinely govern which physical cores the guest uses. Microsoft says this is the only supported configuration on client Windows and that it should not be changed with `bcdedit`.

### Cited Findings
- Documented: "The root scheduler arrived with Windows 10, version 1803. When you enable the root scheduler type, the hypervisor gives the root partition control of work scheduling. In the root partition OS instance, the NT scheduler manages all aspects of assigning work to system logical processors." — [Microsoft Learn, Manage Hyper-V hypervisor scheduler types](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/manage/manage-hyper-v-scheduler-types)
- Documented: "Starting with Windows 10, version 1803, the root scheduler is used by default on client systems only", in part because "It's important to properly operate future systems with heterogenous core architectures." "This configuration is the only supported hypervisor scheduler configuration for client systems. Administrators shouldn't attempt to override the default hypervisor scheduler type on Windows client systems." — [Microsoft Learn, Manage Hyper-V hypervisor scheduler types](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/manage/manage-hyper-v-scheduler-types)
- Documented: per-VM processor resource controls (caps, weights, reserves) "aren't supported when you enable the hypervisor root scheduler"; they "only apply where the hypervisor directly controls virtual processor scheduling, such as with the classic and core scheduler types." — [Microsoft Learn, Manage Hyper-V hypervisor scheduler types](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/manage/manage-hyper-v-scheduler-types)
- Documented: the scheduler type is the BCD entry `hypervisorschedulertype` (`bcdedit /set hypervisorschedulertype Classic|Core|Root`, admin, reboot required). The current type is reported by Hyper-V-Hypervisor event ID 2 in the System log: 1 = classic with SMT disabled, 2 = classic, 3 = core, 4 = root. PowerShell: `Get-WinEvent -FilterHashTable @{ProviderName="Microsoft-Windows-Hyper-V-Hypervisor"; ID=2} -MaxEvents 1`. — [Microsoft Learn, Manage Hyper-V hypervisor scheduler types](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/manage/manage-hyper-v-scheduler-types)
- Documented: the core scheduler "can potentially reduce performance. If only one virtual processor in a group can run, only one of the instruction streams in the core launches. The other is left idle." A VM without SMT exposed has each virtual processor "consume the entire core when it runs". It is the default on Windows Server 2019 and later, not on client. — [Microsoft Learn, Manage Hyper-V hypervisor scheduler types](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/manage/manage-hyper-v-scheduler-types); [Microsoft Learn, About scheduler type selection](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/manage/about-hyper-v-scheduler-type-selection)
- Documented from the Linux side of the same hypervisor: "The root scheduler allows the root partition to schedule guest vCPUs across physical cores, supporting both time slicing and CPU affinity (e.g., via cgroups). In contrast, the core scheduler delegates vCPU-to-physical-core scheduling entirely to the hypervisor." — [Linux kernel mailing list, Hyper-V integrated scheduler patch series](https://lkml.iu.edu/hypermail/linux/kernel/2601.2/10121.html)
- Documented: QEMU's WHPX backend "is implemented on top of Vid, which is itself implemented on the same set of hypercalls as the mshv driver on Linux." — [QEMU documentation, Windows Hypervisor Platform](https://www.qemu.org/docs/master/system/whpx.html)

### Inferences
- With the root scheduler, a vCPU runs when and where Windows schedules the QEMU thread that calls `WHvRunVirtualProcessor`. So everything in question 1 (QoS, E-core relegation, priority) applies directly to guest speed, and affinity of the vCPU thread does determine the physical core. This is a strong inference from the two statements above, not a sentence Microsoft has written about the Windows Hypervisor Platform specifically.
- Switching to the classic or core scheduler would take placement away from Windows (and from Thread Director hints), is unsupported on client, and on a hybrid processor would likely be worse. No guidance for third-party WHPX users on scheduler type was found; the practical advice is "leave it alone" and, at most, have the launcher read event ID 2 to warn if it is not 4.
- Under the root scheduler the SMT side-channel isolation that the core scheduler provides is absent, but that is the client default and not something the launcher changes.

### Gaps
- No Microsoft document states in so many words that a Windows Hypervisor Platform virtual processor executes in the context of the calling user thread and follows its affinity.
- The event ID 2 record was not present in the test host's System log, so the scheduler type there is unconfirmed (the log may have rolled over since the last boot record was written).

## 3. Virtualization-based security: Memory Integrity (HVCI), Core Isolation, Credential Guard, Windows Sandbox, WSL2

### Takeaway
Published measurements put the host-side cost of VBS with Memory Integrity at roughly 5 percent on recent processors and up to about 8 to 10 percent in worst cases, but nobody appears to have measured its effect on a WHPX guest. WHPX already requires the Windows hypervisor to be running, so turning VBS off does not get QEMU "off the hypervisor"; the expected gain is small and unproven, and the security cost is real.

### Cited Findings
- Measured: Tom's Hardware found HVCI cost about 3 to 6 percent and VBS about 4 to 5 percent in games across four processors, summarised as "around a 5% loss in performance, give or take 1%". The tests used processors with MBEC (Intel 7th generation and later, AMD Zen 2 and later); older processors "will suffer more". — [Tom's Hardware](https://www.tomshardware.com/news/windows-11-gaming-benchmarks-performance-vbs-hvci-security)
- Measured (secondary reports of ComputerBase tests): about 10 percent at most on an old Ryzen 7 1800X, and about 8 percent lower frame rates on a Ryzen 7 5800X3D under Windows 11 24H2 with Memory Integrity on. — [Digital Trends](https://digitaltrends.com/computing/are-windows-11-security-features-killing-gaming-performance); [Landian News](https://landian.news/article/3401.html)
- Documented by a vendor: Windows 11 24H2 enables VBS by default; with it on, Windows runs a hypervisor beneath the OS, which "prevents VMware Workstation from having direct access to hardware virtualization", with increased processor overhead, slower I/O and reduced responsiveness. No magnitude is given. The fix they list is turning off Memory Integrity (Windows Security, Device security, Core isolation details), removing the Hyper-V, Virtual Machine Platform, Windows Hypervisor Platform, Windows Sandbox and WSL features, and `bcdedit /set hypervisorlaunchtype off`. — [Broadcom knowledge base 417896](https://knowledge.broadcom.com/external/article/417896/after-the-host-os-upgrade-to-version-win.html)
- Documented: "WHPX requires the Windows Hypervisor Platform feature to be installed", enabled with `DISM /online /Enable-Feature /FeatureName:HypervisorPlatform /All` (admin, reboot). — [QEMU documentation, Windows Hypervisor Platform](https://www.qemu.org/docs/master/system/whpx.html)
- Documented, related security-versus-speed switch inside QEMU: `-accel whpx,ssd=off` disables the "separate security domain" feature, which "results in a significant MMIO performance increase at the detriment of security mitigations". The source comment says the combination "results in a significant vmexit performance improvement by skipping speculative execution mitigations" (it clears IBRS, STIBP, IBPB and SSBD support for the guest). — [QEMU documentation, Windows Hypervisor Platform](https://www.qemu.org/docs/master/system/whpx.html); [QEMU source, target/i386/whpx/whpx-all.c](https://github.com/qemu/qemu/blob/v11.1.0/target/i386/whpx/whpx-all.c)

### Inferences
- The Broadcom remedy (hypervisor off) is the opposite of what WHPX needs: QEMU with `-accel whpx` cannot run at all with `hypervisorlaunchtype off`. For Orchord the only VBS-related knob is Memory Integrity itself, and the hypervisor stays loaded either way.
- Memory Integrity adds cost to host kernel-mode work (driver code, page permission changes). A guest that is mostly burning virtual processor time in software rendering spends its time inside the guest, so the plausible effect is at the low end of the measured range. This is reasoning, not data.
- Both testers' processors have the hardware feature that makes HVCI cheap (i7-1355U is far newer than Intel 7th generation; the Ryzen 7 5700X is Zen 3).
- The test host currently has VBS running with service 2 active (local observation; value 2 is Memory Integrity in Microsoft's Win32_DeviceGuard value list, which was not re-fetched in this session). An A/B test there would be the only way to get a real number.
- Recommendation for the report: do not advise users to turn off Memory Integrity. It is admin-only, needs a reboot, weakens kernel protection, and has no demonstrated benefit for this workload. `ssd=off` is a QEMU-side option with a documented "significant" benefit and a guest-isolation cost, and belongs with the QEMU tuning notes.

### Gaps
- No measurement of WHPX (or Android Emulator, VirtualBox or VMware in Hyper-V mode) guest speed with Memory Integrity on versus off was found.
- Nothing found on Credential Guard specifically affecting guest speed.
- Nothing authoritative found on whether merely having Windows Sandbox or WSL2 installed (not running) changes anything beyond keeping the hypervisor loaded.

## 4. Power: plan and power mode, battery versus mains, processor state, core parking, Efficiency mode, Modern Standby, keeping the machine awake

### Takeaway
The documented power effects are tied to QoS (question 1) and are strongest on battery; an explicit HighQoS tag is the launcher-side fix. A launcher can stop idle sleep with a power request and no admin rights, but on a Modern Standby laptop on battery Windows ends that request 5 minutes after the sleep timeout, and closing the lid or pressing the power button always wins.

### Cited Findings
- Documented: Low and Utility QoS select the "most efficient CPU frequency" and efficient cores "On battery"; Eco does so "Always"; QoS "can assist in reducing CPU power consumption while operating on AC power to reduce thermal output". — [Microsoft Learn, Quality of Service](https://learn.microsoft.com/en-us/windows/win32/procthread/quality-of-service)
- Documented: Task Manager Efficiency mode = low base priority plus EcoQoS. If a user (or a tool) applies it to QEMU, the guest is throttled by design. — [Microsoft Performance and Diagnostics blog](https://devblogs.microsoft.com/performance-diagnostics/reduce-process-interference-with-task-manager-efficiency-mode/)
- Documented power request types (`PowerCreateRequest` then `PowerSetRequest`): `PowerRequestSystemRequired` = "The system continues to run instead of entering sleep after a period of user inactivity." `PowerRequestDisplayRequired` keeps the display on (and needs SystemRequired as well to stop sleep). `PowerRequestExecutionRequired` = "The calling process continues to run instead of being suspended or terminated by process lifetime management mechanisms." `PowerRequestAwayModeRequired` is only for traditional S3 sleep systems. — [Microsoft Learn, PowerSetRequest](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-powersetrequest)
- Documented limits: "On Modern Standby systems on DC power, system and execution required power requests are terminated 5 minutes after the system sleep timeout has expired." and "power requests are terminated upon user-initiated system sleep entry (power button, lid close or selecting Sleep from the Start menu)." — [Microsoft Learn, PowerSetRequest](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-powersetrequest)
- Documented best practice: supply a reason string in `REASON_CONTEXT`, set the request just before the scenario and clear it with `PowerClearRequest` as soon as it ends. — [Microsoft Learn, PowerSetRequest](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-powersetrequest)
- Documented: the heterogeneous scheduling policy is a per-power-plan setting (`SCHEDPOLICY`, hidden), with "Automatic" letting the OS decide "based on system configuration and QoS type". — [Microsoft Learn, SchedulingPolicy](https://learn.microsoft.com/en-us/windows-hardware/customize/power-settings/configuration-for-hetero-power-scheduling-schedulingpolicy)
- Documented: a raised timer resolution "can also prevent the CPU power management system from entering power-saving modes" (QEMU always raises it; see question 5). — [Microsoft Learn, timeBeginPeriod](https://learn.microsoft.com/en-us/windows/win32/api/timeapi/nf-timeapi-timebeginperiod)
- Hearsay, conflicting: "Best performance" power mode fixes E-core relegation of unfocused programs according to some guides; other users report the High performance mode made no difference. — [XMG article](https://www.xmg.gg/en/?p=35366); [Microsoft Q&A thread](https://learn.microsoft.com/en-us/answers/questions/1027852/windows-11-22h2-thread-director-issues-with-intel)

### Inferences
- The launcher should hold a `PowerRequestSystemRequired` request on its own process while a VM is running (no admin to create; it can be inspected with `powercfg /requests`, which from memory needs an elevated prompt, not re-verified here). Adding `PowerRequestExecutionRequired` is reasonable on Modern Standby machines. The request belongs to the launcher, not to QEMU; QEMU's source shows no call that prevents sleep (none of `SetThreadExecutionState`, `PowerCreateRequest` appear in the Windows-specific files examined).
- The test host is a Modern Standby machine on the Balanced plan (local observation), so on battery the 5-minute rule applies: an unattended VM will still be suspended eventually. This cannot be overridden by an application and should simply be explained to users.
- For users, the low-risk advice is: plug in for heavy VM use, and on Windows 11 choose Settings, System, Power and battery, Power mode, Best performance (no admin). The size of the benefit is unmeasured for this workload and the reports conflict, so it should be offered as "may help", not promised.
- A U-series laptop processor such as the i7-1355U is power- and heat-limited; sustained 4-vCPU software rendering will likely hit its long-term power limit and drop frequency whatever Windows settings are used. This is general knowledge about that processor class, not something sourced here.

### Gaps
- No primary source was retrieved on processor minimum/maximum state or core parking settings and their effect on a VM; no measurement of Balanced versus Best performance for a QEMU guest exists in what was found.
- `SetThreadExecutionState` documentation was not fetched; `PowerSetRequest` is the newer equivalent and was used instead.
- Whether a HighQoS-tagged background process is still frequency-limited by the "Best power efficiency" mode is not documented.

## 5. Timer resolution

### Takeaway
QEMU asks Windows for the finest timer resolution the machine supports as soon as it starts, so the launcher does not need to (and since Windows 10 2004 could not) do it on QEMU's behalf. On Windows 11 the system may silently ignore that request when the owning window is minimized, covered or otherwise invisible and silent; the launcher can forbid that with the same `SetProcessInformation` call used for QoS.

### Cited Findings
- Documented in source: at start-up QEMU calls `timeGetDevCaps(&mm_tc, sizeof(mm_tc)); timeBeginPeriod(mm_tc.wPeriodMin);` in `os_setup_early_signal_handling`, and `timeEndPeriod` at exit. — [QEMU source, os-win32.c](https://github.com/qemu/qemu/blob/master/os-win32.c)
- Documented: "Starting with Windows 10, version 2004, this function no longer affects global timer resolution. For processes which call this function, Windows uses the lowest value (that is, highest resolution) requested by any process. For processes which have not called this function, Windows does not guarantee a higher resolution than the default system resolution." — [Microsoft Learn, timeBeginPeriod](https://learn.microsoft.com/en-us/windows/win32/api/timeapi/nf-timeapi-timebeginperiod)
- Documented: "Starting with Windows 11, if a window-owning process becomes fully occluded, minimized, or otherwise invisible or inaudible to the end user, Windows does not guarantee a higher resolution than the default system resolution." — [Microsoft Learn, timeBeginPeriod](https://learn.microsoft.com/en-us/windows/win32/api/timeapi/nf-timeapi-timebeginperiod)
- Documented opt-out: with `PROCESS_POWER_THROTTLING_IGNORE_TIMER_RESOLUTION` in `ControlMask` and `StateMask = 0` ("Always honor Timer Resolution Requests"), "the system remembers and honors any previous timer resolution request by the process." Setting the flag in both masks makes Windows ignore the process's requests. — [Microsoft Learn, SetProcessInformation](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-setprocessinformation)
- Measured by an independent engineer: the default interrupt interval is 15.625 milliseconds (64 per second); on Windows 10 2004 a process that had not raised the resolution saw `Sleep(1)` wake "only ... about 64 times a second", and "if a process wants a faster timer interrupt then it should be calling timeBeginPeriod itself." He also warns that multi-process programs whose parent raises the rate for its children may misbehave. — [Bruce Dawson, Random ASCII](https://randomascii.wordpress.com/2020/10/04/windows-timer-resolution-the-great-rule-change/)
- Documented trade-off: a higher resolution "can also reduce overall system performance, because the thread scheduler switches tasks more often", and can stop the processor entering power-saving modes. — [Microsoft Learn, timeBeginPeriod](https://learn.microsoft.com/en-us/windows/win32/api/timeapi/nf-timeapi-timebeginperiod)

### Inferences
- If Windows 11 drops QEMU back to 15.6 millisecond granularity, every QEMU timer (main loop timeouts, audio buffer pacing, display refresh, and any guest timer device that QEMU emulates in user mode) becomes up to 15 times coarser. Expected symptoms are choppy audio and sluggish guest timing rather than higher processor load. On Windows 10 hosts, where QEMU emulates the guest's interrupt controller and its timer in user mode (see question 9), guest timer accuracy depends on this even more, but Windows 10 does not have the "ignore when hidden" behaviour.
- Whether a windowless QEMU that is merely a child of a window-owning process is subject to the Windows 11 rule is not stated (the timer rule says "window-owning process"; the QoS rule explicitly includes descendants). Setting the opt-out is free and removes the doubt.
- `wPeriodMin` is normally 1 millisecond, so QEMU runs the host at a 1 millisecond tick for its own process. That costs some battery on the host for as long as the VM runs; it is inherent to QEMU and not a launcher choice.

### Gaps
- No published measurement of QEMU guest audio latency or responsiveness at default versus raised timer resolution on Windows was found.
- Not verified whether QEMU's audio back ends on Windows use event-driven waits that are immune to timer resolution.

## 6. Antivirus: Microsoft Defender scanning of disk images and QEMU I/O

### Takeaway
Microsoft's own guidance for Hyper-V hosts is to exclude virtual disk files, their folders and the VM worker processes from real-time scanning, but it is framed as avoiding errors and "optimal operation", with no numbers; no measurement of Defender's cost on a qcow2 image was found. Adding an exclusion needs administrator rights and lowers protection, so it should be an opt-in suggestion to the user, not something the launcher does silently.

### Cited Findings
- Documented: for Hyper-V hosts, "Configure the real-time scanning component within your antivirus software to exclude" all directories containing virtual disk files (`*.vhd`, `*.vhdx`, `*.avhd`, `*.avhdx`, `*.iso`, state files and others), custom virtual disk directories, and the processes `Vmms.exe`, `Vmwp.exe`, `Vmsp.exe`, `Vmcompute.exe`, "For optimal operation of Hyper-V and the running virtual machines". The stated motive is avoiding failures such as virtual machines missing or failing to start. — [Microsoft Learn, Recommended antivirus exclusions for Hyper-V hosts](https://learn.microsoft.com/en-us/troubleshoot/windows-server/virtualization/antivirus-exclusions-for-hyper-v-hosts)
- Documented caveat: "This article contains information that shows how to help lower security settings", and the changes "should be made only on" machines with the Hyper-V role and running virtual machines or on their file servers. The automatic Defender exclusions it mentions apply to Windows Server with the Hyper-V role, not to client Windows or to QEMU. — [Microsoft Learn, Recommended antivirus exclusions for Hyper-V hosts](https://learn.microsoft.com/en-us/troubleshoot/windows-server/virtualization/antivirus-exclusions-for-hyper-v-hosts)
- Documented syntax: `Add-MpPreference -ExclusionPath 'C:\Temp'` "disables Windows Defender scheduled and real-time scanning for files in this folder." `-ExclusionProcess` takes "paths to process images" and "excludes any files opened by the processes that you specify from scheduled and real-time scanning ... The cmdlet does not exclude the processes themselves." `-ExclusionExtension` excludes by file extension. — [Microsoft Learn, Add-MpPreference](https://learn.microsoft.com/en-us/powershell/module/defender/add-mppreference)
- Independent test: adding exclusions through PowerShell requires elevation, and Tamper Protection did not block it in NVISO's 2022 tests (Tamper Protection covers real-time protection and related switches, not the exclusion list). — [NVISO Labs](https://blog.nviso.eu/2022/12/02/can-we-block-the-addition-of-local-microsoft-defender-antivirus-exclusions/)
- Vendor claim, different scenario: Dev Drive with Defender "performance mode" (asynchronous scanning) gives "up to 30% better performance for overall build times" versus Windows 11 22H2, and Microsoft calls asynchronous scanning safer than folder and process exclusions. This is for many-small-file developer workloads, not one large image file. — [Windows Developer Blog](https://blogs.windows.com/windowsdeveloper/2023/06/01/dev-drive-performance-security-and-control-for-developers/); [Microsoft Learn, Defender performance mode](https://learn.microsoft.com/en-us/defender-endpoint/microsoft-defender-endpoint-antivirus-performance-mode)

### Inferences
- The most targeted exclusion for Orchord would be a process exclusion for the bundled QEMU executable, for example `Add-MpPreference -ExclusionProcess "C:\full\path\qemu-system-x86_64.exe"` (admin). By the documented semantics this stops scanning of files QEMU opens (the disk images and firmware) while QEMU's own executable is still scanned. A folder exclusion for the VM folder is the broader alternative. The user-interface path on Windows 11 is Windows Security, Virus and threat protection, Manage settings, Exclusions, Add or remove exclusions (path given from general knowledge, not re-verified here).
- Expected benefit is uncertain. Real-time scanning is mainly triggered when files are opened, closed after writing, or executed; QEMU keeps one large image open for hours and does block I/O inside it, so the steady-state cost may be small and the gain mostly at VM start, first use of an installer image, and when images are created or copied. This is reasoning; treat any "Defender slows VMs a lot" claim as hearsay until measured.
- Security trade-off: anything inside an excluded image or opened by the excluded process is not scanned on the host. For a macOS guest image that is low risk to Windows, but an exclusion on a user-writable folder is a known hiding place for malware, so recommend the process exclusion over a folder exclusion and never apply it without consent.

### Gaps
- No measured impact of Defender real-time protection on QEMU or any hypervisor's disk image I/O was found.
- Whether Tamper Protection or managed-device policy now blocks local exclusions on current Windows 11 builds was not re-checked (the NVISO test is from 2022).
- Third-party antivirus products were not researched.

## 7. Memory: commitment, pinning, paging and compression, large pages, low free memory

### Takeaway
QEMU on Windows commits the whole guest RAM size at start with an ordinary `VirtualAlloc`, with no large-page option and no documented pinning, and hands that ordinary process memory to the hypervisor as the guest's backing store. Whether Windows can then page out or compress guest memory under pressure is not documented anywhere that was found; the safe assumption is that it can, so the guest's RAM size must fit comfortably in free host memory.

### Cited Findings
- Documented in source: guest RAM is allocated with `VirtualAlloc(NULL, size, MEM_COMMIT, PAGE_READWRITE)`; there is no `MEM_LARGE_PAGES` path, and the no-reserve option is refused with "Skipping reservation of swap space is not supported." — [QEMU source, util/oslib-win32.c](https://github.com/qemu/qemu/blob/master/util/oslib-win32.c)
- Documented in source: pre-allocation on Windows (`qemu_prealloc_mem`) is a simple single-threaded loop that writes one byte per page; "async prealloc not supported". — [QEMU source, util/oslib-win32.c](https://github.com/qemu/qemu/blob/master/util/oslib-win32.c)
- Documented in source: WHPX maps that memory into the guest with `WHvMapGpaRange(partition, mem, gva, size, flags)` with read, execute and (if writable) write flags. — [QEMU source, accel/whpx/whpx-common.c](https://github.com/qemu/qemu/blob/master/accel/whpx/whpx-common.c)
- Documented: `WHvMapGpaRange` "sets a region in the caller's process as the backing memory for that range." The page says nothing about locking, pinning or large pages. — [Microsoft Learn, WHvMapGpaRange](https://learn.microsoft.com/en-us/virtualization/api/hypervisor-platform/funcs/whvmapgparange)
- Documented: process memory priority "helps to determine how long pages remain in the working set of a process before they are trimmed"; lower-priority pages are trimmed first. `SetProcessInformation(ProcessMemoryPriority)` is the API. — [Microsoft Learn, SetProcessInformation](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-setprocessinformation)

### Inferences
- `MEM_COMMIT` charges the full guest RAM against the system commit limit (physical RAM plus page file) immediately, but physical pages are only used as the guest touches them. On a 16 GB host a guest sized at 8 GB needs 8 GB of commit headroom at launch and will grow toward 8 GB of physical use as macOS fills its memory (macOS tends to touch most of its RAM for caches).
- Because the backing store is ordinary private process memory with no documented pinning, Windows working-set trimming, the page file and memory compression can plausibly apply to it. If they do, a host short of free memory would make the guest stall on host page faults, which looks like a slow or frozen VM rather than high processor load. "Memory cleaner" tools that force working sets to be emptied would be actively harmful to a running VM for the same reason. All of this is inference pending a test (watch QEMU's working set versus commit in Task Manager under memory pressure).
- Large pages are not available through QEMU on Windows as built: there is no code path, and Windows large pages additionally need the "Lock pages in memory" privilege (`SeLockMemoryPrivilege`), which is admin-granted and takes effect at next sign-in. Not a launcher option.
- Practical guidance for the report: size guest RAM so that host free memory stays healthy (on the 16 GB test host, 6 to 8 GB for the guest is the plausible ceiling), close memory-heavy host applications, and do not shrink or disable the page file, since full commit is required up front.

### Gaps
- No Microsoft statement was found on whether Windows Hypervisor Platform guest memory is pageable, compressible or pinned on the host. This is the biggest unknown in this section.
- Whether QEMU's `-overcommit mem-lock=on` does anything on Windows was not checked.
- No measurement of guest slowdown under host memory pressure with WHPX was found.

## 8. Storage: disk type, write caching, NTFS compression and sparse files, BitLocker, separate drive

### Takeaway
The only solid numbers found are for BitLocker's software encryption, which one test showed cutting solid-state drive random-write speed by up to about 45 percent; everything else about image placement on Windows is general advice without measurements. Storage affects boot, application launch and swap inside the guest far more than it affects steady-state virtual processor load.

### Cited Findings
- Measured: software BitLocker (the Windows 11 Pro default) on a Samsung 990 Pro with a Core i9-12900K cost about 21 percent on 4 KB random reads, 43 to 46 percent on random writes, 13 percent on a file copy and about 20 percent in PCMark 10 storage, versus none for hardware (OPAL) encryption. The authors note it is one drive on one high-end system and "suspect" laptops fare worse (untested). — [Tom's Hardware](https://tomshardware.com/news/windows-software-bitlocker-slows-performance)
- Vendor corroboration: the impact "may be more noticeable during random read/write tests" and when many small files are loaded; sequential performance shows limited difference. — [MSI support FAQ](https://www.msi.com/faq/faq-11154)
- Documented (old): NTFS could fragment very large sparse files "with many 64-KB segments"; a Windows 8.1 hotfix made it allocate larger chunks. — [Microsoft Support KB 2964438](https://support.microsoft.com/kb/2964438)
- Hearsay: a Windows guest on a nearly full qcow2 image dropped to about 2 megabytes per second and defragmenting did not help (2016, Linux host). — [Proxmox user mailing list](https://lists.proxmox.com/pipermail/pve-user/2016-May/010299.html)

### Inferences
- A qcow2 file grows as the guest writes, so on NTFS it will fragment over time; on a solid-state drive that matters little. On a hard disk a qcow2-backed macOS guest will be very slow regardless of tuning, and that is worth a plain warning to users.
- NTFS compression on the folder holding the image should be avoided: it forces compress and decompress work on every image I/O and badly fragments large files. This is long-standing general guidance; no source specific to qcow2 on NTFS was found, so label it as such.
- BitLocker or Device Encryption cannot be changed per file and turning it off is an admin action with an obvious security cost; the realistic advice is only "if you have an unencrypted internal solid-state drive, keep VM images there". Moving the image to a second physical drive helps only if the system drive is the bottleneck (it also holds the page file).
- macOS guests under memory pressure swap heavily to their virtual disk, so host storage speed and guest RAM size interact.

### Gaps
- No measurements for QEMU image I/O on Windows by cache mode, by NTFS compression or by BitLocker state were found. Windows host write-cache settings (Device Manager, disk Policies) were not researched to a citable source.
- QEMU's own `cache=` and `aio=` options on Windows belong to the QEMU-side notes and were not covered here.

## 9. AMD hosts and Windows 10: QEMU's "legacy OS" path

### Takeaway
QEMU decides at start-up whether Windows is "modern"; Windows 10 fails the test and gets a reduced configuration: no Hyper-V enlightenments for the guest, and by default the guest's interrupt controller is emulated by QEMU in user mode instead of by the hypervisor. That means more exits to user mode per interrupt and timer event on Windows 10 than on Windows 11, independent of processor vendor. No AMD-specific WHPX slowdown is documented, only scattered bug reports.

### Cited Findings
- Documented in source: `is_modern_os` is set false when `WHvGetCapability(WHvCapabilityCodeProcessorPerfmonFeatures)` fails; the comment reads "Relying on this is a crutch to maintain Windows 10 support. WHvCapabilityCodeProcessorPerfmonFeatures and WHvPartitionPropertyCodeSyntheticProcessorFeaturesBanks are implemented starting from Windows Server 2022 (build 20348)." Windows 10 22H2 is build 19045, so it is "legacy". — [QEMU source, target/i386/whpx/whpx-all.c](https://github.com/qemu/qemu/blob/v11.1.0/target/i386/whpx/whpx-all.c)
- Documented in source: Hyper-V enlightenments (synthetic processor features such as the reference time counter, synthetic timers, guest idle register, flush hypercalls) are only set `if (is_modern_os && whpx->hyperv_enlightenments_allowed)`; asking for them explicitly on Windows 10 fails with "Hyper-V enlightenments not available on legacy Windows". — [QEMU source, target/i386/whpx/whpx-all.c](https://github.com/qemu/qemu/blob/v11.1.0/target/i386/whpx/whpx-all.c)
- Documented in source: the hypervisor's local interrupt controller emulation is enabled only when `!(whpx_is_legacy_os() && pic_enabled && !whpx->kernel_irqchip_required)`; that is, on Windows 10 with the legacy PIC present (the default machine) it is skipped unless explicitly required. On legacy systems QEMU also uses a separate CPUID path because "Legacy OSes don't have WHvGetVirtualProcessorCpuidOutput". — [QEMU source, target/i386/whpx/whpx-all.c](https://github.com/qemu/qemu/blob/v11.1.0/target/i386/whpx/whpx-all.c)
- Documented: "On Windows 10, a legacy PIC interrupt injected does not wake the guest from an HLT when using the Hyper-V provided interrupt controller", so the Hyper-V interrupt controller "is disabled by default" there; it can be enabled with `-M q35,pic=off`, in which case "using a UEFI is recommended". An earlier revision of the same page said the problem was "addressed in QEMU 11.0 on Windows 11 platforms" and gave `-M kernel-irqchip=off` as the Windows 10 workaround. — [QEMU documentation, Windows Hypervisor Platform](https://www.qemu.org/docs/master/system/whpx.html); [earlier revision of whpx.rst](https://qemu.googlesource.com/qemu/+/e788efd9af1663ec98111bae3c0f4922be2e5abb/docs/system/whpx.rst)
- Documented: on x86-64 the back end "is tested starting from Windows 10 version 2004"; earlier releases "might work but are not tested". `-M kernel-irqchip=` "is not expected to be manually set during normal operation". Guests using MMX, SSE or AVX instructions to access device memory are not supported, and legacy VGA modes are "quite suboptimal". — [QEMU documentation, Windows Hypervisor Platform](https://www.qemu.org/docs/master/system/whpx.html)
- Documented in source: turning off the separate security domain is attempted on all systems but "Some old Windows 10 releases didn't have this, so not fatal". — [QEMU source, target/i386/whpx/whpx-all.c](https://github.com/qemu/qemu/blob/v11.1.0/target/i386/whpx/whpx-all.c)
- Bug reports on AMD (individual, not performance data): a FreeDOS guest stops accepting keyboard input under WHPX with a "WHPX injection" error on a Ryzen 5 3600 with Windows 10, fine under TCG; `-cpu max` fails to boot on a Ryzen with Windows 11 with "WHPX: Unexpected VP exit code 4". — [QEMU issue 346](https://gitlab.com/qemu-project/qemu/-/issues/346); [QEMU issue 1043](https://gitlab.com/qemu-project/qemu/-/issues/1043)
- Documented development activity: a late QEMU 11.0 release-candidate pull request describes a "big i386/emulate performance improvement" touching the shared instruction emulator used by WHPX. — [Patchew, Paolo Bonzini pull request](https://patchew.org/QEMU/20260325172337.87212-1-pbonzini@redhat.com)

### Inferences
- On the Windows 10 tester's machine every guest interrupt-controller access, timer programming and inter-processor interrupt is handled by QEMU in user mode. For a 4-vCPU macOS guest that is a lot of extra exits and of contention on QEMU's global lock; the Windows 10 host should be expected to show higher host processor load and worse smoothness than Windows 11 for the same guest work. No published measurement of the size was found; the tester's own A/B numbers would be the first.
- `-M q35,pic=off` is the documented way to get the hypervisor's interrupt controller on Windows 10. Whether macOS boots with the legacy PIC removed (through OpenCore) is unknown and would need testing; it is a QEMU-side experiment, not a host setting.
- For a macOS guest the missing Hyper-V enlightenments probably matter less than the interrupt-controller location, because macOS does not natively use most Hyper-V interfaces. This is an assumption about the guest, not sourced.
- The Ryzen 7 5700X has no E-cores, so none of the hybrid issues apply; the Windows 10 legacy path is the main host-side difference for that tester. Upgrading that machine to Windows 11 would move it to the modern path, which is the largest single host-side change available to that tester, though its benefit is unmeasured.

### Gaps
- No benchmark comparing WHPX on Windows 10 versus Windows 11, or AMD versus Intel, was found.
- No authoritative list of AMD-specific WHPX defects exists in what was found; only the individual issues above.
- The QEMU 11.0 and 11.1 change logs were not retrieved, so which WHPX improvements landed in exactly which release is not established here.

## 10. Other hypervisor clients running at the same time, and nested hypervisors compared with WHPX

### Takeaway
VMware Workstation and VirtualBox both fall back to a slower mode that uses the same Windows Hypervisor Platform when the Windows hypervisor is active, and their vendors describe that as a performance loss without giving numbers; QEMU with WHPX is always in that position. No comparison numbers between those products and QEMU/WHPX were found.

### Cited Findings
- Documented by vendor: with the Windows hypervisor active, VMware Workstation loses direct hardware virtualization and runs with "increased CPU overhead", slower I/O and reduced responsiveness; Workstation 25H2 adds "Hyper-V/WHP Detection" to show which mode a VM is in. No magnitude given. — [Broadcom knowledge base 417896](https://knowledge.broadcom.com/external/article/417896/after-the-host-os-upgrade-to-version-win.html)
- Documented by vendor: since 2020 VMware Workstation's monitor can run at user level on the Windows Hypervisor Platform API, and that mode is used automatically when Hyper-V is enabled; it was presented as a compatibility feature, with no performance numbers. — [VMware Workstation blog](https://blogs.vmware.com/workstation/2020/05/vmware-workstation-now-supports-hyper-v-mode.html)
- Community documentation (not the official VirtualBox manual, which was not retrieved): VirtualBox shows a green turtle icon when Hyper-V or VBS forces its fallback mode, which "significantly reduces performance". — [Kicksecure wiki](https://www.kicksecure.com/wiki/VirtualBox/Green_Turtle_Issue)
- Documented: with the root scheduler the Windows scheduler "manages host resources on a global basis and doesn't manage the guest resources of individual VMs". — [Microsoft Learn, Manage Hyper-V hypervisor scheduler types](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/manage/manage-hyper-v-scheduler-types)

### Inferences
- WSL2, Docker Desktop, Windows Sandbox, the Android subsystem or emulator, and Hyper-V virtual machines all share the one hypervisor with QEMU. There is no documented mutual exclusion or special penalty; they simply compete for processor time and, above all, memory like any other heavy program. On a 16 GB host a running WSL2 or Docker virtual machine can take several gigabytes, which feeds straight into the memory-pressure risk in question 7. Advice: close them while the macOS VM runs; this is common sense, not a measured result.
- The fact that VMware and VirtualBox describe WHP mode as noticeably slower than their native monitors suggests WHP-based virtualization has a real overhead on device-emulation-heavy workloads (every exit goes through user mode). That overhead is inherent to QEMU/WHPX on Windows and cannot be tuned away from the host side, since no kernel-mode alternative to WHPX exists for QEMU on current Windows with the hypervisor enabled.

### Gaps
- No benchmark of VMware or VirtualBox in Hyper-V mode versus native, or versus QEMU/WHPX, from a reputable source was found (one 2026 comparison article had unverifiable sourcing and was discarded).
- No documentation found on interference between simultaneous WHP partitions.

## 11. Process priority and I/O priority for QEMU

### Takeaway
Raising QEMU to Above Normal is a no-admin, low-risk change that plausibly helps smoothness when the host is busy and may keep Windows' heuristics from treating it as background work, but there is no measurement and the forum evidence conflicts. High priority is discouraged by Microsoft for a process that can use all processor time, which a software-rendering guest does.

### Cited Findings
- Documented: `SetPriorityClass(hProcess, class)` needs only `PROCESS_SET_INFORMATION` on the handle. `ABOVE_NORMAL_PRIORITY_CLASS` is "above NORMAL_PRIORITY_CLASS but below HIGH_PRIORITY_CLASS". — [Microsoft Learn, SetPriorityClass](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-setpriorityclass)
- Documented warning: for `HIGH_PRIORITY_CLASS`, "Use extreme care when using the high-priority class, because a high-priority class application can use nearly all available CPU time." For `REALTIME_PRIORITY_CLASS`, threads "preempt the threads of all other processes, including operating system processes performing important tasks", and can "cause disk caches not to flush or cause the mouse to be unresponsive." — [Microsoft Learn, SetPriorityClass](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-setpriorityclass)
- Documented: priority feeds QoS heuristics: "threads running with reduced thread priority can imply a lower QoS level." — [Microsoft Learn, Quality of Service](https://learn.microsoft.com/en-us/windows/win32/procthread/quality-of-service)
- Documented: `PROCESS_MODE_BACKGROUND_BEGIN` lowers a process's "resource scheduling priorities" including disk and memory, and can only be set by the process on itself; "processes that interact with the user should not use" it. — [Microsoft Learn, SetPriorityClass](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-setpriorityclass)
- Documented: audio threads tagged by the Multimedia Class Scheduler Service get "Deadline" QoS, "High performance to meet media deadlines." — [Microsoft Learn, Quality of Service](https://learn.microsoft.com/en-us/windows/win32/procthread/quality-of-service)
- Hearsay, conflicting: some users say Above normal priority stops Windows pushing unfocused work to E-cores; another says setting High "didn't change the behavior". — [Folding@home forum](https://forum.foldingathome.org/viewtopic.php?p=358596); [ElevenForum thread](https://www.elevenforum.com/t/forcing-performance-mode-for-background-app-on-intel-p-e-core-cpu.15763/)
- Documented: QEMU's Windows-specific start-up code sets the timer resolution and a console handler only; it does not change its own priority class. — [QEMU source, os-win32.c](https://github.com/qemu/qemu/blob/master/os-win32.c)

### Inferences
- Because the root scheduler makes vCPUs ordinary Windows threads (question 2), process priority directly decides whether guest processors or other host programs win when the host is saturated. With 4 vCPUs busy on a 12-logical-processor laptop the host is rarely saturated, so Above Normal should change little in the common case and help mainly when something else (indexing, updates, a browser) competes.
- Risk on this project specifically: the host user relies on a screen reader. If QEMU's 4 busy vCPU threads outrank the screen reader and the audio stack, host speech can stutter or lag. Above Normal is the most that should be considered; High should not be used; Realtime additionally needs a privilege ordinary users lack. If Above Normal is tried, host speech responsiveness should be part of the test.
- A cleaner design than raising priority is to leave QEMU at Normal and rely on the explicit HighQoS tag from question 1, which addresses the documented throttling mechanism without changing who wins under contention.
- The launcher must not start QEMU at Below Normal or Idle, or in a job or mode that lowers priority, since reduced priority can itself imply a lower QoS level.

### Gaps
- No documentation or measurement on raising I/O priority for a VM process was found; normal is the default and the documented API surface only lowers it (background mode).
- Whether QEMU's Windows audio back ends register their threads with the Multimedia Class Scheduler Service was not checked in source.
- No measurement of guest audio smoothness versus QEMU priority class was found.
