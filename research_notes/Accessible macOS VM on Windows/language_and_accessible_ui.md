## 1. Language comparison for a wx-based app: Rust + wxDragon vs C++ + wxWidgets vs other bindings

### Takeaway
Only two compiled routes to wx are credible in 2026: **C++ with wxWidgets directly** (complete API, including every accessibility hook) and **Rust with wxDragon 0.9.x** (actively released, bundles wxWidgets 3.3.3, already used by blind developers for screen-reader-first apps, but pre-1.0 with recent breaking changes and memory-safety fixes). Both need the same MSVC C++ toolchain plus CMake on Windows, so setup cost barely separates them; the front-end language has no effect on guest speed while QEMU/Hyper-V does the virtualisation.

### Inferences
- **Accessibility parity.** wxDragon statically links the same wxWidgets 3.3.3 C++ code, so every native-control behaviour in section 2 is identical in Rust and C++. The differences are (a) which wx classes the binding wraps, (b) whether full `wxAccessible` subclassing (overriding `GetChildCount/GetChild/Navigate` for custom child elements) is reachable from Rust — the release notes mention only property setters and a "support wrapper", and (c) lag: new wx accessibility APIs (e.g. `SetAccessibleName`, `EnableFocusFromKeyboard`) arrive in C++ the moment they are merged, and in wxDragon only after the binding adopts 3.3.4 and wraps them (issue #229 is still open with no reply).
- **Setup cost on this machine (no C/C++ compiler, no Rust).** C++ route: VS 2022 Community or Build Tools with the VCTools workload + CMake (+ vcpkg, or prebuilt wx binaries). Rust route: all of that **plus** rustup, Ninja and possibly LLVM/libclang, because wxDragon compiles a C++ wrapper and (per downstream READMEs) often wxWidgets itself. So Rust is a superset of the C++ setup, not an alternative to it. All pieces can be installed from the command line (winget, rustup-init), which is the most screen-reader-friendly path; this is inferred from the documented silent-install options rather than from a blind user's report.
- **Guest VM speed.** When orchord launches QEMU (or Hyper-V) as an external process, the guest's CPU, memory and device emulation run entirely inside that process and the Windows hypervisor; the front end only spawns it and exchanges small JSON messages over QMP. The front-end language therefore has **no measurable effect on guest speed**, only on the manager's own startup time, memory use and UI latency. Language starts to matter only if the project embeds its own virtual machine monitor in-process (WHP `WHvRunVirtualProcessor` loop plus device models): guest code still runs natively under the hypervisor, but every VM exit and emulated-device access runs in the VMM's language, so a compiled language without a runtime pause (Rust or C++, as crosvm demonstrates for Rust) is then required. This is reasoning from the architecture documented in the WHP docs, not a benchmark.
- **Non-UI work favours Rust's package ecosystem.** Rust has a ready QMP crate, tokio for child-process and socket supervision, and the official `windows` crate for Win32/UIA/WHP. In C++ each of these is a separate library choice (wx's own process/socket classes, or vcpkg packages) and QMP must be hand-written over a JSON library. Background knowledge not verified in this session: Rust crates such as `reqwest` (resumable HTTP with range requests) and `fatfs` (FAT image creation) exist; wxWidgets has `wxWebRequest` for async HTTP with progress.
- **Reducing Rust error noise** (background knowledge, not sourced here): `cargo build --message-format=short` prints one line per diagnostic (`file:line:col: error[E…]: message`), which removes the ASCII-art decoration the blind NVDA user complained about; MSVC diagnostics are already single-line `file(line,col): error Cxxxx: …`.
- Paperback's repository carries a "cpp" topic tag, which suggests it was originally a C++ wxWidgets program before moving to Rust/wxDragon; this history was not confirmed.

## 2. Screen-reader behaviour of each wx control on Windows, and which to prefer

### Takeaway
Prefer wx classes that are thin wrappers over real Win32 controls (`ListBox`, `SysListView32`, `SysTreeView32`, `ComboBox`, `Edit`, `Button`, `msctls_*`), create a `wxStaticText` label immediately before each control, and avoid the generic composites (`wxDataViewCtrl`, `wxSpinCtrlDouble`, `wxFilePickerCtrl`, `wxInfoBar`, `wxListbook`) unless tested. For the VM list use `wxListBox` (one line per VM) or a report-mode `wxListCtrl` (columns); hand-roll the wizard on `wxDialog` + `wxSimplebook` rather than `wxWizard`.

### Cited Findings
- General rule from a wx maintainer-adjacent source: "For most widgets wx uses the native Windows controls", and "It's important that e.g. a StaticText as label for a text input is created right before the text input"; standalone StaticText is not reached by keyboard navigation and a read-only TextCtrl may be skipped. — [discuss.wxpython: Creating NVDA accessible applications (Sept 2025)](https://discuss.wxpython.org/t/creating-nvda-accessible-applications/40334)
- Why creation order matters: via MSAA "edit fields attempt to retrieve their name from their parent by asking about the static text directly to the left"; "only edit control and comboboxes are retrieving their label from the parent". — [wx ticket #19222 via wx-dev (c. 2021, pre-2023, possibly outdated)](https://groups.google.com/g/wx-dev/c/nEaCaK6vHZU)
- wx's own header docs: screen readers use the window's label by default, and for controls such as wxTextCtrl the text of the label preceding it. — [wx-dev thread for PR #27056](https://groups.google.com/g/wx-dev/c/tLjR-EqDP_M)
- Win32 classes in wxWidgets 3.3.3 (Local probe): `wxListBox` → `ListBox`; `wxListCtrl` (report) → `SysListView32`; `wxTreeCtrl` → `SysTreeView32`; `wxChoice` and read-only `wxComboBox` → `ComboBox`; `wxCheckBox` and `wxRadioBox` → `Button`; `wxTextCtrl` multiline read-only → `Edit`; `wxSlider` → `msctls_trackbar32`; `wxGauge` → `msctls_progress32`; `wxSpinCtrl` → `msctls_updown32` (with buddy edit); `wxStatusBar` → `msctls_statusbar32`; `wxNotebook` → `_wx_SysTabCtl32`; `wxWizard` → `#32770` (standard dialog). Generic wx-drawn/composite windows (`wxWindowNR`): `wxDataViewListCtrl` (inner window class `wxDataView`), `wxSpinCtrlDouble`, `wxFilePickerCtrl`/`wxDirPickerCtrl`, `wxInfoBar`, `wxListbook`. For all the native ones `GetOrCreateAccessible()` returns nothing, i.e. Windows' own MSAA/UIA proxy is what the screen reader sees. — Local probe; class reference [wxAccessible docs](https://docs.wxwidgets.org/3.3/classwx_accessible.html)
- **wxDataViewCtrl / wxDataViewListCtrl (verified locally, 3.3.3):** it is not a native list. wx supplies its own accessible object: control role = list, **name = the default window name `"dataviewCtrl"`**, description `"dataviewCtrl (2 items)"`; each row is a list item whose **name is the first column's text** and whose **description is `"State: Stopped"`** (remaining columns as "Header: value"), states focusable/selectable. So rows are exposed, but column data is in the description, not as table cells. — Local probe
- wxDataViewCtrl accessibility history: accessible classes were added in 2016, with follow-up fixes for a destructor assert under JAWS and for `GetName()/GetDescription()` (pre-2023, possibly outdated). — [wx commit: JAWS assert fix](https://git.amebis.si/Amebis/wxWidgets/src/commit/095c95852551444cd04411714fc0a1793640696b); [wx commit: GetName/GetDescription fix](https://git.amebis.si/Amebis/wxWidgets/src/commit/dbb2781199c892e5dbf49d38abc48336b104dd21)
- **wxSpinCtrlDouble** has no accessible name even with a static text to its left, because an extra `ROLE_SYSTEM_CLIENT` window named "wxSpinCtrlDouble" encloses the edit and spin button; a plain `wxSpinCtrl` gets its label correctly; the ticket says a wxAccessible workaround is not possible (c. 2021, pre-2023, possibly outdated — but the local probe confirms `wxSpinCtrlDouble` is still a generic `wxWindowNR` composite in 3.3.3). — [wx ticket #19222](https://groups.google.com/g/wx-dev/c/nEaCaK6vHZU)
- **wxCheckBox / wxRadioButton + dark mode:** with dark mode enabled in 3.3.1, checkboxes became owner-drawn (`BS_OWNERDRAW` replacing `BS_CHECKBOX`), so NVDA and Narrator announced "button" with no checked state. Maintainer's first advice was not to use dark mode when accessibility matters; fixed by commit "Fix wxCheckBox and wxRadioButton accessibility in wxMSW dark mode" (in 3.3.2), with follow-ups "Fix accessible label of checkboxes broken by recent changes" and "Remove mnemonics from accessible labels of controls" (regression fix #26270 in 3.3.3). — [wxWidgets issue #26184](https://github.com/wxWidgets/wxWidgets/issues/26184); [wxWidgets news 3.3.3](https://www.wxwidgets.org/news/2026/07/wxwidgets-3.2.11-and-3.3.3-released/)
- In 3.3.3 a `wxCheckBox` now carries a wx accessible object even in light mode, reporting the label without the `&` mnemonic ("Boot machine after setup completes") and deferring role/state to the system. — Local probe
- **wxCheckListBox:** wxWidgets 3.3.2 gave it its own MSAA implementation that sends state-change events itself (NVDA had to remove its own notifier to stop double announcements); but in 3.3.3 it "reports no child items to MSAA", so without a custom accessible "object navigation can't reach items, position info (such as '1 of 3') is lost, every item is reported as focused, and none as selected". NVDA keeps its own `ListCtrlAccessible`. — [NVDA PR #20882](https://github.com/nvaccess/nvda/pull/20882)
- **wxListBox vs combo boxes:** NVDA's own developers proposed list boxes over combo boxes where the user just moves through entries and activates one. — [NVDA issue #6100](https://github.com/nvaccess/nvda/issues/6100)
- **wxFilePickerCtrl / wxDirPickerCtrl** are a generic container holding a `TextCtrl` and a `Button` labelled "Browse" (Local probe). NVDA's GUI code does not use them; it has `PathSelectionHelper`, "a textCtrl with a button in horizontal layout". — Local probe; [NVDA guiHelper.py](https://raw.githubusercontent.com/nvaccess/nvda/master/source/gui/guiHelper.py)
- **wxWizard (source, master):** buttons are created so that "Desired TAB order is 'next', 'cancel', 'help', 'back'"; default labels are `"&Next >"`, `"< &Back"`, `"&Cancel"`, `"&Finish"`, `"&Help"`; on each page change `ShowPage` calls `m_page->Show(); m_page->SetFocus();`, re-labels Next to Finish on the last page, calls `m_btnNext->SetDefault()` and disables Back on the first page. **Nothing changes the window title or sends any accessibility event on page change.** Cancel goes through `wxEVT_WIZARD_CANCEL` then `EndModal(wxID_CANCEL)`. — [wxWidgets src/generic/wizard.cpp](https://raw.githubusercontent.com/wxWidgets/wxWidgets/master/src/generic/wizard.cpp)
- Local probe of a bare `wxWizard`: children in creation order are a static line, `&Next >`, `&Cancel`, `< &Back`. — Local probe
- **wxSlider:** NVDA's `EnhancedInputSlider` adds arrow/page/Home/End handling and manually fires a win event because "Win events don't seem to be sent for certain explicitly set values". — [NVDA nvdaControls.py](https://raw.githubusercontent.com/nvaccess/nvda/master/source/gui/nvdaControls.py)
- **wxSpinCtrl:** NVDA uses `SelectOnFocusSpinCtrl` (selects the value on focus so typing replaces it). — [NVDA nvdaControls.py](https://raw.githubusercontent.com/nvaccess/nvda/master/source/gui/nvdaControls.py)
- **wxRadioBox / wxRadioButton:** a wx test suite notes "Space may not work reliably - use Arrow keys instead"; arrows both move and select; Tab leaves the group. That suite lists expected announcements only and records no verified per-screen-reader results. — [accesswatch/wx-accessibility-test-suite (Oct 2025)](https://github.com/accesswatch/wx-accessibility-test-suite)
- **wxGauge / progress bars in NVDA:** output mode is off / beep / speak / both; updates from a non-foreground window are ignored unless "report background progress bars" is on; beep pitch is `beepMinHZ * 2 ** (percentage / 25.0)` for 40 ms each time the value moves by at least the beep interval; speech is the text "%d percent" at the speech interval; braille is updated on every change. — [NVDA behaviors.py](https://raw.githubusercontent.com/nvaccess/nvda/master/source/NVDAObjects/behaviors.py)
- Indeterminate progress bars are silent in NVDA; NVDA's own installer plays a sound itself. — [GnuPG Kleopatra ticket T7946](https://static.dev.gnupg.org/T7946.html)
- **Dialogs:** NVDA builds a dialog's spoken description from its static text, labels and read-only single-line edits when the dialog has no description. — [NVDA behaviors.py](https://raw.githubusercontent.com/nvaccess/nvda/master/source/NVDAObjects/behaviors.py)
- **wxStatusBar and wxListCtrl** get explicit accessibility support only in the unreleased 3.3.4 (#24305, #15411); **wxInfoBar** TAB navigation and announcements were fixed after 3.3.3. — [changes.txt](https://raw.githubusercontent.com/wxWidgets/wxWidgets/master/docs/changes.txt); [wxDragon issue #229](https://github.com/AllenDang/wxDragon/issues/229)
- Historical regression worth knowing: in wxPython 4.0.4–4.0.7 NVDA and Narrator announced generic names such as "choice" or "check" instead of labels when wx attached its own IAccessible and the control's `name` was empty (2019–2020, pre-2023, possibly outdated). — [Phoenix issue #1129](https://github.com/wxWidgets/Phoenix/issues/1129); [discuss.wxpython thread](https://discuss.wxpython.org/t/screen-readers-not-reading-field-labels-in-wx-python-4-0-4/34439)

### Inferences
- **VM list:** `wxListBox` (class `ListBox`) is the lowest-risk control: one string per VM such as "Sequoia test, stopped", read natively by every screen reader with position information. If columns (name, state, macOS version) are wanted, use report-mode `wxListCtrl` (`SysListView32`), which Windows exposes as a real list view; put the most identifying text in column 0. Do not use `wxDataViewListCtrl`: it is wx-drawn, its control name defaults to "dataviewCtrl" unless the window name is set, and column values are only in the item description (which NVDA may not speak depending on the user's description setting). `wxListView` is only a convenience subclass of `wxListCtrl`, so its accessibility is identical (background knowledge).
- **Numbers (RAM/CPU/disk):** use integer `wxSpinCtrl` with a preceding label that carries the unit ("Memory (GB):"), never `wxSpinCtrlDouble`. A plain `wxTextCtrl` with validation is an equally safe alternative and is what to fall back to if a spin control misreports. A `wxSlider` needs the NVDA-style win-event workaround and conveys no unit, so it is the weakest choice for these values. How each screen reader announces value and unit was not observed.
- **Choices:** `wxChoice` (drop-down list) for macOS version and similar closed sets; avoid editable `wxComboBox`. For 2–3 mutually exclusive options either `wxRadioBox` (native group box plus radio buttons) or a `wxChoice`; NVDA's own leaning is toward lists.
- **Paths:** build "label + `wxTextCtrl` + `Browse…` button" by hand (as NVDA does) so the static-text label directly precedes the edit; inside `wxFilePickerCtrl` the edit's parent is the picker's own container, so the label-to-the-left lookup may fail.
- **Summary page / logs:** multiline read-only `wxTextCtrl` (`Edit` class) is a native control the user can arrow through; read-only **single-line** fields are not tabbable on MSW until `EnableFocusFromKeyboard()` (3.3.4).
- **Wizard:** hand-roll it. `wxWizard` gives no title change and no announcement on page change, and its button labels contain literal `<` and `>` characters that screen readers may speak as symbols. A `wxDialog` with a `wxSimplebook` (wrapped by wxDragon; `wxWizard` is not) lets the app set the title to e.g. "New Virtual Machine — step 2 of 4: macOS version", label buttons "Back"/"Next"/"Finish", and move focus to the first control of the new page so the screen reader reads title/context plus that control. Keep "Boot machine after setup completes" as a plain `wxCheckBox` on the last page, before Finish in tab order.
- **Settings dialog:** `wxNotebook` (native tab control, Ctrl+Tab/Ctrl+PageDown behaviour comes from Windows) over `wxListbook` (generic composite).
- **Status and transient info:** do not rely on `wxStatusBar` or `wxInfoBar` being read; neither takes focus, and explicit accessibility for them only arrives in 3.3.4. Speak important changes explicitly (section 4) and keep the status bar as a place the user can query.
- **Help text:** no source was found on `wxHtmlWindow` or `wxWebView` accessibility; a read-only multiline text control or opening the documentation in the user's browser avoids the question.
- **Message boxes:** `wxMessageDialog` maps to the system message box on Windows and is read as a normal dialog (background knowledge); `wxProgressDialog` was not verified — a custom dialog with a `wxGauge`, a status text and a Cancel button is fully under the app's control.

### Gaps
- No direct NVDA/JAWS/Narrator speech transcripts were obtained for any control; everything above is from source code, issue trackers and the structural probe. JAWS and Narrator evidence in particular is nearly absent.
- No NVDA issue specifically documenting `wxDataViewCtrl` behaviour was found; the "poorly accessible" reputation is supported here only by the structural probe.
- Whether NVDA table navigation (Ctrl+Alt+arrows) works in wx report-mode `wxListCtrl`, and how virtual-mode lists behave, was not verified.
- `wxHtmlWindow`, `wxWebView`, `wxProgressDialog`, `wxListbook` and `wxInfoBar` behaviour with screen readers: no sources found.
- The exact scope of "Accessibility support in wxListCtrl (#15411)" in 3.3.4 (native vs generic list control) was not checked.

## 3. Keyboard design

### Takeaway
Use native menu accelerators and `&` mnemonics for everything, give every action a menu item, and treat announcements after menu commands as a timing problem. Ctrl+P for configuration is used by none of the comparable VM managers found; there is no single convention (VirtualBox Ctrl+S, VMware Ctrl+D, Hyper-V Ctrl+O).

### Cited Findings
- VirtualBox Manager: Ctrl+S opens Settings for the selected VM, Ctrl+N creates a new VM, Ctrl+D opens the virtual media manager, Ctrl+G opens preferences. — [VirtualBox shortcut cheat sheet](https://maketecheasier.com/cheatsheet/virtualbox-keyboard-shortcuts/)
- VMware Workstation: Ctrl+D "Edit the Virtual Machine Settings" (old source, pre-2023, possibly outdated; not confirmed in the Workstation 17 hot-key table, which documents the menu path VM > Settings). — [How-To Geek](https://www.howtogeek.com/135/keyboard-shortcuts-for-vmware-workstation/)
- Hyper-V Virtual Machine Connection: Ctrl+S starts the VM, Ctrl+O opens VM settings, Ctrl+N creates a checkpoint, Ctrl+Alt+End sends Ctrl+Alt+Del. — [Microsoft: Hyper-V Virtual Machine Connection](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/virtual-machine-connection)
- UTM: only the preferences shortcut (Cmd+,) is documented in the page found; no per-VM edit shortcut was found. — [UTM docs](https://docs.getutm.app/preferences/macos/)
- hn-blind's design rule: "Everything is keyboard driven, and every command is also on the menu bar." — [hn-blind README](https://github.com/garo-pro/hn-blind)
- Menu labels carry shortcuts as wx accelerators, so a handler cannot tell a key press from a menu click; Paperback added a frame-level `CHAR_HOOK`, which "runs before the accelerator table", to mark keyboard-originated commands. — [Paperback PR #943](https://github.com/trypsynth/paperback/pull/943)
- After a menu command or dialog closes, NVDA runs a focus-return chain (window title, etc.) that talks over an announcement made at the same moment; Paperback delays such announcements ~30 ms after a dialog and 100 ms after a popup menu, announces immediately for direct shortcuts, and notes the timing is machine-dependent. Re-targeting focus does not avoid the chain. — [Paperback PR #943](https://github.com/trypsynth/paperback/pull/943)
- NVDA handles Space on its checkable list via `EVT_CHAR_HOOK` and sends a win event so the state change is announced. — [NVDA nvdaControls.py](https://raw.githubusercontent.com/nvaccess/nvda/master/source/gui/nvdaControls.py)
- NVDA's dialog helper places dismiss buttons last ("These buttons are expected to be the last items added to the dialog"). — [NVDA guiHelper.py](https://raw.githubusercontent.com/nvaccess/nvda/master/source/gui/guiHelper.py)
- On MSW the order in which controls are created determines TAB order. — [wizard.cpp comment](https://raw.githubusercontent.com/wxWidgets/wxWidgets/master/src/generic/wizard.cpp)
- `MoveAfterInTabOrder` and `wxDialog::SetEscapeId` are present in the 3.3.3 build. — Local probe
- wxWidgets fixed (after 3.3.3) an IME issue where Escape in a dialog with IME candidate windows closed the dialog. — [NVDA PR #20882 comment](https://github.com/nvaccess/nvda/pull/20882)

### Inferences
- **Ctrl+P.** It does not clash with anything in an app that has no Print command, and "P for properties" is memorable, but users will not have learned it elsewhere. Background knowledge (not sourced in this session): the Windows-wide convention for "properties of the selected item" is **Alt+Enter**. A safe design is a menu item "Machine > Settings…\tCtrl+P" with Alt+Enter as a second accelerator, and the same command in the context menu, so discovery never depends on the shortcut.
- **Enter on the list.** For `wxListCtrl` use the native activation event (`EVT_LIST_ITEM_ACTIVATED`, fired on Enter and double-click); `wxListBox` only has a double-click event, so Enter must be caught with a key/char-hook handler on the list. Do not make "Boot" the dialog default button on a frame — bind Enter on the list itself (background knowledge of wx behaviour; not verified here).
- **Context menu.** Handle `EVT_CONTEXT_MENU` (Windows raises it for Shift+F10 and the Applications key as well as right-click) and position the menu at the selected item when the event has no mouse position (background knowledge).
- **Dialogs.** Create controls in reading order (label, control, label, control, …, buttons last) so that creation order = tab order = label association. Give OK/Next `SetDefault()`, give Cancel `wxID_CANCEL` so Escape closes, and set initial focus explicitly to the first input.
- **Mnemonics.** Every menu item and every button/label gets a unique `&` letter within its menu or dialog. Since 3.3.3 strips mnemonics from accessible names, `&` no longer pollutes what is read.
- **No focus traps.** Avoid multiline text controls that swallow Tab; ensure radio groups are left with Tab.
- **Speaking after commands.** Adopt Paperback's pattern from the start: one `announce_for_command(from_keyboard, msg)` helper, immediate for shortcuts, delayed for menu-originated commands and post-dialog announcements, and fold two consecutive messages into one.

### Gaps
- No authoritative, current list of VMware Workstation 17 or UTM shortcuts for "edit VM settings" was found.
- The Alt+Enter convention and the `EVT_CONTEXT_MENU` keyboard behaviour are background knowledge, not verified from documentation in this session.
- JAWS and Narrator behaviour for the focus-return chain is unknown (Paperback tested NVDA on Windows 11 only).

## 4. Speaking custom messages from Rust or C++

### Takeaway
Let native controls speak for themselves and reserve live speech for transient status. The most current mechanisms are (1) UI Automation notification events raised from a real provider attached to the app's window (proven with NVDA in Rust by the `live-region` crate) and (2) Prism, the 2026 successor to Tolk/SRAL, for direct speech and braille; the NVDA controller client is a solid NVDA-only fallback. Tolk, SRAL, accessible_output2/3 and cytolk are stale or archived.

### Cited Findings

**UI Automation notification events**
- `HRESULT UiaRaiseNotificationEvent(IRawElementProviderSimple *provider, NotificationKind, NotificationProcessing, BSTR displayString, BSTR activityId)`; `Uiautomationcore.dll`; Windows 10 version 1709 or later. — [Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/api/uiautomationcoreapi/nf-uiautomationcoreapi-uiaraisenotificationevent)
- The object returned by `UiaHostProviderFromHwnd` cannot be used to raise events; "you must create a provider object that fully implements the IRawElementProviderSimple interface". — [Microsoft Learn: UiaHostProviderFromHwnd](https://learn.microsoft.com/en-us/windows/desktop/api/uiautomationcoreapi/nf-uiautomationcoreapi-uiahostproviderfromhwnd)
- `live-region` (Rust, MIT, for wxDragon apps) does exactly that: an `Announcer { hwnd }` struct with `#[implement(IRawElementProviderSimple)]` (`windows` crate) returning `ServerSideProvider | UseComThreading`, `E_NOTIMPL` for patterns, empty `VARIANT` for properties (so UIA falls back to the host provider) and `UiaHostProviderFromHwnd` for `HostRawElementProvider`. It installs `SetWindowSubclass` on the window and answers `WM_GETOBJECT` with `lparam == UiaRootObjectId` via `UiaReturnRawElementProvider`; cleans up on `WM_NCDESTROY`. Its comment on the shortcut: raising on the host provider "returns `S_OK` and reaches no UIA client at all." It checks `UiaClientsAreListening` and returns `false` if nothing is listening. — [live-region windows.rs](https://raw.githubusercontent.com/trypsynth/live-region/master/src/windows.rs)
- Priority mapping used there: Low → `NotificationProcessing_All` (queued), Medium → `NotificationProcessing_CurrentThenMostRecent` (current utterance finishes, staler ones dropped), High → `NotificationProcessing_ImportantMostRecent` (interrupts); kind `NotificationKind_Other`; empty activity id. NVDA verified: it cancels speech for `ImportantMostRecent`/`MostRecent`, except during say-all. "JAWS and Narrator honour the same UIA contract but their exact behaviour is untested here." Messages are sanitised (control characters removed, whitespace collapsed, truncated to 512 characters). — [live-region lib.rs](https://raw.githubusercontent.com/trypsynth/live-region/master/src/lib.rs)
- Why not an MSAA live region: its politeness is "one setting on the window", so one announcement cannot carry its own priority. — [live-region windows.rs](https://raw.githubusercontent.com/trypsynth/live-region/master/src/windows.rs)
- Alternative attachment used by OSARA (REAPER, C++): a zero-size, disabled but shown child window carries the provider; hiding it made `UiaRaiseNotificationEvent` fail; attaching to the main window did not work there (2019, pre-2023, possibly outdated). — [OSARA PR #198](https://github.com/jcsteh/osara/pull/198)
- NVDA added UIA notification handling in PR #8045; its base handler speaks whatever notification it receives. By default NVDA ignores notifications whose source is not the focused application. — [NVDA PR #8045](https://github.com/nvaccess/nvda/pull/8045); [NVDA issue #16862](https://github.com/nvaccess/nvda/issues/16862)
- Win32 live-region alternative: `NotifyWinEvent(EVENT_OBJECT_LIVEREGIONCHANGED, hwnd, OBJID_CLIENT, CHILDID_SELF)` on a window marked as a live region (pre-2023 Microsoft blog, possibly outdated). — [Microsoft UIA blog](https://learn.microsoft.com/en-us/archive/blogs/winuiautomation/how-to-have-important-changes-in-your-win32-ui-announced-by-narrator)

**wxAccessible / MSAA**
- `wxAccessible` is MSAA-only on MSW; `NotifyEvent(eventType, window, objectType, objectId)` lets the app signal changes (the build exposes the full `wxACC_EVENT_OBJECT_*` set including NAMECHANGE, VALUECHANGE, STATECHANGE and `wxACC_EVENT_SYSTEM_ALERT`). — [wxAccessible docs](https://docs.wxwidgets.org/3.3/classwx_accessible.html); Local probe
- NVDA itself calls `NotifyWinEvent` directly after programmatic changes "so that NVDA receives a stateChange". — [NVDA nvdaControls.py](https://raw.githubusercontent.com/nvaccess/nvda/master/source/gui/nvdaControls.py)

**Direct screen-reader output libraries**
- **Prism** (ethindp): "the Platform-agnostic Reader Interface for Speech and Messages", aims to unify SpeechCore, UniversalSpeech, SRAL and Tolk and also drives TTS engines; MPL-2.0; Windows 10+; bindings listed: Rust `prismer` (crates.io), .NET `prismatoid` (NuGet), Python `prismatoid` (PyPI, 0.18.3, requires Python ≥ 3.10, Windows wheels), Godot, Tauri; "bindings are an in-progress effort"; JAWS backend is a build option (`PRISM_ENABLE_JAWS_BACKEND`); 402 commits, no tagged releases. — [Prism README](https://github.com/ethindp/prism); [PyPI prismatoid](https://pypi.org/project/prismatoid/)
- hn-blind uses Prism through a different Rust binding (`garo-pro/prism2rust`) and reports that `prism-sys` needs **C++23**; it uses Prism for transient status and stays quiet on focus movement when a screen reader is the active backend. — [hn-blind README](https://github.com/garo-pro/hn-blind)
- **SRAL** (m1maker): archived and read-only; the author recommends Prism, citing "architectural problems"; supported NVDA, JAWS, ZDSR, Narrator, UIA and SAPI; MIT. — [SRAL README](https://github.com/m1maker/SRAL)
- **Tolk** (dkager): Windows DLL abstracting NVDA, JAWS, SAPI etc.; LGPLv3; repository last updated 8 June 2024. Rust crates: `tolk` 0.5.0 (May 2021), `tolk-sys` 0.2.2 (Dec 2020, Rust 2015 edition) (pre-2023, possibly outdated). The Rust `tts` crate offers a Tolk feature and a WinRT backend. — [dkager/tolk](https://github.com/dkager/tolk); [lib.rs tolk](https://lib.rs/crates/tolk); [lib.rs tolk-sys](https://lib.rs/crates/tolk-sys); [docs.rs tts](https://docs.rs/tts)
- **NVDA controller client** (`nvdaControllerClient.dll`): LGPL 2.1 ("you can use the library in any application", changes to the library itself must be contributed back). API 2.0 arrived in NVDA 2024.1 (`nvdaController_getProcessId`, `nvdaController_speakSsml`); API 3.0 in NVDA 2026.3 (`nvdaController_isSpeaking`); older NVDA returns error 1717 (`RPC_S_UNKNOWN_IF`). Functions return 0 on success. Use the DLL matching the process architecture. Security note: check whether Windows is locked or on a secure screen before speaking sensitive text. Examples in the repo cover Python, C, C# and **Rust** (a workspace with `nvda-bindgen` generating bindings from `nvdaController.h` and an `nvda` crate — a repository example, not a crates.io package). — [NVDA controllerClient readme](https://github.com/nvaccess/nvda/blob/master/extras/controllerClient/readme.md); [NVDA commit adding the Rust example](https://app.semanticdiff.com/gh/nvaccess/nvda/commit/021c13da5d78bdb725cc4fcb906f9141e701e3de)
- Python-only, for reference: accessible_output2 0.17 (PyPI, 9 July 2022, MIT); accessible_output3 0.1.2 (16 March 2023, MIT); cytolk 0.1.13 (12 Nov 2023, MIT wrapper over LGPL Tolk). All stale on PyPI. — [PyPI accessible-output2](https://pypi.org/project/accessible-output2/); [PyPI accessible-output3](https://pypi.org/project/accessible-output3/); [PyPI cytolk](https://pypi.org/project/cytolk/)

### Inferences
- **When to speak.** Never speak what focus already conveys (control names, values, list items) — the user would hear it twice, and braille users get it from the control. Speak only things with no focus change: "Download complete", "Sequoia test started", errors from background jobs, wizard validation failures. hn-blind's rule is the model: with a screen reader active, native controls own focus speech and the app adds only transient status.
- **Recommended layering for orchord (Rust or C++):** primary = UIA notification events via an `IRawElementProviderSimple` attached to the main frame by subclassing `WM_GETOBJECT` (works for NVDA, and by API contract for Narrator and JAWS; reaches braille through the screen reader; no DLL to ship). In Rust this is the `live-region` crate as-is; in C++ it is roughly 100–150 lines of COM implementing the same four methods. Fallback/complement = NVDA controller client (direct, NVDA-only, LGPL DLL shipped beside the exe) or Prism for JAWS/SAPI coverage.
- **Background limitation.** Because NVDA drops UIA notifications from non-focused apps by default, "download finished" while the user is in another window will not be spoken via UIA; use a toast (`wxNotificationMessage`) and/or the controller client or Prism for that case.
- **Licensing for an open-source project:** Prism MPL-2.0 (file-level copyleft), Tolk LGPLv3 and the NVDA client LGPL 2.1 are all usable via dynamic linking; `live-region` and wxDragon are MIT/Apache.
- Prism's Rust story is unsettled (README names `prismer`, a 2026 app uses `prism2rust`, and a web search could not confirm `prismer` on crates.io) and its native build needs C++23, i.e. a current MSVC. Prism's C API can be consumed directly from C++.
- `wxAccessible::NotifyEvent` with NAMECHANGE/VALUECHANGE is the lightweight way to make NVDA re-read a control whose text the app changed (e.g. a status label that has focus); it is not a general "say this" channel.

### Gaps
- Which Windows backends Prism ships (NVDA, JAWS, SAPI, OneCore, UIA, ZDSR, Narrator) is not stated on the README fetched; the latest release date of each binding was not obtained.
- The NVDA controller client's full function list and the speech-priority/symbol-level enums live in `nvdaController.h`, which was not read.
- JAWS and Narrator handling of UIA notifications from a wx (non-UIA-native) window is untested in every source found.
- Maintenance state of accessible_output2 upstream on GitHub (as opposed to PyPI) was not established; TWBlue pins a specific git commit of it.

## 5. Accessible patterns for long-running operations (12+ GB downloads, disk image creation)

### Takeaway
Show a non-modal progress view with a real `wxGauge` (so NVDA's own beep/speech settings apply), a text line the user can read on demand, and a Cancel button; never move focus when progress changes; add explicit, low-frequency announcements only for milestones and completion.

### Cited Findings
- NVDA's progress handling is user-configurable (off/beep/speak/both), is silent for background windows unless the user enables background reporting, beeps with rising pitch per interval, and speaks "N percent" per speech interval; it needs a determinate value. — [NVDA behaviors.py](https://raw.githubusercontent.com/nvaccess/nvda/master/source/NVDAObjects/behaviors.py)
- Indeterminate ("busy") bars are completely silent in NVDA, and a bar with only a few discrete states leaves NVDA "silent for quite a while without indication that [the app] is busy" — so expose frequent, continuous value updates. — [Kleopatra ticket T7946](https://static.dev.gnupg.org/T7946.html)
- An NVDA change made indeterminate progress dialogs beep on completion only if progress-bar output includes beeps (2017, pre-2023, possibly outdated). — [NVDA PR #6776](https://app.semanticdiff.com/gh/nvaccess/nvda/pull/6776/overview)
- `wxGauge` is the native `msctls_progress32` in 3.3.3. — Local probe
- UIA notification priorities give the needed politeness levels: Low queues, Medium replaces staler messages after the current utterance, High interrupts. — [live-region lib.rs](https://raw.githubusercontent.com/trypsynth/live-region/master/src/lib.rs)
- NVDA ignores UIA notifications from an app that is not focused. — [NVDA issue #16862](https://github.com/nvaccess/nvda/issues/16862)
- Two announcements deferred at the same moment can cut each other off; fold them into one message. — [Paperback PR #943](https://github.com/trypsynth/paperback/pull/943)
- NVDA's GUI keeps wx calls on the GUI thread with helpers `wxCallOnMain` (run on GUI thread and block for the result) and `alwaysCallAfter` (decorator that schedules on the GUI thread). — [NVDA guiHelper.py](https://raw.githubusercontent.com/nvaccess/nvda/master/source/gui/guiHelper.py)
- hn-blind keeps all wx linkage in `main.rs` so non-GUI modules are unit-testable. — [hn-blind README](https://github.com/garo-pro/hn-blind)
- `wxNotificationMessage` exists in 3.3.3 and is wrapped by wxDragon (`notification_message`). — Local probe; [docs.rs wxdragon::widgets](https://docs.rs/wxdragon/latest/wxdragon/widgets/index.html)

### Inferences
- **Layout of the progress view:** label + `wxGauge` (range 0–1000 or bytes scaled, updated a few times per second so the percentage moves smoothly); a read-only multiline text control or list holding the current line, e.g. "Downloading macOS Sequoia installer: 4.2 of 13.1 GB, 32 percent, about 18 minutes remaining at 8.1 MB/s"; a Cancel button (Escape = Cancel, with a confirmation because cancelling a 12 GB download is costly); optionally "Run in background". Keep the app usable (non-modal) so the user can Tab away and back.
- **Announcement cadence:** let NVDA's own progress beeps/speech do the routine work (they follow the user's preferences). App-initiated speech only at start, on stage change (download → verify → create disk → done), on error, and on completion; if periodic spoken progress is offered, make it optional and coarse (for example every 10 percent or every few minutes) at Low/Medium priority so it never interrupts. Do not update the window title or a focused control's label several times a second.
- **Never steal focus** on progress or completion; on completion announce and (if the app is not focused) raise a toast. If a dialog must appear (failure), it is acceptable for it to take focus because it needs a decision.
- **Threading:** all wx calls stay on the main thread. Rust: run downloads, hashing, image creation and QEMU/QMP supervision on a tokio runtime or worker threads and marshal results back to the UI thread (the wx equivalent of `CallAfter`); C++: `wxThread`/`std::thread` plus `wxEvtHandler::CallAfter` or `wxQueueEvent` (background knowledge). Throttle UI updates to a few per second.
- **Earcons:** optional short sounds for start/finish/error help users who have progress speech off, but must be off-switchable and never the only signal.
- **Indeterminate phases** (e.g. "preparing disk image" with unknown length) are silent in NVDA, so announce the phase start and end explicitly, or convert to a determinate bar wherever a byte count is known.

### Gaps
- How NVDA, JAWS and Narrator announce Windows toast notifications raised via `wxNotificationMessage` was not researched.
- No source was found for `wxProgressDialog` accessibility.
- No published guidance specific to announcing time-remaining for multi-gigabyte downloads was found; the cadence above is a design inference.
- The exact wxDragon API for posting work back to the UI thread was not looked up.

## 6. Empty-state pattern for the VM list

### Takeaway
A single placeholder row is a reasonable pattern in a native list because an empty native list gives the user nothing to land on; make its text self-explanatory and make Enter on it do the obviously useful thing (open the New Virtual Machine wizard) rather than nothing.

### Cited Findings
- In web contexts screen readers announce empty lists ("Lists with 0 items") and the recommended fix is to hide the empty list and show a separate message; an empty-state guideline recommends moving focus to the heading or primary action when the empty state appears after a user action. — [WordPress Trac #32843 (2015, pre-2023, possibly outdated)](https://core.trac.wordpress.org/ticket/32843); [Compound design system: empty state accessibility](https://compound.thephoenixgroup.com/latest/components/components/empty-state/accessibility-6f5bOu7u-6f5bOu7u)
- In wx on Windows a standalone static text is not reached by keyboard navigation and is generally read only on mouse-over. — [discuss.wxpython thread](https://discuss.wxpython.org/t/creating-nvda-accessible-applications/40334)

### Inferences
- The web advice (replace the list with a message) does not transfer directly: in a wx frame a message in a `wxStaticText` is invisible to a keyboard/screen-reader user, and an empty `ListBox` announces only its name with nothing to arrow to. A placeholder item such as "No virtual machines. Press Enter or Control+N to create one." is therefore discoverable exactly where the user lands on start-up.
- Enter on the placeholder should open the wizard (the text promises it). Boot, Settings and Delete must be disabled for the placeholder (grey the menu items, and make Ctrl+P a no-op with a spoken "No virtual machine selected"). Keep a flag rather than testing the row text, and remove the placeholder the moment a real VM exists, re-selecting the new VM.
- The row count a screen reader reports will be "1 of 1" while empty; wording the item as a sentence makes it clear it is not a VM.

### Gaps
- No desktop-specific (Win32/MSAA) guidance or blind-user discussion of placeholder list items was found; this section is largely design reasoning.

## 7. High-contrast, dark mode and low-vision considerations

### Takeaway
Leave wx in its default light/system-colour mode for the first release: native controls then follow Windows high-contrast themes automatically, whereas wxWidgets' opt-in dark mode is still labelled experimental and has already broken screen-reader roles once (owner-drawn checkboxes in 3.3.1).

### Cited Findings
- Dark mode on Windows is opt-in via `wxApp::MSWEnableDarkMode()` (described as experimental) or `wxApp::SetAppearance()`; without opting in, `wxSystemAppearance::IsDark()` returns false even if the system is dark; use `IsSystemDark()`/`AreAppsDark()` to query the system. Environment variable `wx_msw_dark_mode=1` opts in, `=2` forces dark. — [wxSystemAppearance docs](https://docs.wxwidgets.org/3.3/classwx_system_appearance.html); [wxDarkModeSettings docs](https://docs.wxwidgets.org/3.3/classwx_dark_mode_settings.html)
- Dark mode support debuted in 3.3.0 (#23028); 3.3.1 fixed notebook background in dark **high contrast** themes (#25542) and several control renderings; 3.3.3 added dark-mode message boxes (#26570) and run-time light/dark switching (#26516); 3.3.4 continues with wxNotebook, wxSpinButton, common dialogs. — [changes.txt](https://raw.githubusercontent.com/wxWidgets/wxWidgets/master/docs/changes.txt)
- Dark mode made checkboxes owner-drawn and unreadable as checkboxes to NVDA/Narrator in 3.3.1; maintainer initially "recommended not using dark mode when accessibility matters"; fixed in 3.3.2 with a regression fix in 3.3.3. — [wxWidgets issue #26184](https://github.com/wxWidgets/wxWidgets/issues/26184)
- The developer machine reports `IsDark: False, IsSystemDark: False, AreAppsDark: False`. — Local probe
- NVDA carries its own `DPIScaledDialog` "until wxWidgets/wxWidgets#334 is resolved". — [NVDA nvdaControls.py](https://raw.githubusercontent.com/nvaccess/nvda/master/source/gui/nvdaControls.py)
- wxWidgets 3.3 changed the default look of some controls such as tree views. — [NVDA PR #20882](https://github.com/nvaccess/nvda/pull/20882)

### Inferences
- Do not hard-code colours or fonts anywhere; use sizers only (no absolute positions) so larger system fonts and text scaling reflow correctly; query `wxSystemSettings` if a colour is ever needed.
- If dark mode is offered later, make it follow the system (`SetAppearance(System)`), and re-test every checkbox, radio button and list with NVDA after each wx upgrade, because dark mode works by owner-drawing or re-theming native controls.
- Ship an application manifest declaring per-monitor-v2 DPI awareness (the usual wx requirement on Windows; background knowledge) so text is crisp for low-vision users with scaling above 100 percent.

### Gaps
- No source was found that tests wxWidgets 3.3 under Windows 11 contrast themes with a screen magnifier; high-contrast behaviour beyond the one notebook fix is undocumented.
- The DPI manifest requirement and wxDragon's manifest handling were not verified (wxDragon mentions an `msw.no-manifest-check` setting for its examples).

## 8. Accessibility testing

### Takeaway
Manual NVDA passes remain the ground truth, but structural checks can be automated cheaply: Paperback already asserts on what UI Automation reports in its Windows UI tests, and the in-process probe used for these notes shows what wx exposes without a screen reader running.

### Cited Findings
- Paperback's Windows UI tests "check what UI Automation reports, including what screen readers are told". — [Paperback README](https://github.com/trypsynth/paperback)
- A blind wxPython developer diagnosed missing labels by comparing output in Microsoft's `inspect.exe`. — [discuss.wxpython thread](https://discuss.wxpython.org/t/screen-readers-not-reading-field-labels-in-wx-python-4-0-4/34439)
- Guidepup drives NVDA on Windows (and VoiceOver on macOS) from JavaScript with one API; `@guidepup/setup --ci` and a `guidepup/setup-action` GitHub Action exist. — [Guidepup README](https://cdn.jsdelivr.net/npm/@guidepup/guidepup@0.24.1/README.md)
- `NvdaTestingDriver` (.NET, NuGet, 0.2.0-beta) starts a bundled portable NVDA, drives it, and returns the text NVDA would speak for comparison with expected text. — [NuGet: NvdaTestingDriver](https://www.nuget.org/packages/NvdaTestingDriver)
- NVDA controller client 3.0 adds `nvdaController_isSpeaking`, and 2.0 adds `nvdaController_getProcessId`. — [NVDA controllerClient readme](https://github.com/nvaccess/nvda/blob/master/extras/controllerClient/readme.md)
- `accesswatch/wx-accessibility-test-suite` (Oct 2025, MIT) is a wxPython app exercising about 60 wx controls with expected NVDA/JAWS/Narrator announcements and test steps, but records no verified results. — [wx-accessibility-test-suite](https://github.com/accesswatch/wx-accessibility-test-suite)
- `live-region` returns `false` when no UIA client is listening, which makes "was the announcement deliverable" testable. — [live-region windows.rs](https://raw.githubusercontent.com/trypsynth/live-region/master/src/windows.rs)

### Inferences
- **Manual protocol per screen:** with NVDA, Tab through every control and confirm name, role, state and value; open with the list focused and check the first thing spoken; use NVDA's speech viewer and log (NVDA+F1 on an object gives its developer info: window class, role, name, states) to capture exactly what was said; repeat with Narrator (UIA-first) and JAWS (background knowledge of NVDA tools; not sourced in this session).
- **Automated layer:** a UIA client test (Rust `windows` crate or C++ COM, or an external tool such as Accessibility Insights for Windows / `inspect.exe` for ad-hoc checks) that walks each dialog and asserts every focusable element has a non-empty Name and the expected ControlType, that tab order matches the specification, and that no Name equals a wx default such as "dataviewCtrl".
- **NVDA in CI:** feasible but brittle. Options are Guidepup (Node; the machine already has Node.js) or NvdaTestingDriver (.NET; already installed, beta), both of which need an interactive desktop session on a Windows runner; treat this as a later, optional smoke test rather than a gate.
- Keep the UI thin and the logic (QMP, downloads, image building) in non-GUI modules so most tests need no window at all (hn-blind's structure).

### Gaps
- Accessibility Insights for Windows and pywinauto were not researched in this session (pywinauto is Python and out of scope after the language decision).
- Whether GitHub-hosted Windows runners reliably provide the interactive session NVDA needs was not confirmed.
- NVDA's own system-test approach was not examined.

## 9. Reference projects and published guidance (including the short Python reference)

### Takeaway
The best current models are Paperback and hn-blind (Rust/wxDragon, screen-reader-first, 2026) for architecture and announcements, and NVDA's `source/gui` (wxPython) for control-level patterns that apply to wxWidgets in any language.

### Cited Findings
- **Paperback** (trypsynth, MIT): wxDragon desktop app; live-region announcements; UIA-asserting UI tests; a documented announcement-timing strategy; its author upstreams accessibility APIs to wxWidgets (PR #27056). — [Paperback](https://github.com/trypsynth/paperback); [PR #943](https://github.com/trypsynth/paperback/pull/943); [wx-dev PR #27056](https://groups.google.com/g/wx-dev/c/tLjR-EqDP_M)
- **live-region** (trypsynth, MIT): small crate to read for the UIA provider technique; API `set_live_region(window)`, `announce(label, msg)`, `announce_with_priority(label, msg, Priority::{Low,Medium,High})`. — [live-region](https://github.com/trypsynth/live-region); [lib.rs source](https://raw.githubusercontent.com/trypsynth/live-region/master/src/lib.rs)
- **hn-blind** (MIT, 2026): wxListCtrl/wxTreeCtrl/menus/notebook dialog; Prism for speech and braille; user-editable phrase templates; rule "Left closes a subthread" for trees. — [hn-blind](https://github.com/garo-pro/hn-blind)
- **NVDA `source/gui/guiHelper.py`**: `BoxSizerHelper.addLabeledControl` and `LabeledControlHelper` always construct the `StaticText` label first, then the control; layout rules "Horizontal layout, label first, control second", checkboxes "control first, label second", lists "Vertical layout, label above, control below"; enabling/hiding the control also updates its label; `PathSelectionHelper`; `addDialogDismissButtons`. — [guiHelper.py](https://raw.githubusercontent.com/nvaccess/nvda/master/source/gui/guiHelper.py)
- **NVDA `source/gui/nvdaControls.py`**: `ListCtrlAccessible` (custom `wxAccessible` reporting checkbox role and checked/selected/focused states, because "wx doesn't seem to have a method to check whether a list item is focused"), `CustomCheckListBox` ("to fix a11y bugs in the standard wx checkable list box"), `AutoWidthColumnCheckListCtrl`, `EnhancedInputSlider`, `SelectOnFocusSpinCtrl`, `DPIScaledDialog`. — [nvdaControls.py](https://raw.githubusercontent.com/nvaccess/nvda/master/source/gui/nvdaControls.py)
- **Python status, for reference only:** wxPython 4.3.1 (30 July 2026) tracks wxWidgets master 3.3.x and warns that 4.3.x may see API instability; 4.2.5 (8 Feb 2026) is built on wxWidgets 3.2.9; Windows wheels exist for Python 3.13 and 3.14 on x86, x64 and ARM64. NVDA 2026.1 ships wxPython 4.2.4; the update to 4.3.1 (wxWidgets 3.3.3) was merged to NVDA master on 29 Sept 2026 for 2027.1. TWBlue pins wxPython 4.3.1 with accessible_output2 and cx_Freeze + NSIS; Bookworm pins wxPython 4.2.1 with accessible-output2 0.17, PyInstaller + NSIS. — [PyPI wxPython](https://pypi.org/project/wxPython/); [wxPython 4.3.0 notes](https://wxpython.org/news/2026-07-27-wxpython-430-release/index.html); [NVDA 2026.1.1 changes](https://download.nvaccess.org/releases/2026.1.1/documentation/changes.html); [NVDA PR #20882](https://github.com/nvaccess/nvda/pull/20882); [TWBlue requirements.txt](https://raw.githubusercontent.com/MCV-Software/TWBlue/next-gen/requirements.txt); [Bookworm pyproject.toml](https://raw.githubusercontent.com/blindpandas/bookworm/develop/pyproject.toml)
- wxGlade has accessibility-oriented options under Preferences → Accessibility. — [discuss.wxpython thread](https://discuss.wxpython.org/t/creating-nvda-accessible-applications/40334)
- The wxWidgets wiki's accessibility tips page is reported as quite out of date. — [wxWidgets forum thread](https://forums.wxwidgets.org/viewtopic.php?p=127730)
- Official references: wxAccessible class docs; NVDA controller client readme. — [wxAccessible docs](https://docs.wxwidgets.org/3.3/classwx_accessible.html); [controllerClient readme](https://github.com/nvaccess/nvda/blob/master/extras/controllerClient/readme.md)

### Inferences
- The fact that NVDA, TWBlue and Bookworm are all wx-based confirms the toolkit choice (native Win32 controls) rather than any language: the screen-reader behaviour comes from wxWidgets and Windows, so a Rust or C++ app using the same controls and the same label-then-control ordering inherits it.
- NVDA's need for `ListCtrlAccessible`, the slider win-event workaround and its own path-selection helper are a ready-made list of where plain wx falls short; orchord can avoid all three by not using checkable lists, sliders or picker controls.
- A project-local helper modelled on `guiHelper.addLabeledControl` (one function that creates label then control and adds both to a sizer) is the single most effective way to make correct labelling the default in either language.

### Gaps
- No blind-developer blog posts or mailing-list threads (AudioGames developer room, program-l) specifically about accessible wxWidgets in C++ or Rust were retrieved; the AudioGames forum result found concerned accessible_output2 only.
- TWBlue and Bookworm source was not read beyond dependency manifests.

## 10. Ranked recommendation (Rust vs C++) and the conditions that would flip it

### Takeaway
Rank 1: **Rust + wxDragon** (with the `windows` crate, `live-region`-style UIA announcements and optionally Prism or the NVDA controller client). Rank 2: **C++ + wxWidgets 3.3.x** built with MSVC and vcpkg/CMake. No third compiled option is credible. Confidence is moderate: the ranking rests on ecosystem evidence and documented APIs, not on a hands-on build, so a one-day spike should confirm it before commitment.

### Cited Findings
- Evidence for Rust first: two 2026 screen-reader-first apps built on wxDragon by developers who test with NVDA; a ready MIT crate for prioritised announcements verified with NVDA; binding released eight times in about five months and tracking wxWidgets 3.3.3; accessible name/role/description/value/state setters since v0.9.18. — [Paperback](https://github.com/trypsynth/paperback); [hn-blind](https://github.com/garo-pro/hn-blind); [live-region](https://github.com/trypsynth/live-region); [wxDragon releases](https://github.com/allendang/wxdragon/releases)
- Evidence for Rust in the non-UI work: `qapi` crate for QMP with tokio examples; official `windows` crate covering UIA and the Hypervisor module; crosvm as a precedent for a Rust WHP-based monitor. — [docs.rs qapi](https://docs.rs/qapi/latest/index.html); [windows-docs-rs Hypervisor](https://microsoft.github.io/windows-docs-rs/doc/windows/Win32/System/Hypervisor/index.html); [crosvm whpx.rs](https://chromium.googlesource.com/crosvm/crosvm/+/32fba3ecac64cbbcab3b08b14d483c8e60707dd1/hypervisor/src/whpx.rs)
- Evidence against Rust: pre-1.0 binding with API-breaking changes and a use-after-free fix in the most recent release; `wxWizard`/`wxListbook` not wrapped; accessibility goes through the binding's own shim; open issue #229 for the newest wx accessibility APIs has no maintainer response; toolchain is a superset of C++'s (MSVC + CMake + Ninja, possibly LLVM, long first build); rustc's default diagnostics are noisy with a screen reader. — [wxDragon releases](https://github.com/allendang/wxdragon/releases); [docs.rs widgets](https://docs.rs/wxdragon/latest/wxdragon/widgets/index.html); [wxDragon issue #229](https://github.com/AllenDang/wxDragon/issues/229); [hn-blind README](https://github.com/garo-pro/hn-blind); [HN thread](https://news.ycombinator.com/item?id=37926926)
- Evidence for C++: complete wx API including full `wxAccessible` subclassing and new APIs as soon as they merge; choice of stable 3.2.11 or development 3.3.3; prebuilt MSVC binaries; static single-exe builds documented; the NVDA controller client, Tolk and Prism are C/C++ libraries usable directly. — [wxAccessible docs](https://docs.wxwidgets.org/3.3/classwx_accessible.html); [wxMSW install docs](https://docs.wxwidgets.org/3.3/plat_msw_install.html); [wxWidgets news](https://www.wxwidgets.org/news/2026/07/wxwidgets-3.2.11-and-3.3.3-released/); [controllerClient readme](https://github.com/nvaccess/nvda/blob/master/extras/controllerClient/readme.md)
- Evidence against C++: no QMP library found; template error output is long and deeply nested; no verified current accessible-first C++ wx app found in this research. — [qemu.qmp docs (Python only)](https://qemu.readthedocs.io/projects/python-qemu-qmp/en/latest/); [Rust vs common C++ bugs](https://geo-ant.github.io/blog/2022/common-cpp-errors-vs-rust/)
- Other bindings are dead or not compiled-language options (wx.NET 2010, wx-rs 2023 alpha, wxrust 2022 alpha). — [Wikipedia bindings table](https://en.wikipedia.org/wiki/List_of_language_bindings_for_wxWidgets); [wx-rs](https://github.com/AlexCharlton/wx-rs)

### Inferences
- **Why Rust ranks first.** (1) The UI orchord needs is exactly the subset wxDragon demonstrably handles in shipped accessible apps: list, menus, notebook dialog, status bar, simplebook for a hand-rolled wizard, gauge, checkbox, choice, spin control. (2) Most of orchord's risk is outside the UI — process supervision, QMP, resumable multi-gigabyte downloads, image building, Win32 calls — where cargo's ecosystem and memory safety save more time than C++'s complete wx API costs. (3) The 2026 accessible-wx community (Paperback's author in particular) is working in Rust and upstreaming fixes, so help and reusable code exist. (4) Both languages produce a native exe with no interpreter bootloader, so neither inherits the PyInstaller-style antivirus pattern; code signing still matters for SmartScreen (background knowledge).
- **Why C++ is a close second, not a distant one.** It is the only route with zero binding risk, it needs slightly less tooling, and since wxDragon compiles a C++ wrapper anyway, a Rust project can still drop to C++ for a missing wx API — which also means a C++ compiler is unavoidable on this machine either way.
- **Flip to C++ first if any of these hold:**
  1. The spike finds wxDragon cannot do something essential and the gap cannot be patched quickly: a custom `wxAccessible` with child elements, `EVT_CHAR_HOOK`/accelerator handling, list activation events, or thread-to-UI marshalling.
  2. The developer already writes C++ fluently and has no Rust experience, and wants the first release soon — the Rust learning curve plus a moving pre-1.0 binding is then the larger risk.
  3. wxDragon's release cadence stalls or issue #229-class requests stay unanswered while orchord needs 3.3.4+ accessibility APIs (`SetAccessibleName`, `EnableFocusFromKeyboard`, wxListCtrl/wxStatusBar accessibility).
  4. The project decides it must stay on the ABI-stable, security-patched wxWidgets 3.2.x line (wxDragon bundles 3.3.x only).
  5. Screen-reader ergonomics of the Rust toolchain (error output, long CMake/Ninja builds, LLVM dependency) prove worse in practice than MSVC's.
- **Stay with / strengthen Rust if:** the project later embeds its own VMM over the Windows Hypervisor Platform, adds low-level keyboard hooks or other latency-sensitive Win32 work, or values unit-testable non-GUI modules and one-command dependency management.
- **De-risking spike (before committing), about a day:** install VS 2022 C++ tools + CMake + Ninja + rustup from the command line; build a wxDragon window with a menu bar (File > New Virtual Machine, Ctrl+N), a `ListBox` with the placeholder row, Enter and context-menu handling, a dialog with label + text field + spin control + checkbox + Next/Back on a `SimpleBook`, a gauge fed from a worker thread, and one `live-region` announcement; then test with NVDA (and once with Narrator). Note first-build time, exe size and how readable `cargo build --message-format=short` is. If any item fails, build the same skeleton in C++ against prebuilt wxWidgets 3.3.3 binaries and compare.
- **Second language regardless of choice:** none is strictly required. A small C++ shim may be needed in a Rust build only to reach an unwrapped wx API; the NVDA controller client and Prism are prebuilt/native libraries consumed over a C interface.

### Gaps
- The ranking has not been validated by building anything in Rust or C++ on the developer's machine (no compiler is installed); first-build time, exe size, antivirus behaviour of the resulting unsigned exe, and screen-reader readability of real build errors are all unmeasured.
- The developer's existing fluency in Rust versus C++ is unknown and is probably the single largest factor.
- No head-to-head account from a blind developer who has used both wxDragon and C++ wxWidgets was found (Paperback's author would be the obvious person to ask, given the apparent C++ to Rust move).
