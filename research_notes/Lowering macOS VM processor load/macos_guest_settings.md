# macOS guest-side settings that lower processor load in an unaccelerated VM (VoiceOver user, macOS 11, 12, 14, 15 on Intel)

Reading guide for the report writer:

- Every bullet under "Cited Findings" carries a reliability tag: [Apple documentation], [man page], [Project README] (a VM project's own instructions, tested by its authors but not measured), [Forum anecdote] (one or a few users, unmeasured), or [Low-quality aggregator] (SEO-style article with no testing shown).
- Where I only saw a search-result excerpt and could not open the page itself (AppleVis and Dell both returned "403 Forbidden" to direct fetches), the bullet says "excerpt only".
- Commands that are widely circulated but that I could NOT tie to a source verified in this session are listed under "Gaps" as "Unverified candidates". They are probably correct but must be tested on the actual guest before the report presents them as fact.
- Headline result of the whole exercise: I found NO published measurement of WindowServer processor use in an unaccelerated macOS guest before and after any of these settings. Every effect size in circulation is either absent or unsourced. The report should say so plainly and recommend measuring on the guest (for example `top -l 5 -stats pid,command,cpu -o cpu` before and after each change).

## Accessibility display options: Reduce Motion, Reduce Transparency, Increase Contrast

### Takeaway
Reduce Motion and Reduce Transparency are the two guest-side display settings that every VM-oriented source recommends, and they are harmless to VoiceOver, but nobody has published a measured saving for a software-rendered guest. The `defaults write com.apple.universalaccess` route is blocked by privacy protection on current macOS unless Terminal has Full Disk Access, so the reliable route for a blind user is the System Settings toggle (keyboard and VoiceOver accessible) or granting Terminal Full Disk Access first.

### Cited Findings
- [Project README] The Docker-OSX authors' optimizer list, written specifically for virtual machines, gives these four commands under "Reduce Motion & Transparency": `defaults write com.apple.Accessibility DifferentiateWithoutColor -int 1`, `defaults write com.apple.Accessibility ReduceMotionEnabled -int 1`, `defaults write com.apple.universalaccess reduceMotion -int 1`, `defaults write com.apple.universalaccess reduceTransparency -int 1`. No measurement is given. The README dates from the Catalina and Big Sur era. — [sickcodes/osx-optimizer README](https://github.com/sickcodes/osx-optimizer)
- [Forum anecdote] Since at least Catalina, writing to `com.apple.universalaccess` from Terminal is restricted and fails with "Could not write domain com.apple.universalaccess; exiting." Using `sudo` does not fix it. Granting the terminal application Full Disk Access (Privacy settings) is suggested as the workaround, but the commenter had not tested it. A linked issue places the same error on Monterey. — [mathiasbynens/dotfiles issue 1039](https://github.com/mathiasbynens/dotfiles/issues/1039)
- [Forum anecdote] On Ventura the same "Could not write domain" error appeared when the command ran from an automation tool's shell action, although it worked in that user's Terminal; the suggested fix was to give the full path, `/usr/bin/defaults write ~/Library/Preferences/com.apple.universalaccess ...`. — [Keyboard Maestro forum](https://forum.keyboardmaestro.com/t/execute-shell-script-action-fails-to-increase-macos-contrast/31061)
- [Vendor help page] A device-management vendor publishes a script that runs, as the logged-in user, `defaults write /Users/$loggedInUser/Library/Preferences/com.apple.universalaccess.plist reduceMotion 1` and the same for `reduceTransparency 1`. The page names no macOS version and does not say whether a logout is needed. Caution: the script's last line deletes the same preference file it just wrote, which looks like a mistake, so do not copy it verbatim. — [Hexnode help](https://www.hexnode.com/mobile-device-management/help/script-to-reduce-motion-and-transparency-on-macos-devices.md)
- [Forum anecdote, excerpt only] A commenter notes that setting `reduceMotion` from the command line does take effect, but that the effect of Reduce Motion is limited: it mainly replaces slide transitions with cross-fades rather than removing animation altogether. — [mathiasbynens/dotfiles issue 711](https://github.com/mathiasbynens/dotfiles/issues/711)
- [Low-quality aggregator] A March 2026 guide for a slow macOS Sequoia guest on VMware Workstation on Windows recommends System Settings, Accessibility, Display, Reduce Motion ON (it calls zoom animations "one of the biggest GPU consumers") and Reduce Transparency ON (replaces blur with solid colour). It gives no figures for either. — [itech4mac](https://www.itech4mac.net/2026/03/how-to-fix-slow-macos-sequoia-on-vmware-workstation-windows-host/)
- [Low-quality aggregator] General WindowServer articles for real Macs recommend the same two toggles. Some quote reductions of 30 to 50 percent from disabling transparency, but those figures are unsourced; one of the same articles warns against promising any fixed reduction because the effect depends on the Mac, display, applications and activity. — [mole.fit](https://mole.fit/blog/windowserver-high-cpu-mac), [cindori](https://cindori.com/how-to/windowserver-high-cpu-mac-fixes)
- [Forum anecdote] One counter-report: on Intel Macs running Big Sur or Monterey, turning Reduce Transparency ON made a Quick Look drawing glitch (red squares) worse, and the thread advised leaving it off. This is a visual artefact, irrelevant to a blind user, but it shows the setting changes drawing paths. — [Apple Community thread](https://origin-discussions2-us-dr-prz.apple.com/thread/253651367)

### Inferences
- Location by version. macOS 11 and 12: System Preferences, Accessibility, Display, with checkboxes "Reduce motion", "Reduce transparency", "Increase contrast". macOS 14 and 15: System Settings, Accessibility, Display (the path the itech4mac guide gives for Sequoia). The preference keys in the osx-optimizer README (`reduceMotion`, `reduceTransparency` in `com.apple.universalaccess`) are the same ones the dotfiles community has used since before Big Sur, so the key names appear stable across 11 to 15, but I found no source that tested them on 14 or 15 specifically.
- None of these three settings needs System Integrity Protection disabled. The obstacle is privacy protection (Full Disk Access), which is a separate mechanism.
- The settings are stored in the user's preferences, so they survive a restart. Whether a `defaults write` takes effect in the running session or only after logging out is not established by any source I found; the System Settings toggle applies immediately.
- No VoiceOver downside: these are purely visual. Increase Contrast automatically implies reduced transparency on the versions in scope, so it is a superset, but I found no source saying it saves any more processor time than Reduce Transparency alone.
- `DifferentiateWithoutColor` in the README is not a performance setting; it can be dropped from any recommended list.

### Gaps
- No measurement exists (that I could find) of WindowServer processor use with and without Reduce Motion or Reduce Transparency in a software-rendered guest on any macOS version.
- Unverified candidate, not sourced this session: `defaults write com.apple.universalaccess increaseContrast -bool true` as the command equivalent of Increase Contrast.
- Unverified: whether granting Terminal Full Disk Access really unblocks the write on Sonoma and Sequoia. The one source proposing it had not tested it. This should be tested on the guest.
- Unknown: whether Sequoia's extra motion options (such as auto-play of animated images, or the non-blinking cursor preference) save anything. I found no source.

## WindowServer cost without a GPU: what consumes processor time and what can be turned off; resolution and colour depth

### Takeaway
All VM communities agree that an unaccelerated macOS guest is slow because the processor does all compositing, and that only some animation can be switched off; but I found no breakdown of which effects cost the most, and no evidence either way on resolution or colour depth. Removing continuously changing content (animated wallpaper, desktop widgets, Stage Manager) and transparency is the consistent advice.

### Cited Findings
- [Vendor staff, forum] There is no Metal graphics support for a macOS guest on VMware Workstation; a Sequoia guest showed a black screen with 3D acceleration off, and Final Cut Pro refused to run with "This graphic configuration does not support hardware acceleration". — [Broadcom community](https://community.broadcom.com/vmware-cloud-foundation/discussion/sequoia-graphics-configuration-not-supported)
- [Project README] Quickemu states macOS guests are optimised by default "but no GPU acceleration is available". — [quickemu README (mirror)](https://git.binarymagic.net/AIR/quickemu/commit/28b549c886009eaf3b37897755b2db74d386eab8)
- [Forum anecdote] TrueNAS thread, May 2023, Monterey and Ventura guests without a passed-through graphics card: "Unless you have a supported GPU passed through to the VM, it will be near unusable"; "Just simple things like minimizing a window can lockup your VM for 5-10 seconds"; "You can try to turn off some animations, but not everything can be turned off." Other posters in the same thread disagreed and found ordinary file and web tasks acceptable on a Ryzen 5600 with no graphics card. — [TrueNAS community](https://www.truenas.com/community/goto/post?id=679315)
- [Forum anecdote] A patched older Mac with no graphics acceleration (root patches not installed) is "painfully slow, because you have no graphics acceleration". — [MacRumors forum](https://forums.macrumors.com/threads/opencore-on-macbook-pro-2012.2370464/)
- [Low-quality aggregator] General explanation: persistent WindowServer processor spikes often indicate unaccelerated drawing paths or overly frequent redraws; remote-desktop and virtual-display tools add capture and composition work; high refresh rates and animated desktops raise the work even when no window is being touched, because more frames or continuously changing pixels must be composited. — [andreafortuna.org](https://andreafortuna.org/2025/10/05/macos-windowserver/), [mole.fit](https://mole.fit/blog/windowserver-high-cpu-mac)
- [Apple documentation, excerpt only] In Sonoma and later, widgets are controlled in System Settings, Desktop & Dock, Widgets. "Show Widgets" has separate checkboxes for "On Desktop" and "In Stage Manager", and by default widgets are shown in both. The same pane has "Click wallpaper to reveal desktop". — [Apple Support](https://support.apple.com/108996), also described at [Intego](https://www.intego.com/mac-security-blog/how-to-use-desktop-widgets-on-macos-sonoma/)
- [Forum anecdote] Sonoma's aerial wallpapers are downloaded by a background process named `idleassetsd`; users reported downloads stalling with timeouts. This shows that choosing an aerial wallpaper or screen saver on Sonoma and later triggers background downloading as well as animation. — [Apple Developer Forums](https://developer.apple.com/forums/thread/738475?page=2)
- [Project README] To remove the "heavy login screen wallpaper": `sudo defaults write /Library/Preferences/com.apple.loginwindow DesktopPicture ""`. — [sickcodes/osx-optimizer README](https://github.com/sickcodes/osx-optimizer)
- [Vendor blog] In VMware macOS guests, macOS no longer remembers a custom display mode and falls back to a default mode; resolutions above 2560 by 1600 need more video memory because the framebuffer exceeds 16 MB. This is VMware-specific. — [williamlam.com](https://williamlam.com/tag/resolution)
- [Forum anecdote, excerpt only] On real Macs, a Mac mini with no display attached ran sluggishly with VoiceOver, and attaching a monitor or dummy plug helped. — [AppleVis](https://applevis.com/comment/133382)

### Inferences
- The AppleVis headless-Mac anecdote matters here: a Mac with no display attached loses graphics acceleration, and blind users report that VoiceOver then becomes sluggish. That is the same condition as this guest, and it suggests that VoiceOver's own responsiveness (not only visual smoothness) suffers when WindowServer is software-rendered. So reducing WindowServer work is plausibly a direct route to faster speech response, though no source measures it.
- In software rendering the compositing cost should scale roughly with the number of pixels redrawn, so a lower resolution (for example 1024 by 768 or 1280 by 720, non-Retina) ought to cut work. This is reasoning, not a sourced finding. In a QEMU guest using the emulated VMware adapter without guest tools, the resolution is fixed by the firmware and boot loader on the host side (the firmware's display mode and OpenCore's resolution setting), not by a macOS setting, so this belongs with the host-side research.
- A static, solid-colour desktop picture, no desktop widgets, Stage Manager off, no aerial or animated screen saver, and "screen saver: never" remove every source of continuous redraw on Sonoma and Sequoia. On Big Sur and Monterey the equivalents are: no dynamic desktop picture and screen saver set to never.
- Apple's widget and Stage Manager toggles are ordinary user preferences: they survive a restart, need no System Integrity Protection change, and have no VoiceOver downside (a blind user gains nothing from desktop widgets or Stage Manager thumbnails).

### Gaps
- No source measured the processor cost of blur, shadows, wallpaper, widgets or Stage Manager under software rendering.
- No source addressed colour depth in a macOS guest. I found nothing saying a lower depth is selectable or helpful on macOS 11 to 15.
- Unverified candidates, not sourced this session: `defaults write com.apple.WindowManager GloballyEnabled -bool false` (Stage Manager off), `defaults write com.apple.WindowManager StandardHideWidgets -bool true` and `StageManagerHideWidgets -bool true` (hide widgets), `defaults write com.apple.WindowManager EnableStandardClickToShowDesktop -bool false`, `defaults -currentHost write com.apple.screensaver idleTime -int 0` (screen saver never). Two searches for the WindowManager keys returned nothing confirming them; test before publishing.
- Unknown: whether VoiceOver's Screen Curtain reduces WindowServer work in a guest. No source found.
- Unknown: whether the OpenCore Legacy Patcher non-Metal notes apply. Those machines still have OpenGL acceleration, so they are not a true software-rendering comparison, and my search did not surface their documentation.

## Background services that burn processor time, and how to disable them

### Takeaway
Turning Spotlight indexing off with `mdutil` and stopping automatic software updates are the two changes VM projects explicitly call large wins, and both work without touching System Integrity Protection. Apple's machine-learning and experiment daemons (photoanalysisd, mediaanalysisd, triald) are much harder: per-user `launchctl disable` works for some, others cannot be persistently unloaded with protection on, and the reliable low-risk approach is to remove their work (no photo library, no iCloud, Siri and analytics off) rather than fight launchd.

### Cited Findings
- [Project README] "Disable spotlight indexing on macOS to heavily speed up Virtual Instances": `sudo mdutil -i off -a`; re-enable with `sudo mdutil -i on -a`. The README warns that you then cannot use Spotlight to find applications. No measurement. — [sickcodes/osx-optimizer README](https://github.com/sickcodes/osx-optimizer)
- [Reference notes] `mdutil` flags: `-i on|off` turns indexing on or off, `-a` applies to all stores on all volumes, `-E` erases and rebuilds the index, `-s` shows status. — [wener.me Spotlight notes](https://wener.me/notes/os/macos/spotlight)
- [Low-quality aggregator] `mds_stores` normally settles within a few hours once initial indexing completes; a corrupted or incomplete index is described as the usual cause of permanently high use. — [cloudhousetechnologies](https://cloudhousetechnologies.com/blog/fix-mds-stores-high-cpu-spotlight-mac-2026)
- [Low-quality aggregator, single source] A guide claims a Sequoia bug caused Spotlight to write very large amounts of data to disk and recommends `sudo mdutil -a -i off` as a precaution. Treat the claim with caution. — [macos-tahoe.com](https://macos-tahoe.com/blog/spotlight-rebuild-guide-fix-search-not-working-2025/)
- [Low-quality aggregator] The itech4mac Sequoia guest guide recommends: System Settings, Siri & Spotlight, uncheck all Search Results categories; General, Software Update, Automatic OFF; General, Time Machine OFF. No figures. Note that unchecking result categories is weaker than `mdutil -a -i off`. — [itech4mac](https://www.itech4mac.net/2026/03/how-to-fix-slow-macos-sequoia-on-vmware-workstation-windows-host/)
- [Project README] "Disable updates (at your own risk!)", run as root: `defaults write /Library/Preferences/com.apple.SoftwareUpdate AutomaticDownload -bool false`, `defaults write com.apple.SoftwareUpdate AutomaticCheckEnabled -bool false`, `defaults write com.apple.commerce AutoUpdate -bool false`, `defaults write com.apple.commerce AutoUpdateRestartRequired -bool false`, `defaults write com.apple.SoftwareUpdate ConfigDataInstall -int 0`, `defaults write com.apple.SoftwareUpdate CriticalUpdateInstall -int 0`, `defaults write com.apple.SoftwareUpdate ScheduleFrequency -int 0`, `defaults write com.apple.SoftwareUpdate AutomaticDownload -int 0`. Stated reason: stops huge downloads and stops the disk image growing. Downside: no security updates, which includes XProtect and other security data files (`ConfigDataInstall`, `CriticalUpdateInstall`). — [sickcodes/osx-optimizer README](https://github.com/sickcodes/osx-optimizer)
- [Forum anecdote] photoanalysisd: killing it is not enough because it is restarted; the suggested method is `launchctl disable gui/$UID/com.apple.photoanalysisd` followed by `launchctl kill -TERM gui/$UID/com.apple.photoanalysisd`, undone with `launchctl enable ...`. Another site uses the `user/$UID` domain instead; the two disagree on domain, so test. — [Apple Community](https://discussions.apple.com/thread/8155926?page=1), [iBoysoft](https://iboysoft.com/wiki/photoanalysisd.html)
- [Press how-to] mediaanalysisd (Ventura-era guide): stopping it permanently requires disabling System Integrity Protection and removing its launch agent file from `/System/Library/LaunchAgents`. Apple advises that protection be disabled only temporarily. — [AppleInsider](https://appleinsider.com/inside/macos-ventura/tips/how-to-stop-mediaanalysisd-from-hogging-your-cpu-in-macos)
- [Forum anecdote] triald on Monterey 12.3: used more than 50 percent of a processor, restarted immediately when force-quit, and persisted in Safe Mode. "It was not possible to persistently unload the LaunchAgents for either triald or mediaanalysisd." Moving `~/Library/Trial/` aside helped one user "if only for a few days" and did not help another. Turning Siri on or off gave contradictory results. No confirmed fix. A senior community member warned that deleting system processes' data files tends to make things worse. — [Apple Community](https://discussions.apple.com/thread/253753373)
- [Low-quality aggregator, excerpt only] triald is described as a background service connected with Siri and with experiments delivered through CloudKit. — [iBoysoft](https://iboysoft.com/wiki/triald-process-mac.html)
- [Forum anecdote, excerpt only] On Sonoma, launchd behaviour changed and there are processes that `launchctl` "no longer has any control over". — [Apple Developer Forums](https://developer.apple.com/forums/thread/738722)

### Inferences
- Spotlight off is the best-supported single background change. It needs administrator rights but not System Integrity Protection, applies on 11, 12, 14 and 15 (the command is unchanged), and the README's re-enable instruction implies it persists until reversed. VoiceOver-specific downside: many blind users launch applications with Command-Space; with indexing off that stops finding applications. Workarounds are Finder's Applications folder (Command-Shift-A, then type the first letters) or Launchpad. Searching in Mail and Finder also stops working.
- A compromise that keeps application launching: leave indexing on, let the first-run index finish once (hours of `mds_stores` and `mdworker` activity after installation), then add the large data folders to Spotlight's privacy exclusion list. No source measured this for a guest.
- For a guest that never uses Photos, iCloud, Siri or Apple Intelligence, the cheapest way to keep photoanalysisd, mediaanalysisd, cloudd, bird and similar daemons idle is to give them nothing to do: do not sign in to iCloud (or turn off iCloud Photos and iCloud Drive), keep the Photos library empty, and decline Siri during setup. This is consistent with the sources (the daemons are reported busy "after a lot of photos are added or an operating system upgrade") but is my reasoning, not a tested result.
- System Integrity Protection: per-user `launchctl disable gui/$UID/...` for user agents is reported to work with protection on. Removing or unloading system-domain launch files is reported to need protection off, and on Big Sur and later the system volume is also sealed, so editing `/System/Library/LaunchAgents` is a much larger step than on older systems. I would not recommend it for this user.
- The first hours after installation or after any update are a known heavy period (indexing, photo and media analysis, update checks). Advice in the report should distinguish "wait for it to finish once" from "disable permanently".

### Gaps
- No reliable, tested, per-version recipe was found for disabling `biomed`, `duetexpertd`, `analyticsd`, `spindump`, `ReportCrash`, `tailspind`, XProtect scans (`XProtectRemediator`, `XprotectService`), `softwareupdated`, `suggestd`, `siriknowledged` or iCloud daemons on Sonoma or Sequoia. The searches returned nothing usable; community scripts exist but I did not locate or verify one.
- Unverified candidates, not sourced this session: `sudo softwareupdate --schedule off`; `sudo tmutil disable` (Time Machine; local snapshots are only made when Time Machine is configured); turning off System Settings, Privacy & Security, Analytics & Improvements (all switches) to quieten `analyticsd` submissions; `defaults write com.apple.assistant.support "Assistant Enabled" -bool false` for Siri; App Store, Settings, Automatic Updates off.
- Unknown: whether `mdutil -a -i off` also stops the Siri Suggestions and Spotlight knowledge daemons (`suggestd`, `corespotlightd`). No source addressed this.
- Unknown: the idle processor cost of each daemon in a guest. No measurements found.
- The persistence of `mdutil -i off` across macOS updates was not confirmed by a source; some users report indexing being re-enabled after major upgrades.

## Dock, Finder and Mission Control animation defaults

### Takeaway
The classic animation-shortening `defaults` keys are still passed around in gists and guides, but I found no source that tested any of them on Sonoma or Sequoia, and one forum report says a window-animation setting "worked at first" and then stopped. Treat all of them as cheap, reversible, unproven; Reduce Motion is the only officially supported control.

### Cited Findings
- [Community gists and notes, undated or 2018 to 2021] The commonly listed keys are `defaults write -g NSAutomaticWindowAnimationsEnabled -bool false` (new-window animation, introduced with Lion), `defaults write com.apple.dock expose-animation-duration -float 0` (Mission Control), and `defaults write com.apple.dock launchanim -bool false` (application launch bounce from the Dock), followed by `killall Dock`. None of these sources states a macOS version beyond the era in which it was written. — [gist by DarioBF](https://gist.github.com/DarioBF/49037825efab934fd234f3303460615d), [gist by kidpixo](https://gist.github.com/kidpixo/78b9a40ab58e026cf9a432573e27ced5), [MPI notes on system animations](https://github.molgen.mpg.de/pages/bs/macOSnotes/mac/mac_system_anim.html), [krypted.com](https://krypted.com/?p=7286)
- [Forum anecdote] A user trying to disable window-movement animation reported that the change "worked at first. And now ... suddenly it's not." The macOS version is not stated. — [Keyboard Maestro forum](https://forum.keyboardmaestro.com/t/can-animation-of-moving-windows-be-disabled/34149)
- [Forum anecdote] TrueNAS poster on Monterey and Ventura guests: some animations can be turned off "but not everything can be turned off." — [TrueNAS community](https://www.truenas.com/community/goto/post?id=679315)
- [Project README] To make shutdown and start-up lighter, stop applications being reopened at login: `defaults write com.apple.loginwindow TALLogoutSavesState -bool false`. — [sickcodes/osx-optimizer README](https://github.com/sickcodes/osx-optimizer)

### Inferences
- These keys are user preferences: they survive restarts, need no System Integrity Protection change, and are undone with `defaults delete`. None has a VoiceOver downside; shorter animations can only help, because VoiceOver often waits for a window or Mission Control transition to finish before it speaks the new focus.
- Dock autohide is worth considering on its own merits for a software-rendered guest: a hidden Dock removes a permanently composited translucent layer. No source measured this.

### Gaps
- No source confirms which of these keys still have an effect on Sonoma 14 or Sequoia 15. This needs direct testing on the guest.
- Unverified candidates, not sourced this session (widely circulated, plausible, untested here): `defaults write com.apple.dock autohide -bool true`, `defaults write com.apple.dock autohide-time-modifier -float 0`, `defaults write com.apple.dock autohide-delay -float 0`, `defaults write com.apple.dock mineffect -string scale`, `defaults write com.apple.dock springboard-show-duration -float 0` and `springboard-hide-duration -float 0` (Launchpad), `defaults write -g NSWindowResizeTime -float 0.001`, `defaults write -g QLPanelAnimationDuration -float 0`, `defaults write com.apple.finder DisableAllAnimations -bool true`, `defaults write -g NSScrollAnimationEnabled -bool false`, `defaults write -g NSToolbarFullScreenAnimationDuration -float 0`. Apply with `killall Dock` and `killall Finder`.
- No measurement of processor savings from any animation key was found.

## Power and sleep: pmset, Power Nap, App Nap

### Takeaway
`pmset` settings are system-wide and persistent, and for a guest the goal is to stop the Mac sleeping or hibernating (which tends to hang or confuse a VM) rather than to save processor time; nothing I found shows that any power setting lowers running processor load. App Nap should be left ON: disabling it makes background applications use more resources.

### Cited Findings
- [man page] `sleep`: system sleep timer in minutes, 0 disables. `displaysleep`: display sleep timer, 0 disables. `disksleep`: disk spin-down timer, 0 disables. `powernap`: enable or disable Power Nap on supported machines (0 or 1). `standby`: makes the kernel automatically hibernate a machine after it has slept for a set time. `autopoweroff`: after sleeping for the delay, writes a hibernation image and enters a lower-power state. `hibernatemode`: change hibernation mode, "Please use caution". `womp`: wake on Ethernet magic packet. `ttyskeepawake`: prevent idle sleep while a remote login session is active. — [pmset man page copy at DssW](https://www.dssw.co.uk/reference/pmset/)
- [man page] The flags `-a`, `-b`, `-c`, `-u` apply settings to all power sources, battery, charger, or UPS. "All changes made through pmset are saved in a persistent preferences file (per-system, not per-user)" at `/Library/Preferences/SystemConfiguration/com.apple.PowerManagement.plist`. — [pmset man page copy at DssW](https://www.dssw.co.uk/reference/pmset/)
- [man page, excerpt only] `hibernatemode` accepts 0, 3 or 25; to stop hibernation images being written at all, `hibernatemode`, `standby` and `autopoweroff` must all be 0. — [pmset man page copy at sudo.is](https://www.sudo.is/docs/macos/man_pmset.html)
- [Project README] Disabling App Nap (`sudo defaults write NSGlobalDomain NSAppSleepDisabled -bool YES`) "increases RAM usage" and means applications never enter the sleeping state; the README lists it under methods for build servers, as a way to make applications respond faster, not as a way to reduce load. — [sickcodes/osx-optimizer README](https://github.com/sickcodes/osx-optimizer)
- [Project README] To stop the screen locking: `defaults write com.apple.loginwindow DisableScreenLock -bool true`. — [sickcodes/osx-optimizer README](https://github.com/sickcodes/osx-optimizer)
- [Low-quality aggregator] The itech4mac guide suggests setting energy to "High Performance" to prevent throttling, without detail; that option is a hardware feature of certain Macs and probably does not exist in a guest. — [itech4mac](https://www.itech4mac.net/2026/03/how-to-fix-slow-macos-sequoia-on-vmware-workstation-windows-host/)

### Inferences
- A sensible guest baseline built only from documented settings is `sudo pmset -a sleep 0 disksleep 0 powernap 0 standby 0 autopoweroff 0 hibernatemode 0 womp 0`. It is persistent, needs no System Integrity Protection change, and its purpose is stability (no sleep, no hibernation image, no dark-wake background work from Power Nap). I found no evidence it changes processor load while the guest is awake. Power Nap only matters while asleep, so with sleep disabled it is moot.
- `displaysleep` is a judgement call. Letting the display sleep could in principle stop WindowServer compositing while idle, but no source shows that, and display sleep in a guest risks a screen lock or a wake problem that a blind user cannot diagnose visually. Recommend `displaysleep 0` plus the screen-lock setting above unless testing shows a benefit.
- App Nap: keep enabled. It is the mechanism that throttles hidden background applications, which is what a four-processor guest wants. A VoiceOver user should know that disabling it is not a speech-latency fix according to any source found.
- Moving the settings location: macOS 11 has System Preferences, Energy Saver (desktop) or Battery (portable); macOS 12 the same; macOS 14 and 15 have System Settings, Energy (or Battery) and Lock Screen. The `pmset` command is the same on all four.

### Gaps
- `disablesleep`, `tcpkeepalive` and `lowpowermode` were not in the man page copy I could read, so I cannot cite their behaviour. `sudo pmset -a disablesleep 1` is an unverified candidate.
- No source examined power settings specifically in a QEMU guest, and none measured any processor effect.
- Unknown whether Low Power Mode (available on some machines from Monterey) is offered in a guest or what it would do to software rendering.

## VoiceOver-specific settings: voices, VoiceOver Utility options, and reports of lag

### Takeaway
The only consistent community finding is about the voice: small rule-based voices (Fred historically, Eloquence on Ventura and later) are reported as noticeably more responsive than Alex or the Vocalizer voices such as Samantha, and VoiceOver sound effects and per-application Activities have each been blamed for delays. All of this is anecdote from real Macs; I found nothing at all about VoiceOver inside a virtual machine.

### Cited Findings
- [Forum anecdote, excerpt only, 2013 to 2017] AppleVis users recommend switching to Fred for responsiveness: it "has been on the Mac since the beginning", is "small and responsive", and switching to it "really does increase VoiceOver's responsiveness", at the cost of a harsher sound. — [AppleVis, "Increasing Responsiveness of Voiceover on a Mac"](https://applevis.com/comment/18354), [AppleVis, "Voiceover quirkiness on my Mac"](https://www.applevis.com/comment/76043)
- [Forum anecdote, excerpt only] Alex and similar high-quality voices "sound wonderful" but "are not the most responsive voices for VoiceOver". — [AppleVis](https://www.applevis.com/comment/75949)
- [Forum anecdote, excerpt only, 2017] One commenter warned against the Vocalizer voices (Samantha and others), saying Apple had "major responsiveness issues" with them since Mavericks in 2013. — [AppleVis](https://www.applevis.com/comment/75961)
- [Community bug tracker] "VoiceOver is sluggish when using the speech rotor with Nuance voices" was tracked as a bug and marked fixed in macOS Ventura 13.0, so on Big Sur 11 and Monterey 12 the Nuance (Vocalizer) voices carry that known sluggishness. — [AppleVis bug page](https://applevis.com/bugs/mac/voiceover-sluggish-when-using-speech-rotor-nuance-voices)
- [Community bug tracker] An older bug, lag when browsing VoiceOver Utility with Vocalizer voices, was marked fixed in OS X 10.11. — [AppleVis bug page](https://applevis.com/bugs/mac/lag-when-using-voiceover-utility)
- [Community editorial, excerpt only] macOS Ventura 13 added the voices introduced in iOS 16, including Eloquence. AppleVis's editorial team said VoiceOver felt somewhat more responsive than on Monterey in some situations, while noting performance is hard to measure. Beta-era commenters called Eloquence "very responsive on macOS". — [AppleVis Ventura article](https://applevis.com/comment/140894), [AppleVis Ventura thread](https://www.applevis.com/comment/137240)
- [Forum anecdote, excerpt only] Turning off VoiceOver's navigation sounds may reduce lag: "the navigation clicks, squalks, beeps and chirps decrease VO's responsiveness". — [AppleVis](https://www.applevis.com/comment/76043)
- [Forum anecdote, excerpt only, 2022] On a 2019 Mac mini, VoiceOver paused for one to two seconds after switching applications while a per-application Activity was defined; deleting the Activities removed the delay. — [AppleVis](https://www.applevis.com/comment/136226)
- [Forum anecdote, excerpt only, 2022] VoiceOver's "not responding" and "busy" announcements come from VoiceOver waiting on the application's accessibility interface; the thread's view is that the application's slowness, not speech synthesis, is the bottleneck, and a faster machine may not cure it. — [AppleVis](https://applevis.com/comment/133382)
- [Apple documentation, excerpt only] VoiceOver Utility, Visuals category, "Panels and Menus" tab: "Show caption panel" checkbox; "Show Braille Panel" pop-up with Off, On, Automatic (Automatic is the default and only shows the panel when a braille display is connected). Keyboard commands: VO-Fn-Command-F10 toggles the caption panel, VO-Fn-Command-F9 the braille panel, and VO-Fn-Command-F11 shows or hides the caption panel, braille panel and VoiceOver cursor together. Open VoiceOver Utility with VO-Fn-F8. — [Apple VoiceOver User Guide](https://support.apple.com/guide/voiceover/cpvouviscap/mac)
- [Community workaround, excerpt only] For persistent VoiceOver misbehaviour: toggle VoiceOver off and on, log out and back in, or (after exporting settings) delete the VoiceOver preference files. — [AppleVis](https://www.applevis.com/comment/76042)

### Inferences
- Voice recommendation by version. Big Sur 11 and Monterey 12: Eloquence is not available (it arrived in Ventura 13), so Fred is the community's "fastest" choice, with Alex as the quality compromise; avoid Vocalizer voices, which had a tracked sluggishness bug until 13.0. Sonoma 14 and Sequoia 15: Eloquence is available and is reported as very responsive; Fred remains available. Siri and "Premium" or "Enhanced" voices are larger and are the likeliest to cost processor time, but no source measured this.
- In an unaccelerated guest the caption panel is the one VoiceOver visual that redraws on every utterance (it is a translucent floating panel showing each spoken phrase). Turning off "Show caption panel", leaving the braille panel on Automatic or Off, and hiding the VoiceOver cursor (VO-Fn-Command-F11 does all three) should remove per-utterance WindowServer work. This is reasoning from how the feature works; no source tested it in a guest.
- The "busy" finding implies that speech latency in a guest is largely the application and WindowServer round trip, not the synthesiser. So the settings that reduce WindowServer and background load (earlier sections) may matter more for key-to-speech delay than the choice of voice does.
- None of the VoiceOver Utility changes needs System Integrity Protection changes; they are per-user and persistent, and VoiceOver Utility's File menu can export them for backup.

### Gaps
- I found no report of any kind about VoiceOver running in a macOS virtual machine (QEMU, VMware, UTM, Proxmox), sluggish or otherwise, and therefore no fix reports. This is a real gap in public knowledge and the project's own testing is the only evidence available.
- eSpeak: I found no source saying eSpeak ships with macOS 13 or later. Apple's Ventura additions reported by AppleVis are Eloquence and other iOS 16 voices. Third-party synthesisers may be installable on newer systems, but I could not confirm that or its processor cost in this session; do not state that eSpeak is built in.
- No measured processor cost or latency per voice exists in any source found. The Fred, Alex and Vocalizer comparisons are from 2013 to 2017 and may not hold on macOS 11 to 15.
- Not confirmed against Apple's documentation in this session (page bodies were not retrievable): the exact names and locations of "Mute sound effects", "Enable audio ducking", positional audio, "Speak while typing"/typing echo, verbosity levels, and cursor-wrapping options, and whether any of them affects responsiveness. Apple's guide has a "Sound" category and a "Use positional audio" topic at [the VoiceOver User Guide contents](https://support.apple.com/guide/voiceover/toc). Unverified candidates worth testing: mute sound effects, turn off positional audio and audio ducking, verbosity Low, typing echo to "Nothing" or "Characters".
- Unknown: whether a faster speech rate changes processor cost, and whether Screen Curtain changes WindowServer load in a guest.
- Unknown: whether audio latency inside the guest (the emulated sound device's buffer on the host) contributes to speech delay; that is a host-side question.

## Login and start-up

### Takeaway
VM projects recommend automatic login, a plain login window, no reopening of applications at login, and no login-window wallpaper; these shorten start-up but do nothing for steady-state load. The README's automatic-login command is wrong as written and should not be copied.

### Cited Findings
- [Project README] "Skip the GUI login screen (at your own risk!)": `defaults write com.apple.loginwindow autoLoginUser -bool true`. — [sickcodes/osx-optimizer README](https://github.com/sickcodes/osx-optimizer)
- [Project README] Lighter login window, a name and password prompt instead of a user list: `defaults write /Library/Preferences/com.apple.loginwindow.plist SHOWFULLNAME -bool true` and `defaults write com.apple.loginwindow AllowList -string '*'`. — [sickcodes/osx-optimizer README](https://github.com/sickcodes/osx-optimizer)
- [Project README] Do not save and reopen applications across a restart: `defaults write com.apple.loginwindow TALLogoutSavesState -bool false`. Stated to speed boot; "may be slower for you depending on what you are doing." — [sickcodes/osx-optimizer README](https://github.com/sickcodes/osx-optimizer)
- [Project README] Remove the login-window wallpaper: `sudo defaults write /Library/Preferences/com.apple.loginwindow DesktopPicture ""`. — [sickcodes/osx-optimizer README](https://github.com/sickcodes/osx-optimizer)

### Inferences
- The README's `autoLoginUser -bool true` is very likely incorrect: that key normally holds the short user name and automatic login also needs the stored password file that System Settings creates. The dependable, VoiceOver-accessible route is the documented control: System Preferences, Users & Groups, Login Options, "Automatic login" on macOS 11 and 12; System Settings, Users & Groups, "Automatically log in as" on macOS 14 and 15. Automatic login is unavailable while FileVault is on. This paragraph is my own knowledge, not sourced this session.
- VoiceOver downside of the "name and password" login window: the user must type the account name blind at every login instead of pressing Return on a list entry. Not recommended for this user; automatic login makes it moot anyway.
- VoiceOver benefit of automatic login: VoiceOver at the login window is a separate setting from VoiceOver in the user session, and a software-rendered login window is slow; skipping it removes a step where speech may not yet be running.
- Login items location: System Preferences, Users & Groups, Login Items on macOS 11 and 12; System Settings, General, Login Items (with a separate "Allow in the Background" list) on macOS 14 and 15. A fresh guest has few or none.

### Gaps
- Start-up chime: unverified candidate `sudo nvram StartupMute=%01` (and the "Play sound on startup" checkbox in Sound settings on Big Sur and later). Not sourced this session; and in a guest, whether any NVRAM variable persists depends on how the host stores the firmware variables.
- No source measured start-up time or post-login processor load for any of these settings in a guest.

## Which macOS versions are lighter without acceleration

### Takeaway
I found no evidence, measured or even anecdotal, that directly compares software-rendered Big Sur, Monterey, Sonoma and Sequoia guests. The belief that older versions are lighter is plausible but unsupported by anything I could cite.

### Cited Findings
- [Forum anecdote] Complaints of near-unusable unaccelerated guests exist for Monterey and Ventura alike (TrueNAS, 2023), with other users on the same thread finding them acceptable; no cross-version comparison is made. — [TrueNAS community](https://www.truenas.com/community/goto/post?id=679315)
- [Forum anecdote] On real Intel Macs, some users report Sonoma feeling less smooth than Monterey after upgrading, while others in the same thread report no slowdown. — [Apple Community](https://discussions.apple.com/thread/255190423)
- [Low-quality aggregator] A commercial article says older Intel Macs "are likely to notice a slight decrease in performance" on Sequoia; no benchmarks. — [MacKeeper](https://mackeeper.com/blog/sonoma-vs-sequoia/)
- [Forum anecdote] An opposing view on an Adobe forum: Sequoia is "faster in general" than Monterey. — [Adobe community](https://community.adobe.com/t5/photoshop-ecosystem-discussions/is-photoshop-faster-running-on-sequoia/m-p/14921954/highlight/true)
- [Community editorial, excerpt only] For VoiceOver specifically, AppleVis's team found Ventura 13 "somewhat more responsive" than Monterey 12 in some situations, and a Nuance-voice sluggishness bug present before 13.0 was fixed there. — [AppleVis](https://applevis.com/comment/140894), [AppleVis bug page](https://applevis.com/bugs/mac/voiceover-sluggish-when-using-speech-rotor-nuance-voices)

### Inferences
- There are opposing forces for this user. Newer systems add continuously drawn features that are on by default (desktop widgets and aerial wallpapers and screen savers in Sonoma, more background machine-learning daemons), which argues for older versions. But VoiceOver itself received responsiveness fixes and the fast Eloquence voice only from Ventura 13 onward, which argues for Sonoma or Sequoia. On present evidence neither side can be called.
- Because the new visual features are all switchable (previous sections), the practical gap between versions may be small once they are off. This needs measuring on the project's own guests: idle WindowServer percentage and key-to-speech delay on each of 11, 12, 14 and 15 with identical settings.

### Gaps
- No measurement of idle or interactive WindowServer load by macOS version under software rendering was found.
- No information was found on whether WindowServer's software path changed between Big Sur and Sequoia.
- Mojave and Catalina were out of the stated scope and I found no comparative data for them either.

## nvram boot-args and kernel-level settings (serverperfmode and others)

### Takeaway
`serverperfmode=1` is a real, Apple-documented, Intel-only boot argument, but it raises kernel limits for server workloads; nothing indicates it reduces background work or WindowServer load, and one vendor guide says it leaves less memory and processor for other purposes. It is not relevant to this problem, despite appearing in VM optimisation lists.

### Cited Findings
- [Apple documentation] "Turn on performance mode for macOS Server": performance mode "changes the system parameters of your Mac" so it can better use its hardware for demanding server applications. The article "applies only to Mac computers with an Intel processor". OS X 10.11 and later use `nvram`. Check: `nvram boot-args` (on if it shows `serverperfmode=1`). Turn on: `sudo nvram boot-args="serverperfmode=1 $(nvram boot-args 2>/dev/null | cut -f 2-)"`. Turn off: `sudo nvram boot-args="$(nvram boot-args 2>/dev/null | sed -e $'s/boot-args\t//;s/serverperfmode=1//')"`. A restart is required; resetting NVRAM clears it. — [Apple Support 101992](https://support.apple.com/en-us/101992)
- [Vendor guide, excerpt only] Apple does not document every change the mode makes, and the changes depend largely on installed memory; the mode gives extra resources to the network stack, which means "less RAM and CPU available for other purposes". — [Dell PowerScale macOS client guide](https://infohub.delltechnologies.com/en-au/l/powerscale-onefs-macos-client-performance-and-user-experience-optimization/configure-serverperfmode-intel-macs-only-5)
- [Project README] The Docker-OSX optimizer lists "Enable performance mode" with Apple's commands, described as dedicating additional system resources for server applications. No claim of lower processor use is made. — [sickcodes/osx-optimizer README](https://github.com/sickcodes/osx-optimizer)
- [Forum anecdote] If no boot arguments are set, `nvram boot-args` returns an error rather than a value; that simply means performance mode is off. — [Apple Community](https://discussions.apple.com/thread/7566605)

### Inferences
- `serverperfmode=1` should be described in the report as "documented, harmless-looking, but not a load reducer": its purpose is higher process, file and network limits, and with only 4 to 5 GB of memory in the guest the extra kernel reservations could even be counter-productive. Recommend not setting it.
- Setting `boot-args` from inside macOS normally requires System Integrity Protection to permit NVRAM changes for arbitrary arguments; `serverperfmode` is one Apple documents for ordinary use, so it is expected to be allowed, but I did not find a source confirming that on Sonoma or Sequoia. In an OpenCore-booted guest, boot arguments are in practice set in the boot loader's configuration on the host side, and guest-side `nvram` writes persist only if the firmware variable store is writable.

### Gaps
- No source was found describing a boot argument that reduces macOS background activity. `-no_compat_check` only bypasses the hardware compatibility check, and watchdog-related arguments exist for debugging; I found no source tying either to processor load, so both are unverified and probably irrelevant.
- I could not open the Dell page (403), so the list of exact kernel parameters changed by performance mode is not cited here.
- No test of `serverperfmode=1` in a macOS guest, with or without measurement, was found.
