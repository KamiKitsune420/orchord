# QEMU and WHPX settings that lower host processor load and guest lag for an Intel macOS guest on Windows

Method note for the report writer. Most of the QEMU facts below were read directly from the QEMU source at the tag v11.1.0 (downloaded from GitHub and searched locally), not from secondary write-ups. Where a line says "source", it is a documented fact for QEMU 11.1.0. Where it says "hearsay", it is a claim by a project or forum that I could not check against a primary source. Everything under "Inferences" is my own reasoning and has not been measured. The QEMU changelog wiki (wiki.qemu.org/ChangeLog/11.0 and 11.1) could not be read because it is behind a bot check, so release attribution was done from the git history instead: I confirmed with the GitHub compare API which commits are in v11.0.0 and which only arrived in v11.1.0.

Three findings matter more than the rest:

1. QEMU 11.1 added `-accel whpx,ssd=off`, which the QEMU documentation says gives "a significant MMIO performance increase". Every emulated device Orchord uses (AHCI, vmxnet3, xHCI, HPET, applesmc, serial, debugcon) is reached through exactly the kind of exit this speeds up.
2. On a Windows 10 host, QEMU 11.1 turns the Hyper-V interrupt controller off by default, so every interrupt-controller access and every halt goes out to QEMU. On Windows 11 it is on by default. Windows 10 hosts are therefore on a much slower path unless `-machine q35,pic=off` is used.
3. The Windows file driver in QEMU has no discard or write-zeroes support, and the display path under WHPX has no dirty-page tracking. Several settings Orchord uses (`discard=unmap`) or might consider (partial screen updates) therefore do not do on Windows what they do on Linux.

## WHPX accelerator properties in QEMU 10.x and 11.x: what each does to performance

### Takeaway
QEMU 11.1 exposes five WHPX properties: `kernel-irqchip`, `hyperv`, `ignore-unknown-msr`, `intercept-msr-gp` and `ssd`. Only `ssd=off` is documented as a performance switch; `kernel-irqchip` has the largest effect but is chosen automatically and differs between Windows 10 and Windows 11 hosts.

### Inferences
- `ssd=off` is the single most promising QEMU-level change for Orchord. A macOS guest with no paravirtual devices reaches AHCI, vmxnet3, xHCI, HPET, applesmc and the serial port through MMIO and port exits, and the documentation says this is precisely what gets faster. The cost is that branch-predictor flushing between guest and host is dropped and the guest loses the speculative-execution mitigation features. For a single-user desktop running a macOS guest the user installed themselves, that is a modest risk, but it is a real reduction in isolation and should be a deliberate choice (possibly a user-visible option).
- The Windows 10 versus Windows 11 difference is likely to be a large, host-dependent performance gap for Orchord users. On Windows 11 the interrupt controller and its timer are inside the hypervisor. On Windows 10, by default, every APIC register access, every timer re-arm and every halt exits to QEMU. Orchord could test `-machine q35,pic=off` on Windows 10 hosts (OVMF is UEFI, which is what the documentation recommends for that mode). Whether OpenCore and macOS boot without the PIC is untested.
- Hyper-V enlightenments are very unlikely to help macOS. The XNU kernel source lists the hypervisor families it recognises as VMware, Parallels, bhyve, HVF and KVM, with everything else "unknown" (see the timers section), so macOS does not use Hyper-V timers, the idle register or flush hypercalls. `-accel whpx,hyperv=off` would instead let QEMU give macOS the VMware-style frequency leaf. That is a candidate experiment, not a known improvement.
- `ignore-unknown-msr` and `intercept-msr-gp` are correctness and debugging switches. Leaving them at their defaults is right; turning `intercept-msr-gp` on would add exits.
- Anything written about WHPX performance before QEMU 11.0 (older xAPIC-only emulation, Microsoft's emulator library, no enlightenments) describes a substantially different and slower implementation and should not be relied on for 11.1.

### Gaps
- No published measurement of `ssd=off` on a macOS guest, or on any guest, was found. The size of the gain is "significant" in the developers' words only.
- The QEMU changelog wiki pages for 10.0 through 11.1 could not be read (bot protection), so I may have missed release-note wording. The git history was used instead.
- I did not find a qemu-devel thread benchmarking Windows 10 with and without `pic=off`.
- Whether macOS on WHPX reads or writes MSRs that exit on every access is unknown; running once with `-trace whpx_unsupported_msr_access` would answer it.

## Idle handling: what a halted macOS processor costs the host under WHPX

### Takeaway
With the Hyper-V interrupt controller (Windows 11 default), a halted guest processor never returns to QEMU: the hypervisor parks it and wakes it itself, so idle guest processors do not burn host time inside QEMU. With it off (Windows 10 default), each halt and each wake is a round trip through QEMU. There is no halt-polling knob, and `-overcommit cpu-pm` is not implemented for WHPX.

### Cited Findings
- Source (macOS side): when no power-management kext has registered an idle routine, XNU's idle path is "If no power management, re-enable interrupts and halt" (`pal_hlt()`). In a virtual machine the Intel power-management kext does not drive idle, so macOS idles with the HLT instruction. — [XNU osfmk/i386/pmCPU.c](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/i386/pmCPU.c)
- Source: the WHPX run loop's halt exit is labelled "Used for kernel-irqchip=off". With the Hyper-V interrupt controller, the halt exit does not reach QEMU. — [whpx-all.c v11.1.0, lines 2315-2320](https://github.com/qemu/qemu/blob/v11.1.0/target/i386/whpx/whpx-all.c#L2315-L2320)
- Source: QEMU's "is this processor thread idle" hook returns `!whpx_irqchip_in_kernel()`. With the Hyper-V interrupt controller, QEMU never puts the processor thread to sleep itself; the thread stays inside `WHvRunVirtualProcessor` and the hypervisor handles halting. Without it, QEMU marks the processor halted and sleeps the thread until an interrupt arrives. — [whpx-accel-ops.c v11.1.0, lines 82-85](https://github.com/qemu/qemu/blob/v11.1.0/accel/whpx/whpx-accel-ops.c#L82-L85); [whpx-all.c v11.1.0, lines 1907-1925](https://github.com/qemu/qemu/blob/v11.1.0/target/i386/whpx/whpx-all.c#L1907-L1925)
- Source: when QEMU itself has to inject an interrupt while the Hyper-V interrupt controller is in use, it must clear the hypervisor's halt-suspend state by hand ("to get out of HLT we either have to request an interrupt or manually get it away from HLT"). This was added in 11.0 ("Otherwise, interrupts processed through the cancel vCPU and inject path will not cause the vCPU to go out of its halt state"). — [whpx-all.c v11.1.0, lines 1936-1944 and 2039-2051](https://github.com/qemu/qemu/blob/v11.1.0/target/i386/whpx/whpx-all.c#L1936-L1944); [QEMU commit ca7a6add3bd2](https://github.com/qemu/qemu/commit/ca7a6add3bd2)
- Source: QEMU 11.1 exposes Hyper-V's guest idle register (`HV_X64_MSR_GUEST_IDLE`, 0x400000f0). "This enlightenment is only available by the HV when using the Hyper-V LAPIC." It is used only by guests that know about Hyper-V. — [QEMU commit f3e267762566](https://github.com/qemu/qemu/commit/f3e267762566)
- Documented: `-overcommit cpu-pm=on|off` — "Guest ability to manage power state of host cpus (increasing latency for other processes on the same host cpu, but decreasing latency for guest) can be enabled via cpu-pm=on (disabled by default). ... When used, host estimates of CPU cycle and power utilization will be incorrect, not taking into account guest idle time." — [qemu-options.hx v11.1.0, lines 5066-5086](https://github.com/qemu/qemu/blob/v11.1.0/qemu-options.hx#L5066-L5086)
- Source: the WHPX files contain no reference to the `cpu-pm` setting, to MWAIT, or to any halt-polling parameter (searched whpx-all.c, whpx-common.c, whpx-accel-ops.c, and the generic target/i386/cpu.c and host-cpu.c at v11.1.0). The option is parsed in system/vl.c only. — [whpx-all.c v11.1.0](https://github.com/qemu/qemu/blob/v11.1.0/target/i386/whpx/whpx-all.c); [system/vl.c v11.1.0, line 1908](https://github.com/qemu/qemu/blob/v11.1.0/system/vl.c#L1908)
- Source: the EHCI controller model runs a frame timer at 1000 Hz (`FRAME_TIMER_FREQ 1000`) while the guest has its periodic schedule active, and backs off step by step when only the asynchronous schedule is idle (`async_stepdown`, timer interval of (stepdown + 1) milliseconds). — [hw/usb/hcd-ehci.c v11.1.0, lines 41-48 and 2322-2362](https://github.com/qemu/qemu/blob/v11.1.0/hw/usb/hcd-ehci.c#L2322-L2362)
- Source: the xHCI controller model has no per-frame timer; its only timers are a microframe-wrap timer and per-endpoint retry ("kick") timers. — [hw/usb/hcd-xhci.c v11.1.0](https://github.com/qemu/qemu/blob/v11.1.0/hw/usb/hcd-xhci.c)
- Source: the audio subsystem runs a timer at 100 Hz by default ("100Hz -> 10ms") but only while it is needed (the timer is re-armed only when `audio_is_timer_needed`). — [audio/audio.c v11.1.0, lines 405-407](https://github.com/qemu/qemu/blob/v11.1.0/audio/audio.c#L405-L407); [audio/audio-mixeng-be.c v11.1.0, lines 571-605](https://github.com/qemu/qemu/blob/v11.1.0/audio/audio-mixeng-be.c#L571-L605)
- Two QEMU bug reports about an idle guest keeping the host busy exist, but both are for Windows 11 24H2 guests on KVM, not for WHPX and not for macOS. — [QEMU issue 3256](https://gitlab.com/qemu-project/qemu/-/work_items/3256); [QEMU issue 3154](https://gitlab.com/qemu-project/qemu/-/work_items/3154)

### Inferences
- On Windows 11 the remaining idle cost is not QEMU spinning; it is the number of times per second something wakes a guest processor or forces an exit to QEMU. The controllable sources are: emulated device timers that run on QEMU's side (EHCI frame timer, audio timer while a stream is open, HPET if the guest programs it), devices the guest polls through port or MMIO access (applesmc, serial), and QEMU's own main loop (the twice-a-second screendump).
- Orchord passes both `-device qemu-xhci` and `-device usb-ehci`. If nothing is plugged into the EHCI controller, removing it removes one emulated controller that macOS will initialise and that can run a QEMU-side timer. OSX-KVM includes both, so macOS tolerates both; whether macOS is happy with xHCI alone is something Orchord would have to test (Docker-OSX's launch line has only qemu-xhci, which suggests it is).
- `-overcommit cpu-pm=on` should not be tried. Even where it works (KVM) it makes the guest's idle look like 100 percent host use, which is the opposite of the goal.
- If macOS leaves an audio stream open permanently (common when a screen reader is running), the 100 Hz audio timer in QEMU runs permanently. Raising `timer-period` reduces those wakeups at the price of audio latency; see the audio section.

### Gaps
- I found no measurement of host CPU use for an idle macOS guest under WHPX, and no WHPX-specific idle bug report in the QEMU tracker.
- Whether macOS's own timer rate (how often each guest processor wakes when idle) can be lowered from inside the guest is outside the scope of these notes.
- Whether the Windows 10 path (halts handled in QEMU) shows visibly higher idle load was not found measured anywhere.
- I did not verify whether QEMU's Penryn or Skylake-Client models advertise MONITOR/MWAIT to the guest under WHPX. If they did, macOS could try to idle with MWAIT instead of HLT.

## Timers and clocks: HPET, invtsc, vmware-cpuid-freq, -rtc, lost-tick policy

### Takeaway
HPET is on by default and is emulated entirely in QEMU, so `-machine q35,hpet=off` (which quickemu uses for macOS) removes a device that can only add exits; evidence that macOS actually uses it is missing. `+invtsc` is honoured under WHPX. `vmware-cpuid-freq` is already on by default but has no effect on a Windows 11 host unless Hyper-V enlightenments are turned off. KVM's PIT lost-tick policy does not exist under WHPX.

### Cited Findings
- Source: the PC machine enables HPET by default (`pcms->hpet_enabled = true`) and exposes a boolean machine property `hpet`. — [hw/i386/pc.c v11.1.0, lines 1478-1490, 1636 and 1746-1748](https://github.com/qemu/qemu/blob/v11.1.0/hw/i386/pc.c#L1636)
- Practice (not evidence of a measured gain): quickemu disables HPET for macOS guests, with the comment "Disable High Precision Timer", using `hpet=off` on QEMU 7.0 and later and `-no-hpet` before. It does the same for Windows guests. — [quickemu script](https://github.com/quickemu-project/quickemu/blob/master/quickemu)
- Practice: OSX-KVM's launch script does not disable HPET. — [OSX-KVM OpenCore-Boot.sh](https://github.com/kholia/OSX-KVM/blob/master/OpenCore-Boot.sh)
- Source: the list of CPUID leaves that WHPX routes to QEMU includes 0x80000007, the leaf that carries the invariant-TSC bit, and QEMU answers such leaves from its own CPU model, so `+invtsc` on the command line reaches the guest. — [whpx-all.c v11.1.0, lines 3024-3027 and 2484-2506](https://github.com/qemu/qemu/blob/v11.1.0/target/i386/whpx/whpx-all.c#L3024-L3027)
- Hearsay from a maintained project: "A CPU with invtsc is required for macOS to boot". — [quickemu script](https://github.com/quickemu-project/quickemu/blob/master/quickemu)
- Source (macOS side): XNU reads the "VMM generic" leaf 0x40000010 only "if (max_vmm_leaf >= 0x40000010)", taking the TSC frequency from EAX and the bus frequency from EBX. The hypervisor families it names are VMware, Parallels, bhyve, HVF and KVM; anything else is "unknown". There is no Hyper-V family. — [XNU osfmk/i386/cpuid.c](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/i386/cpuid.c)
- Source (macOS side): if both frequencies from that leaf are non-zero, XNU uses them and returns immediately; otherwise it calibrates by CPU family. For the Skylake family it computes the TSC frequency from CPUID leaf 0x15 and a reference clock taken from the firmware property "ARTFrequency" or a built-in default. — [XNU osfmk/i386/tsc.c](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/i386/tsc.c)
- Source: under WHPX the VMware-style frequency leaf is produced by QEMU only when Hyper-V enlightenments are not enabled; the comment says "Use vmware_cpuid_freq as a proxy to report VMware. This is to get the TSC/APIC frequency query functionality provided through vmport". With enlightenments enabled the three hypervisor leaves are passed through from Windows. — [whpx-all.c v11.1.0, lines 2508-2560](https://github.com/qemu/qemu/blob/v11.1.0/target/i386/whpx/whpx-all.c#L2508-L2560)
- Source: this Windows 10 path was restored in 11.1: "reintroduce enlightenments for Windows 10 ... Pretend to be vmware to be able to use vmport's functionality. If the vmware frequency leaf is disabled, pretend to be KVM, with the only capability reported being X2APIC support." — [QEMU commit f741457c1a17](https://github.com/qemu/qemu/commit/f741457c1a17)
- Source: QEMU takes the guest TSC frequency from Windows (`WHvCapabilityCodeProcessorClockFrequency`) and the APIC timer frequency from `WHvCapabilityCodeInterruptClockFrequency`; "When not using the Hyper-V APIC, the frequency is 1 GHz". — [whpx-all.c v11.1.0, lines 2770-2803](https://github.com/qemu/qemu/blob/v11.1.0/target/i386/whpx/whpx-all.c#L2770-L2803)
- Practice: OSX-KVM, Docker-OSX and quickemu all pass `vmware-cpuid-freq=on` for macOS; quickemu's comment is "vmware-cpuid-freq=on enables VMware TSC frequency reporting for macOS timing". All three target KVM. — [OSX-KVM OpenCore-Boot.sh](https://github.com/kholia/OSX-KVM/blob/master/OpenCore-Boot.sh); [Docker-OSX Dockerfile](https://github.com/sickcodes/Docker-OSX/blob/master/Dockerfile); [quickemu script](https://github.com/quickemu-project/quickemu/blob/master/quickemu)
- Documented: `-rtc [base=utc|localtime|datetime][,clock=host|rt|vm][,driftfix=none|slew]`; "Enable driftfix (i386 targets only) if you experience time drift" problems. — [qemu-options.hx v11.1.0, lines 5285-5312](https://github.com/qemu/qemu/blob/v11.1.0/qemu-options.hx#L5285-L5312)
- Practice: quickemu passes `-rtc base=localtime,clock=host,driftfix=slew` in one branch and `-rtc base=utc,clock=host` in the other. — [quickemu script, lines 1758-1761](https://github.com/quickemu-project/quickemu/blob/master/quickemu)

### Inferences
- `hpet=off` is low risk and worth testing: OVMF and macOS both work without HPET in quickemu's configuration. Under WHPX each HPET register access is an exit to QEMU and each HPET timer is a QEMU-side timer, so if macOS touches it at all, removing it helps; if macOS never touches it, removing it costs nothing. Note the XNU tree does contain an hpet.c file, so the kernel has some HPET code; how much it is exercised in a virtual machine is not established.
- On a Windows 11 host with default settings, macOS probably does not get its clock frequencies from the hypervisor leaf, because Hyper-V's own leaf range is unlikely to reach 0x40000010. macOS then calibrates on its own. A wrong calibration shows up as clock drift or timers firing at the wrong rate rather than as raw load, but it is a plausible contributor to "lag" (animations and audio scheduled against a slightly wrong clock). Testing `-accel whpx,hyperv=off` to see whether macOS's boot log then prints a "VMM vendor ... TSC frequency" line with sensible values is a cheap experiment.
- `-rtc` options affect the emulated real-time clock chip only. macOS keeps time from the TSC, so `-rtc` choices are unlikely to change load. `driftfix=slew` exists for Windows guests and is not relevant.
- `-global kvm-pit.lost_tick_policy=...` configures the in-kernel KVM timer chip and is KVM-only; under WHPX the timer chip is QEMU's ordinary emulated one and has no such setting. Not applicable.

### Gaps
- No source measured the exit rate of a macOS guest with HPET on versus off.
- What Hyper-V returns to a WHPX guest for leaf 0x40000000's maximum leaf and for leaf 0x40000010 was not found documented; it needs a one-off check in a running guest.
- Whether `hyperv=off` changes anything else macOS relies on is untested.

## Processor count and topology

### Takeaway
No source gives measured guidance on processor count for macOS under WHPX. What is documented is that Windows client schedules guest processors as ordinary threads through the normal Windows scheduler, which is how hybrid performance and efficiency cores get involved, and that QEMU 11.1 rewrote WHPX's CPUID handling, so the "one core per socket only" restriction may be worth re-testing.

### Cited Findings
- Documented by Microsoft: "Starting with Windows 10, version 1803, the root scheduler is used by default on client systems only", and "When you enable the root scheduler type, the hypervisor gives the root partition control of work scheduling. In the root partition OS instance, the NT scheduler manages all aspects of assigning work to system logical processors." One of the two stated reasons is "It's important to properly operate future systems with heterogenous core architectures." — [Microsoft Learn, Manage Hyper-V hypervisor scheduler types](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/manage/manage-hyper-v-scheduler-types)
- Documented by Microsoft: "This configuration is the only supported hypervisor scheduler configuration for client systems. Administrators shouldn't attempt to override the default hypervisor scheduler type on Windows client systems." and per-virtual-machine processor caps, weights and reserves "aren't supported when you enable the hypervisor root scheduler". — [Microsoft Learn, Manage Hyper-V hypervisor scheduler types](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/manage/manage-hyper-v-scheduler-types)
- Source: QEMU gives the partition exactly the `-smp` processor count (`prop.ProcessorCount = ms->smp.cpus`). — [whpx-all.c v11.1.0, lines 3096-3108](https://github.com/qemu/qemu/blob/v11.1.0/target/i386/whpx/whpx-all.c#L3096-L3108)
- Bug report (QEMU 7.0, Windows 11 host, no maintainer reply): with WHPX, `-smp 4` or `-smp sockets=1,cores=4,threads=1` made each processor appear as a separate single-core CPU in the guest. — [QEMU issue 1137](https://gitlab.com/qemu-project/qemu/-/issues/1137)
- Source: QEMU 11.1 added "whpx: i386: introduce proper cpuid support" and now routes the topology leaves (1 and 0xb, among others) to QEMU's own CPU model. — [QEMU commit history for target/i386/whpx at v11.1.0](https://github.com/qemu/qemu/commits/v11.1.0/target/i386/whpx); [whpx-all.c v11.1.0, lines 3024-3027](https://github.com/qemu/qemu/blob/v11.1.0/target/i386/whpx/whpx-all.c#L3024-L3027)
- Hearsay from a maintained project: "macOS guests cannot boot with most core counts not powers of 2", so quickemu rounds the count down to a power of two. — [quickemu script, lines 764-776](https://github.com/quickemu-project/quickemu/blob/master/quickemu)
- Practice: OSX-KVM defaults to `-smp 4,cores=2,sockets=1` (two cores, four threads); Docker-OSX defaults to `-smp 4,cores=4`. OSX-KVM's notes describe passing a 6-core, 12-thread host through with explicit sockets, cores and threads. — [OSX-KVM OpenCore-Boot.sh](https://github.com/kholia/OSX-KVM/blob/master/OpenCore-Boot.sh); [Docker-OSX Dockerfile](https://github.com/sickcodes/Docker-OSX/blob/master/Dockerfile); [OSX-KVM notes.md](https://github.com/kholia/OSX-KVM/blob/master/notes.md)

### Inferences
- Because guest processors are Windows threads under the root scheduler, the things that steer any Windows thread on a hybrid chip steer them too: process priority, whether Windows classes the process as background, and Windows 11's efficiency mode and power throttling. If Windows parks QEMU's processor threads on efficiency cores (for example because the QEMU window is hidden and Orchord, not QEMU, is in the foreground), a software-rendered macOS desktop will feel much slower. Raising the QEMU process priority class, or opting the process out of power throttling, is a host-side lever outside QEMU's own options; it is an inference from Microsoft's description, not a tested result.
- On the i7-1355U there are only two performance cores. Four guest processors cannot all be on performance cores without sharing hyper-threads. Fewer guest processors (two) would fit the performance cores but give macOS's software renderer less parallelism; more than four would increase idle wakeups and contention with the host. Four is a defensible middle; the honest position is that this needs measuring on the target machine.
- The observed panics with layouts other than one core per socket may have been caused by the old WHPX topology reporting described in issue 1137. Since 11.1 answers the topology leaves from QEMU's model, `-smp 4,sockets=1,cores=4,threads=1` is worth one re-test. A single-socket layout matters little for load but removes an oddity (four sockets) that macOS power and scheduling code was never designed around.

### Gaps
- No source measured host load against guest processor count for macOS on WHPX or on any hypervisor without graphics acceleration.
- No Microsoft or QEMU documentation was found on how WHPX processor threads are placed on performance versus efficiency cores, or on any QEMU option to pin them on Windows (QEMU has no processor-pinning option of its own on Windows that I found).
- Whether issue 1137 is fixed in 11.1 is not stated in the tracker.

## Disk: controller, image format, cache and asynchronous I/O options on Windows

### Takeaway
macOS has had an Apple VirtIO block driver since Mojave (reliable from Catalina), and both OSX-KVM and quickemu describe virtio-blk as the faster choice. On Windows, `aio=native` exists and means Windows overlapped I/O; `discard=unmap` and `detect-zeroes=unmap` cannot return space to the host because the Windows file driver implements neither discard nor write-zeroes; and the qcow2 metadata cache is capped at 8 MB instead of 32 MB.

### Cited Findings
- Hearsay from a maintained project: "Newer macOS (namely Mojave+) have support for some virtio drivers. This can be enabled by applying the following change ... to get some performance gain", replacing `-device ide-hd,bus=sata.4,drive=MacHDD` with `-device virtio-blk-pci,drive=MacHDD`. No numbers are given. — [OSX-KVM notes.md, "Using virtio-blk-pci with macOS"](https://github.com/kholia/OSX-KVM/blob/master/notes.md)
- Hearsay from a maintained project: "VirtIO Block Media doesn't work in High Sierra (at all) or the Mojave (Recovery Image)". quickemu uses `virtio-blk-pci` for the system disk on Catalina, Big Sur, Monterey, Ventura, Sonoma, Sequoia and Tahoe, and `ide-hd` on AHCI for older releases. — [quickemu script, lines 1088-1126](https://github.com/quickemu-project/quickemu/blob/master/quickemu)
- Practice: quickemu keeps the OpenCore boot disk and the recovery image on AHCI (`ide-hd`) and puts only the system disk on virtio-blk. — [quickemu script, lines 2005-2018](https://github.com/quickemu-project/quickemu/blob/master/quickemu)
- Practice: OSX-KVM's default script and Docker-OSX still use `ide-hd` on `ich9-ahci` for all disks, the same as Orchord. — [OSX-KVM OpenCore-Boot.sh](https://github.com/kholia/OSX-KVM/blob/master/OpenCore-Boot.sh); [Docker-OSX Dockerfile](https://github.com/sickcodes/Docker-OSX/blob/master/Dockerfile)
- Source: on Windows the file driver accepts `aio=threads` and `aio=native` (help text "host AIO implementation (threads, native)"); the default is threads unless native was requested. `native` opens the file with `FILE_FLAG_OVERLAPPED` and uses QEMU's Windows asynchronous I/O layer; `threads` runs blocking `ReadFile`/`WriteFile` calls on QEMU's worker thread pool. — [block/file-win32.c v11.1.0, lines 72-170 and 232-300](https://github.com/qemu/qemu/blob/v11.1.0/block/file-win32.c#L232-L300); [block/win32-aio.c v11.1.0](https://github.com/qemu/qemu/blob/v11.1.0/block/win32-aio.c)
- Documented, and misleading for Windows: "aio is "threads", "native", or "io_uring" and selects between pthread based disk I/O, native Linux AIO, or Linux io_uring API." `io_uring` is Linux-only and not applicable on Windows; `native` on Windows is the overlapped-I/O path above. — [qemu-options.hx v11.1.0, lines 1776-1778](https://github.com/qemu/qemu/blob/v11.1.0/qemu-options.hx#L1776-L1778)
- Source: `cache=none` or `cache=directsync` (cache.direct=on) maps to `FILE_FLAG_NO_BUFFERING` on Windows. — [block/file-win32.c v11.1.0, lines 232-251](https://github.com/qemu/qemu/blob/v11.1.0/block/file-win32.c#L232-L251)
- Documented: "The default mode is cache=writeback." — [qemu-options.hx v11.1.0, line 1774](https://github.com/qemu/qemu/blob/v11.1.0/qemu-options.hx#L1774)
- Source: the Windows file driver's operation table contains open, close, create, read, write, flush, truncate and size queries, and no discard and no write-zeroes operation. — [block/file-win32.c v11.1.0, lines 715-735](https://github.com/qemu/qemu/blob/v11.1.0/block/file-win32.c#L715-L735)
- Documented: `detect-zeroes` "enables the automatic conversion of plain zero writes by the OS to driver specific optimized zero write commands. You may even choose "unmap" if discard is set to "unmap" to allow a zero write to be converted to an unmap operation." — [qemu-options.hx v11.1.0, lines 1550-1555](https://github.com/qemu/qemu/blob/v11.1.0/qemu-options.hx#L1550-L1555)
- Documented: "The maximum L2 cache size is 32 MB by default on Linux platforms (enough for full coverage of 256 GB images, with the default cluster size). ... On non-Linux platforms the maximal value is smaller by default (8 MB)". The cache can be raised with `l2-cache-size`. `cache-clean-interval` "is a Linux-specific feature, so cache-clean-interval is not supported on other systems." — [docs/qcow2-cache.txt v11.1.0](https://github.com/qemu/qemu/blob/v11.1.0/docs/qcow2-cache.txt)
- Practice: quickemu's drive options are `discard=unmap,detect-zeroes=unmap,cache=writeback,aio=threads` (on Linux and macOS hosts). — [quickemu script, line 1925](https://github.com/quickemu-project/quickemu/blob/master/quickemu)
- Source: under WHPX each port-I/O exit is handled synchronously on the processor thread (`whpx_handle_portio` calls the device model directly), and MMIO exits go through QEMU's instruction emulator. There is no in-kernel shortcut for device notifications as on KVM. — [whpx-all.c v11.1.0, lines 1106-1150](https://github.com/qemu/qemu/blob/v11.1.0/target/i386/whpx/whpx-all.c#L1106-L1150)

### Inferences
- virtio-blk is the most credible disk-side saving for Sonoma, Sequoia, Monterey and Big Sur. An AHCI command costs several register accesses (issue, interrupt status, acknowledgement), each one an exit to QEMU plus instruction emulation; a virtio request costs about one notification. Under WHPX exits are expensive, so the relative gain should be at least as large as on KVM, where OSX-KVM calls it "some performance gain". The safe shape is quickemu's: keep the OpenCore disk (vvfat) on AHCI and move only the qcow2 system disk. The risks are an existing installation failing to boot if the virtio driver is not in the boot-time kernel collection, and installers or recovery environments that lack the driver; test per macOS release.
- With the default 64 KB clusters, 8 MB of L2 cache covers a 64 GB image (the document's ratio is 32 MB for 256 GB). A macOS system disk larger than 64 GB will fall out of cache on scattered I/O and pay extra reads plus extra QEMU work. Setting `l2-cache-size` to the image's full requirement (1 MB per 8 GB) removes that; the memory cost is small.
- `discard=unmap` on Windows makes qcow2 do its own bookkeeping for each TRIM that macOS sends, but the host file cannot shrink because the layer underneath has no discard. It is not harmful (freed clusters are reused inside the image), but it is processor and metadata work with a smaller payoff than on Linux. `detect-zeroes=unmap` would add a scan of every write buffer for zeroes for a similar partial payoff; I would not add it for load reasons.
- `aio=native` with `cache=none` avoids copying through the Windows file cache and avoids worker-thread hand-offs, which is usually lower processor use per request. It also removes host caching of the image, which can make a lightly loaded guest feel slower on a laptop with 16 GB. This is a measure-it choice, not a clear win. The source I read did not show a check that `aio=native` requires `cache=none` on Windows as it does on Linux, but I did not read every line.
- qcow2 costs more per request than raw (table lookups, allocation on first write). With a warm, adequately sized L2 cache the steady-state difference is small. Raw loses snapshots and thin provisioning, which Orchord probably values more.
- NVMe emulation (`-device nvme`) is another non-AHCI option that every macOS release in scope supports natively, but it is also plain MMIO emulation with no shared-ring design, so I would expect it to sit between AHCI and virtio-blk. Unverified.

### Gaps
- No benchmark of AHCI versus virtio-blk versus NVMe for a macOS guest was found, on WHPX or KVM. All "faster" statements are qualitative.
- The exact macOS point release that first shipped a working VirtIO block driver was not pinned down from an Apple source; the two project sources agree on "Mojave, but really Catalina and later".
- Whether macOS issues TRIM on virtio-blk, and whether APFS behaves differently on virtio versus AHCI, was not found.
- Whether a dedicated I/O thread (`iothread`) for virtio-blk gives any benefit on Windows without KVM-style notifications was not found.
- The processor cost of the vvfat driver used for the OpenCore boot disk was not found; it should only matter during boot.

## Display device and getting frames out

### Takeaway
No evidence was found that the choice among vmware-svga, standard VGA and bochs-display changes steady-state load for macOS, because without a guest driver the VMware device simply runs as standard VGA and the guest draws into plain memory. The real costs are macOS's own software rendering (driven by pixel count) and Orchord's screendump, which converts and writes the whole frame, about 6.2 MB at 1920 by 1080, every time. A VNC or D-Bus display backend is the built-in alternative.

### Cited Findings
- Source: the VMware SVGA device model, when the guest has not switched on SVGA mode, does this on every refresh: "in standard vga mode" — it calls the standard VGA update function. — [hw/display/vmware_vga.c v11.1.0, lines 1142-1162](https://github.com/qemu/qemu/blob/v11.1.0/hw/display/vmware_vga.c#L1142-L1162)
- Source: the VMware SVGA device's video memory property `vgamem_mb` defaults to 16 MB. — [hw/display/vmware_vga.c v11.1.0, lines 1341-1342](https://github.com/qemu/qemu/blob/v11.1.0/hw/display/vmware_vga.c#L1341-L1342)
- Practice with a stated reason: quickemu uses `vmware-svga` for macOS with the comment "macOS has native VMware display driver support; aligns with OSX-KVM". OSX-KVM's notes say of a Ventura resolution-switching problem, "Switching to vmware-svga device seems to have "fixed" the following problem!". Neither gives a performance reason, and I could not confirm from an Apple source that macOS ships a VMware SVGA driver. — [quickemu script, lines 1301-1303](https://github.com/quickemu-project/quickemu/blob/master/quickemu); [OSX-KVM notes.md, "Resolution in Ventura"](https://github.com/kholia/OSX-KVM/blob/master/notes.md)
- Source: WHPX has no dirty-page tracking. Its memory listener's sync function marks the whole region dirty every time, and WHPX registers a migration blocker whose text begins "State blocked due to missing dirty memory tracking support". — [whpx-common.c v11.1.0, lines 355-366](https://github.com/qemu/qemu/blob/v11.1.0/accel/whpx/whpx-common.c#L355-L366); [whpx-all.c v11.1.0, lines 2742-2745](https://github.com/qemu/qemu/blob/v11.1.0/target/i386/whpx/whpx-all.c#L2742-L2745)
- Documented known issue: "In guests using VGA modes that QEMU doesn't pass through framebuffer memory for, performance will be quite suboptimal. Workaround: for affected guests, use a more modern graphics mode." — [QEMU docs, docs/system/whpx.rst v11.1.0](https://github.com/qemu/qemu/blob/v11.1.0/docs/system/whpx.rst)
- Source: the `screendump` command schedules a display update, waits for it, takes a reference to the display surface, creates the output file, and then either writes PNG through libpng or, by default, writes PPM by converting each row to 24-bit RGB and writing it row by row. The code notes the picture can change underneath it while it writes. — [ui/ui-qmp-cmds.c v11.1.0, lines 292-390](https://github.com/qemu/qemu/blob/v11.1.0/ui/ui-qmp-cmds.c#L292-L390); [ui/console.c v11.1.0, lines 146-177](https://github.com/qemu/qemu/blob/v11.1.0/ui/console.c#L146-L177)

- Source: the VNC server is part of the common user-interface sources and is built on any host where VNC support is enabled. — [ui/meson.build v11.1.0, lines 75-91](https://github.com/qemu/qemu/blob/v11.1.0/ui/meson.build#L75-L91)
- Source, not applicable on Windows: QEMU's Apple paravirtual graphics device (`apple-gfx-pci`) is only built when the host provides Apple's ParavirtualizedGraphics framework (the `pvg` dependency), that is, on a macOS host. — [hw/display/meson.build v11.1.0, lines 65-66](https://github.com/qemu/qemu/blob/v11.1.0/hw/display/meson.build#L65-L66)
- Hearsay, not applicable on Windows today but a notable lead: a custom Linux build of QEMU ("qemux/qemu-macos") advertises "Reims vGPU", "a paravirtualized GPU implementation for macOS guests" that "uses the stock AppleParavirtGPU.kext already present in the guest, so no custom guest kernel extension is required", translating Metal to Vulkan on the host. It requires Linux, KVM, a Vulkan 1.2 host driver and memfd-backed guest memory. — [Docker Hub, qemux/qemu-macos](https://hub.docker.com/r/qemux/qemu-macos)
- Practice: quickemu notes "macOS doesn't support SPICE" in its display handling. — [quickemu script, line 1782](https://github.com/quickemu-project/quickemu/blob/master/quickemu)

### Inferences
- If macOS has no VMware SVGA driver loaded (which I believe is the case without VMware Tools, though quickemu's comment says otherwise), then with `vmware-svga` the guest is drawing into a linear frame buffer exactly as it would with `-device VGA`. The device choice then affects which resolutions the firmware offers and how much video memory there is, not processor load. Switching device for load reasons is not supported by any evidence found.
- The lever that does matter with software rendering is the number of pixels. Every window composite is done by the guest's processors, so halving the resolution roughly halves that work. This is the display-side change most likely to reduce load, and it is a guest-resolution setting (OVMF/OpenCore resolution), not a QEMU device flag.
- 16 MB of video memory holds 1920 by 1080 at 32 bits (about 8.3 MB) but not 2560 by 1600 (about 16.4 MB). Raising `vgamem_mb` does not reduce load.
- Screendump cost per call at 1920 by 1080: one full-frame display update (the whole frame is always "dirty" under WHPX), a per-pixel conversion of about 2 million pixels on QEMU's main thread, and a 6,220,800-byte file write, followed by Orchord reading and decoding that file. Twice a second that is about 12 MB of file traffic per second and periodic main-thread stalls that can delay device emulation slightly. It is not large, but it is pure overhead when the picture has not changed. The PNG format option would shrink the file and cost more processor time.
- A lighter built-in route is the VNC server (`-display none -vnc 127.0.0.1:N`, or `-vnc` on a named pipe or loopback socket): QEMU keeps its own copy of the last frame, compares, and sends only the rectangles that changed, so an unchanged screen costs a comparison and no file. The D-Bus display with shared memory avoids even the copy across the socket, but needs a QEMU build with D-Bus display support and a D-Bus client in Orchord, which is a much bigger change. Both are inferences about cost; neither was measured.
- The "legacy VGA modes" warning only concerns early boot text modes, not the macOS desktop.

### Gaps
- No source compared vmware-svga, standard VGA, bochs-display and virtio-vga for a macOS guest's processor load.
- Whether any macOS release in scope ships a driver that actually binds to QEMU's `vmware-svga` or to `virtio-vga`/`virtio-gpu` on Intel was not confirmed from a primary source. One search found nothing either way; both major projects use `vmware-svga` and none uses virtio graphics for macOS.
- Whether the Windows QEMU 11.1 binary that Orchord ships includes the D-Bus display or SPICE was not checked; `qemu-system-x86_64 -display help` on the shipped binary answers it.
- No measurement of screendump cost was found.

## Network device

### Takeaway
macOS has a VirtIO network driver from Big Sur onward, and both OSX-KVM and quickemu now default to `virtio-net-pci` for those releases, keeping `vmxnet3` for older ones. No source measured the processor cost of either.

### Cited Findings
- Hearsay from a maintained project: "VirtIO Network is supported since Big Sur"; quickemu uses `virtio-net-pci` for Big Sur, Monterey, Ventura, Sonoma, Sequoia and Tahoe, and `vmxnet3` for Catalina and older. — [quickemu script, lines 1088-1126](https://github.com/quickemu-project/quickemu/blob/master/quickemu)
- Practice: OSX-KVM's default is `-netdev user,... -device virtio-net-pci,...`, with a commented alternative "-device vmxnet3 ... # Note: Use this line for High Sierra". — [OSX-KVM OpenCore-Boot.sh](https://github.com/kholia/OSX-KVM/blob/master/OpenCore-Boot.sh)
- Practice: Docker-OSX defaults to `vmxnet3` (`-device ${NETWORKING:-vmxnet3}`). — [Docker-OSX Dockerfile, line 213](https://github.com/sickcodes/Docker-OSX/blob/master/Dockerfile)

### Inferences
- For Big Sur, Monterey, Sonoma and Sequoia, `virtio-net-pci` is the better-supported and probably cheaper device: fewer register accesses per packet than vmxnet3's emulated hardware model, which under WHPX means fewer exits. The gain only shows while the network is busy; an idle network device costs nothing either way.
- With `-netdev user` the ceiling is QEMU's built-in user-mode network stack, which runs on QEMU's main thread, so heavy downloads load that thread whichever device model is used.
- e1000-family devices (`e1000-82545em`, `e1000e`) are full hardware emulations with many register accesses per packet and would be expected to be the most expensive of the three families; no project examined uses them for current macOS.

### Gaps
- No throughput or processor measurements for vmxnet3 versus virtio-net versus e1000 in a macOS guest were found.
- Whether macOS's VirtIO network driver has any known stability problems under QEMU without KVM (for example with the features WHPX cannot accelerate) was not found.

## Audio

### Takeaway
QEMU 11.1 has two real Windows audio backends, DirectSound (`dsound`) and SDL; there is no WASAPI backend. The audio engine wakes 100 times a second by default while a stream is open, and DirectSound's default playback buffer is about 93 ms plus 10 ms of added latency. quickemu uses `virtio-sound-pci` for Monterey and later; no latency figures were found anywhere.

### Cited Findings

Of these only dsound and sdl are Windows sound outputs. There is no WASAPI entry. — [audio/meson.build v11.1.0](https://github.com/qemu/qemu/blob/v11.1.0/audio/meson.build)
- Source: `timer-period` is "timer period (in microseconds, 0: use lowest possible)" and defaults to 10000 ("100Hz -> 10ms"). — [qapi/audio.json v11.1.0, lines 495-507](https://github.com/qemu/qemu/blob/v11.1.0/qapi/audio.json#L495-L507); [audio/audio.c v11.1.0, lines 405-407](https://github.com/qemu/qemu/blob/v11.1.0/audio/audio.c#L405-L407)
- Source: the audio timer is armed only while a voice needs it and is stopped otherwise. — [audio/audio-mixeng-be.c v11.1.0, lines 571-605](https://github.com/qemu/qemu/blob/v11.1.0/audio/audio-mixeng-be.c#L571-L605)
- Source: DirectSound options are `in`, `out` and `latency`: "add extra latency to playback in microseconds (default 10000)". — [qapi/audio.json v11.1.0, lines 185-202](https://github.com/qemu/qemu/blob/v11.1.0/qapi/audio.json#L185-L202)
- Source: the DirectSound playback buffer is sized from `out.buffer-length`, defaulting to 92880 microseconds (4096 frames at 44.1 kHz). — [audio/dsound_template.h v11.1.0, line 198](https://github.com/qemu/qemu/blob/v11.1.0/audio/dsound_template.h#L198)
- Source: per-direction options include `mixing-engine` (default on), `fixed-settings` (default true), `frequency` (default 44100), `channels` (default 2), `voices` (default 1), `format` (default s16) and `buffer-length` ("the buffer length in microseconds"). The SDL backend adds `buffer-count` ("number of buffers (default 4)"). — [qapi/audio.json v11.1.0, lines 16-52 and 392-404](https://github.com/qemu/qemu/blob/v11.1.0/qapi/audio.json#L16-L52)
- Hearsay from a maintained project: "macOS 12+ (Monterey onwards) supports virtio-sound-pci natively"; for Big Sur, "Big Sur uses VirtIO but usb-audio/VoodooHDA don't work reliably. Fall back to ich9-intel-hda which may work with VoodooHDA". — [quickemu script, lines 1095-1112](https://github.com/quickemu-project/quickemu/blob/master/quickemu)
- Hearsay from a maintained project, about the Intel HDA route: "The emulated sound output can be choppy, and distorted. Use Sound Card / USB Sound Card passthrough instead." — [OSX-KVM notes.md, "Virtual Sound Device"](https://github.com/kholia/OSX-KVM/blob/master/notes.md)

### Inferences
- Orchord's current pairing (`dsound` with `virtio-sound-pci`) matches what quickemu does for Monterey and later, so the device choice is already the recommended one for those releases. Big Sur is the odd one out: quickemu does not trust virtio-sound there.
- Approximate output latency with defaults is the guest's own buffering, plus up to one 10 ms timer period, plus the DirectSound buffer fill (up to about 93 ms), plus the 10 ms `latency` setting, plus Windows's own mixer. For a screen-reader user that is a noticeable delay. The knobs are `out.buffer-length` (smaller means less delay and more risk of crackle when the host is busy), `latency`, and `timer-period`. Lower `timer-period` cuts delay and raises wakeups; higher does the reverse. These pull in opposite directions for the two goals in this research (less load versus less lag), so they need to be chosen by ear on the target laptop.
- If the guest's sample rate differs from the backend's fixed 44100 Hz, QEMU resamples every buffer. Setting `out.frequency` to what macOS actually outputs (commonly 48000) removes the resampling step. The saving is small.
- SDL's audio layer on Windows normally sits on WASAPI, so `-audiodev sdl` is the nearest thing to a WASAPI backend, if the shipped QEMU was built with SDL. I did not confirm this from an SDL source in this pass, and no evidence was found that it gives lower latency in QEMU.
- virtio-sound exchanges whole buffers through shared rings, so it should cost fewer exits than Intel HDA emulation (which is register-driven). Unmeasured.

### Gaps
- No published latency or processor figures for QEMU's dsound or sdl backends, or for virtio-sound versus Intel HDA with a macOS guest, were found.
- Whether a WASAPI backend has been proposed for QEMU was not searched.
- Whether macOS keeps the audio stream open when silent (which would keep the 100 Hz timer running permanently) is not established.

## Memory: preallocation, large pages, and whether WHPX pins guest memory

### Takeaway
`-mem-prealloc` works on Windows (QEMU touches every page once at start-up), but file-backed memory, shared-memory backends and large pages are not available in the Windows build. Whether Windows pins memory mapped into a WHPX partition was not found documented.

### Cited Findings
- Source: on Windows, guest memory is allocated with `VirtualAlloc(NULL, size, MEM_COMMIT, PAGE_READWRITE)`; there is no large-page flag. — [util/oslib-win32.c v11.1.0, lines 47-63](https://github.com/qemu/qemu/blob/v11.1.0/util/oslib-win32.c#L47-L63)
- Source: preallocation on Windows is a single-threaded loop that writes one byte to every page; "async prealloc not supported". — [util/oslib-win32.c v11.1.0, lines 268-286](https://github.com/qemu/qemu/blob/v11.1.0/util/oslib-win32.c#L268-L286)
- Source: the file-backed and shared-memory backends (`hostmem-file.c`, `hostmem-shm.c`) are compiled only when the host is not Windows, and the memfd backend is Linux-only. `-mem-path` therefore has nothing behind it on Windows. — [backends/meson.build v11.1.0](https://github.com/qemu/qemu/blob/v11.1.0/backends/meson.build)
- Source: WHPX maps each block of guest memory into the partition with `WHvMapGpaRange`, using QEMU's own allocation as the backing. — [whpx-common.c v11.1.0, lines 322-332](https://github.com/qemu/qemu/blob/v11.1.0/accel/whpx/whpx-common.c#L322-L332)
- Documented by Microsoft: creating a mapping "sets a region in the caller's process as the backing memory" for the guest address range. — [Microsoft Learn, WHvMapGpaRange](https://learn.microsoft.com/en-us/virtualization/api/hypervisor-platform/funcs/whvmapgparange)
- Documented: `-overcommit mem-lock=on|off|on-fault` — "Locking qemu and guest memory can be enabled via mem-lock=on or mem-lock=on-fault (disabled by default). This works when host memory is not overcommitted and reduces the worst-case latency for guest." — [qemu-options.hx v11.1.0, lines 5066-5078](https://github.com/qemu/qemu/blob/v11.1.0/qemu-options.hx#L5066-L5078)
- Practice: quickemu disables 1 GB pages for macOS guests (`-pdpe1gb`) with the comment "Disable huge pages (,-pdpe1gb) on macOS to prevent crashes". That is a guest CPU feature flag, not a host large-page setting. — [quickemu script, lines 616-626](https://github.com/quickemu-project/quickemu/blob/master/quickemu)
- Practice: quickemu adds `-device virtio-balloon` for Big Sur and later ("VirtIO Memory Balloning is supported since Big Sur"). — [quickemu script, lines 1092-1108](https://github.com/quickemu-project/quickemu/blob/master/quickemu)

### Inferences
- `-mem-prealloc` moves the cost of first-touch page faults from run time to start-up: 4 GB is about a million page touches, done once. It makes the guest's early minutes smoother and makes the full 4 GB resident immediately, which on a 16 GB laptop is affordable. It does not reduce steady-state load.
- Large pages for guest memory, which help on Linux by cutting address-translation overhead, are simply not reachable from QEMU on Windows today.
- The guest's 4 GB is committed against the Windows commit limit from the start regardless of preallocation, because the allocation uses commit, even though untouched pages use no physical memory.
- Guest memory size itself matters for lag: with 4 GB, Sonoma and Sequoia will compress and swap under modest use, and swap traffic through an emulated AHCI disk is exactly the expensive path described in the disk section. More memory may reduce load more than any memory option. This is an inference, not a sourced fact.

### Gaps
- Whether Windows pins, or can page out, memory mapped into a WHPX partition was not found in Microsoft's documentation.
- Whether `-overcommit mem-lock=on` does anything on Windows was not checked in the source.
- No source measured the effect of preallocation on a WHPX guest.

## Debug outputs: serial to file, debug console, verbose boot

### Takeaway
Each byte sent to the debug console or the serial port is at least one exit from the guest to QEMU followed by a blocking file write. These cost nothing while nothing is printed, but a chatty boot or a guest logging to serial pays per character.

### Cited Findings
- Source: the debug console's write handler writes one character per port write with a blocking call, and the code carries the comment "XXX this blocks entire thread. Rewrite to use qemu_chr_fe_write and background I/O callbacks". — [hw/char/debugcon.c v11.1.0, lines 55-70](https://github.com/qemu/qemu/blob/v11.1.0/hw/char/debugcon.c#L55-L70)
- Source: under WHPX a port write exits to QEMU and is handled on the guest processor's thread (`whpx_handle_portio` → device handler), after which QEMU advances the instruction pointer with a further register write to the hypervisor. — [whpx-all.c v11.1.0, lines 1100-1150](https://github.com/qemu/qemu/blob/v11.1.0/target/i386/whpx/whpx-all.c#L1100-L1150)
- Source: on Windows a file character device is opened with `CreateFile` and written with `WriteFile` per call. — [chardev/char-file.c v11.1.0, lines 55-68](https://github.com/qemu/qemu/blob/v11.1.0/chardev/char-file.c#L55-L68); [chardev/char-win.c v11.1.0, lines 161-180](https://github.com/qemu/qemu/blob/v11.1.0/chardev/char-win.c#L161-L180)
- Documented: `ssd=off` is described as improving exactly this exit path ("significant MMIO performance increase"), and the source comment calls it a "vmexit performance improvement". — [QEMU docs, docs/system/whpx.rst v11.1.0](https://github.com/qemu/qemu/blob/v11.1.0/docs/system/whpx.rst); [whpx-all.c v11.1.0, lines 3208-3213](https://github.com/qemu/qemu/blob/v11.1.0/target/i386/whpx/whpx-all.c#L3208-L3213)
- Source: the Apple SMC device is likewise a plain port-I/O device (data, command and error ports), so every key macOS reads from it is a series of port exits. — [hw/misc/applesmc.c v11.1.0, lines 51-54 and 312-320](https://github.com/qemu/qemu/blob/v11.1.0/hw/misc/applesmc.c#L312-L320)

### Inferences
- A 16550 serial port costs more than one exit per character, because the guest normally reads the line-status register before each byte. A macOS boot with verbose mode and kernel serial output can produce tens of thousands of characters, which is tens to hundreds of thousands of exits, each with a synchronous file write. That slows boot noticeably but stops mattering once the guest goes quiet.
- The useful rule for Orchord: keep `-serial file` and `-debugcon file` available for diagnostics, but make sure the guest side is not told to log there in normal use (OpenCore's logging target not including serial, no `serial=` or `debug=` boot arguments in macOS, no `-v` unless diagnosing). The QEMU options themselves are free while the guest is silent.
- If macOS polls the SMC regularly (sensor and fan keys), that is a steady trickle of port exits that only `ssd=off` makes cheaper; the device cannot be removed because macOS needs it to boot.

### Gaps
- No measurement of per-character cost under WHPX was found.
- How often macOS reads the emulated SMC when idle was not found.

## Options other macOS-on-QEMU projects use that are not KVM-specific

### Takeaway
The three main projects agree on a small set of portable settings. Orchord already matches most of them; the ones it does not use are `hpet=off`, virtio-blk and virtio-net for Big Sur and later, disabling S3 sleep, and disabling 1 GB pages. None of the projects publishes measurements, and all three are tuned for KVM.

### Cited Findings
- quickemu, macOS-specific tweaks: "Disable S3 support in the VM to prevent macOS suspending during install" and "Disable ACPI PCI hotplug to prevent issues with macOS (required for QEMU 6.1+)", implemented as `-global ICH9-LPC.disable_s3=1 -global ICH9-LPC.acpi-pci-hotplug-with-bridge-support=off`. — [quickemu script, lines 688-691](https://github.com/quickemu-project/quickemu/blob/master/quickemu)
- quickemu, processor model: on an Intel host it uses `-cpu host,-pdpe1gb,+hypervisor,vmware-cpuid-freq=on`; otherwise `-cpu Haswell-v2,vendor=GenuineIntel,-pdpe1gb,+avx,+sse,+sse2,+ssse3,vmware-cpuid-freq=on`. Its comments add "A CPU with fma is required for Metal support", "A CPU with AVX2 support is required for >= macOS Ventura", "A CPU with SSE4.2 support is required for >= macOS Catalina". — [quickemu script, lines 615-665](https://github.com/quickemu-project/quickemu/blob/master/quickemu)
- quickemu, devices for Monterey and later: virtio-balloon, virtio-blk-pci system disk, virtio-net-pci, virtio-sound-pci, xHCI, plus a virtio random-number device for all guests. — [quickemu script, lines 1095-1104 and 1780](https://github.com/quickemu-project/quickemu/blob/master/quickemu)
- OSX-KVM, current defaults: `-cpu Skylake-Client,-hle,-rtm,kvm=on,vendor=GenuineIntel,+invtsc,vmware-cpuid-freq=on` (marked "Enable this line for macOS Sequoia and Tahoe"; Penryn for older releases), `-machine q35`, qemu-xhci with usb-kbd and usb-tablet, an extra usb-ehci, isa-applesmc, `-smbios type=2`, ich9-intel-hda, AHCI disks, virtio-net-pci, vmware-svga. — [OSX-KVM OpenCore-Boot.sh](https://github.com/kholia/OSX-KVM/blob/master/OpenCore-Boot.sh)
- Docker-OSX defaults: `-cpu Penryn,vendor=GenuineIntel,+invtsc,vmware-cpuid-freq=on,+ssse3,+sse4.2,+popcnt,+avx,+aes,+xsave,+xsaveopt,check`, `-smp 4,cores=4`, qemu-xhci only (no EHCI), AHCI disks, vmxnet3. Orchord's Penryn flag list is the same list minus `vmware-cpuid-freq=on` and `check`. — [Docker-OSX Dockerfile, lines 195-213](https://github.com/sickcodes/Docker-OSX/blob/master/Dockerfile)
- Source: QEMU 11.0 and 11.1 added host feature passthrough for WHPX ("enable all supported host features", a host-vendor CPU class, and support for the maximum-feature CPU type). — [QEMU commit history for target/i386/whpx at v11.1.0](https://github.com/qemu/qemu/commits/v11.1.0/target/i386/whpx); [whpx-all.c v11.1.0, lines 2856-2890](https://github.com/qemu/qemu/blob/v11.1.0/target/i386/whpx/whpx-all.c#L2856-L2890)

### Inferences
- The processor model is a plausible, untested lever for software rendering speed. Orchord gives Big Sur and Monterey a Penryn model with a few added features (no AVX2, no FMA, no BMI). macOS's software graphics and media code has faster paths when AVX2 is present. Giving those releases the same Skylake-Client model already used for Sonoma and Sequoia, or testing `-cpu host` now that WHPX in 11.1 supports host features, could make the guest do the same drawing with less processor time. The risk is the usual one for macOS: an unexpected feature combination causing a panic, so it needs testing per release. On the i7-1355U specifically, `-cpu host` would present a hybrid Raptor Lake identity that macOS has never supported and may reject; a named model is safer.
- Disabling S3 (`ICH9-LPC.disable_s3=1`) is not a load setting, but a guest that tries to sleep and fails to wake cleanly looks like a hang, and it is free to set.
- Settings in those projects that are KVM-only and must not be copied: `kvm=on` (a KVM CPU flag), `-enable-kvm`, tap networking scripts, host device passthrough, `/dev/urandom` random-number backends, and anything using memfd or huge pages.
- Combined candidate list for Orchord, most promising first, all needing a test on the target laptop: (1) `-accel whpx,ssd=off`; (2) virtio-blk system disk for Big Sur and later; (3) virtio-net for Big Sur and later; (4) `hpet=off`; (5) drop the unused EHCI controller; (6) lower guest resolution; (7) replace twice-a-second screendump with VNC change-only updates; (8) on Windows 10 hosts, `-machine q35,pic=off`; (9) larger qcow2 L2 cache for disks over 64 GB; (10) try a single-socket topology again on 11.1; (11) AVX2-capable processor model for Big Sur and Monterey; (12) `-accel whpx,hyperv=off` as a timing experiment.

### Gaps
- None of OSX-KVM, quickemu or Docker-OSX documents WHPX or Windows hosts; nothing in them has been validated without KVM. UTM was not examined in this pass (it targets macOS hosts and Apple's hypervisor, so its tuning would be not applicable in any case).
- No project publishes before-and-after processor measurements for any of these settings.
- I found no report of anyone running an Intel macOS guest on QEMU with WHPX at all, so every recommendation above is extrapolated from the QEMU source and from KVM practice.
